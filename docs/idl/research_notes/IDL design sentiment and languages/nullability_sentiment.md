# Required-by-default vs optional-by-default in API/schema modelling languages

Research notes, 2026-10-08. Scope: designer rationale and practitioner sentiment on whether fields should be required by default (optional marked `?`) or optional by default (required marked explicitly), and how `= default` interacts with requiredness. Every claim carries a source; opinions are attributed. Where a primary design document could not be retrieved, that is recorded under Gaps rather than paraphrased from memory.

Terminology used below (several sources conflate these, so the notes keep them apart):
- **Requiredness** (presence): must the key/field be on the wire?
- **Nullability**: may the value be `null`?
- **Default**: what a reader substitutes when the field is absent.
- **Presence tracking**: can the reader tell "absent" from "set to the default value"?

## Key question 1: What did each language / schema system choose, and why?

### Takeaway
General-purpose languages designed or retrofitted after ~2010 (Kotlin, Swift, Rust, Dart, C# 8, TypeScript with `strictNullChecks`) uniformly chose **non-null / present by default** with an explicit opt-in marker (`?`, `Option<T>`), citing Hoare's "billion-dollar mistake" and the claim that most values are non-null. Wire/schema systems split: those whose authors were burned by parser-enforced `required` (protobuf, Cap'n Proto, Thrift's implicit "default" requiredness, Avro, JSON Schema/OpenAPI, GraphQL) chose **optional/nullable by default**, each for an evolution or error-containment reason; newer IDLs aimed at humans writing REST APIs (TypeSpec, Fern, Prisma, and Smithy 2.0 in effect) chose **required by default with `?`/`optional<>`** for ergonomics, and Smithy 2.0 added client-side rules so that required-by-default does not reintroduce "required is forever".

### Cited Findings

**General-purpose languages**

- **C# (nullable reference types, Mads Torgersen, Nov 15 2017):** "We believe that it is more common to want a reference _not_ to be null." and "Nulls, not the absence of them, should be the thing that you explicitly have to opt in to." Non-nullable became the default on opt-in so that existing code benefits; enforcement is "in the form of _warnings_, not errors." — [Torgersen, .NET Blog](https://devblogs.microsoft.com/dotnet/nullable-reference-types-in-csharp/)
- **Dart (Bob Nystrom, "Understanding null safety", July 2020):** principle "Code should be safe by default"; the team made "all types _non-nullable by default_"; nullable types are written by "slapping `?` at the end of the underlying base type" as shorthand for a union with `Null`. Justification: "Most existing Dart code is dynamically correct and does not throw null reference errors," so the default should match how code is already written. Soundness is only guaranteed "in Dart programs that are fully null safe." — [dart.dev](https://dart.dev/null-safety/understanding-null-safety)
- **Rust (The Rust Book, ch. 6):** "Rust does not have nulls, but it does have an enum that can encode the concept of a value being present or absent. This enum is `Option<T>`." "In order to have a value that can possibly be null, you must explicitly opt in by making the type of that value `Option<T>`... Everywhere that a value has a type that isn't an `Option<T>`, you _can_ safely assume that the value isn't null. This was a deliberate design decision for Rust to limit null's pervasiveness." Quotes Hoare: "I call it my billion-dollar mistake." — [doc.rust-lang.org](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html)
- **Kotlin:** "Null safety is a Kotlin feature designed to significantly reduce the risk of null references, also known as The Billion-Dollar Mistake." "To allow `null` values, declare a variable with a `?` sign right after the variable type." The docs list Java interop via platform types as one of the only remaining NPE sources. — [kotlinlang.org](https://kotlinlang.org/docs/null-safety.html)
- **Swift:** Chris Lattner (interview) frames optionals as "is something there or is it missing", not pointers; community explanations (Treehouse forum) argue making everything optional "would be cumbersome and would require constant nil checks." No primary Swift design rationale for the non-optional default was retrieved. — [Hacking with Swift interview](https://www.hackingwithswift.com/interviews/chris-lattner-chris-lattner-explains-optionals); [Treehouse community](https://static.teamtreehouse.com/community/why-arent-all-the-types-just-optional-by-default)
- **TypeScript:** optional properties are `?`; without `exactOptionalPropertyTypes` the compiler treats "key absent" and "key present with `undefined`" identically. TSConfig reference: `colorThemeOverride: undefined` "is not the same as `colorThemeOverride` not being defined", e.g. under the `in` operator; the flag makes TypeScript "truly enforce the definition provided as an optional property." The flag is not part of `strict`. — [typescriptlang.org tsconfig](https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html). TkDodo ("optional vs undefined"): "required, but potentially undefined does not have the same intent as optional"; `nickname?: string` vs `nickname: string | undefined` differ in whether the key must exist. — [tkdodo.eu](https://tkdodo.eu/blog/optional-vs-undefined). Valibot's maintainer notes the library "does not distinguish between missing and undefined object entries," which mismatches types under the flag, and worries a separate `undefinedable` helper "could make the API harder to use." — [valibot.dev](https://valibot.dev/blog/should-we-change-the-object-schema/)
- **Counter-sentiment on non-null defaults (informal):** gingerbill (Jan 2026) argues the problem is deeper than the default: in reference-heavy languages the options are allow nulls, make every reference optional, or "Require all explicit initialization of every element everywhere". — [gingerbill.org](https://www.gingerbill.org/article/2026/01/11/mitigating-the-billion-dollar-mistake/). A 2009 Digital Mars forum post claims forced non-null leads developers to "invent a means to fool the compiler, some analogue of null reference - a stub object." — [digitalmars.com](https://digitalmars.com/d/archives/digitalmars/D/Re_Null_references_oh_no_not_again_85437.html)

**Wire formats / IDLs**

- **Protobuf proto2:** three labels; current docs: "**Do not use.** Required fields are so problematic they were removed from proto3 and editions." Existing required fields should be treated as "permanent, immutable elements of the message definition"; "It is nearly impossible to safely change a field from `required` to `optional`." Enum interaction: an unrecognized enum value "is treated as if it were missing, which also causes the required value check to fail." — [protobuf.dev proto2 guide](https://protobuf.dev/programming-guides/proto2/)
- **Protobuf proto3 (v3.0.0 release notes):** "required fields are no longer supported"; explicit `optional` disallowed because "fields are optional by default"; "Removal of field presence logic for primitive value fields, removal of required fields, and removal of default values" was done because it "makes proto3 significantly easier to implement with open struct representations" (Android Java, Objective-C, Go), as part of cleaning up protobuf "before pushing the language as the foundation of Google's new API platform." — [GitHub release v3.0.0](https://github.com/protocolbuffers/protobuf/releases/tag/v3.0.0)
- **Protobuf implicit-presence regret (design note, undated):** "We do not recommend using implicit presence for new fields." Implicit presence "was not introduced for its semantics" but for open-struct APIs; the team later concluded open structs were too constraining. Problems: merging (zero does not overwrite), `MergeFrom(Parse(bytes))` differing from `MergeFrom(bytes)`, patches cannot express "set to zero" (hence `FieldMask`), zero fields vanish from ProtoJSON; the presence issue "became the most-commented issue in the Protobuf repository." proto3 `optional` restored explicit presence (experimental in v3.12.0); editions replaced the keyword with `field_presence`, defaulting to explicit. — [protobuf.dev design-decisions](https://protobuf.dev/design-decisions/implicit-presence/)
- **Protobuf editions `field_presence`:** values `LEGACY_REQUIRED` ("required for parsing and serialization"), `EXPLICIT` (default for Editions 2023/2024/2026 and proto2), `IMPLICIT` (proto3 default except for `optional`-labelled fields). "the `required` and `optional` labels no longer exist in Editions." Migration: remove `required`, add `features.field_presence=LEGACY_REQUIRED`. — [protobuf.dev editions features](https://protobuf.dev/editions/features/). The current proto3 guide recommends `optional` "for maximum compatibility with Protobuf editions and proto2" and warns that for implicit fields "you cannot determine whether the default (zero) value was set or parsed from the wire or not provided at all." — [protobuf.dev proto3 guide](https://protobuf.dev/programming-guides/proto3/); field presence guide: "We recommend using the `optional` label with proto3 unless you have a specific reason not to." — [protobuf.dev field_presence](https://protobuf.dev/programming-guides/field_presence/)
- **Buf, "Protobuf Tip #8: Never use required" (M. C. Sunny Young de la Sota, June 3 2025):** `required` was "part of the root cause of many outages in Google's early use of Protobuf"; a missing required field anywhere, even nested, means the parser "throws away the parsed message"; it moves application-layer errors into the transport layer "opaquely"; Google's internal `protoc` blocks new `required` fields via a fixed allowlist of existing symbols; the coordination needed to remove one is "anathema to Protobuf's core principle of making gradual rollouts safe." Conclusion: "Don't use `required`. It's really not worth it." — [buf.build](https://buf.build/blog/totw-8-never-use-required)
- **Cap'n Proto FAQ (Kenton Varda):** "How do I make a field required? You don't." Calls protobuf's `required` "a horrible mistake": "The validation is baked into the parser, and there's nothing you can do about it." Recounts a scenario where making a field optional broke a data center: "Things like this have actually happened. At Google. Many times." Also: "Cap'n Proto has no notion of 'optional' fields"; every primitive field occupies wire space (compressed away by packing when default-valued); to express optionality, wrap in a union with `Void`, or "give the field a bogus default value and interpret that value to mean 'not present'." For pointer fields `hasFoo()` detects null, but `getFoo()` on a null pointer "returns the default value, which is indistinguishable from a legitimate value." — [capnproto.org/faq](https://capnproto.org/faq.html). Varda on HN (2018): required checks ran on every serialization so "pass-through middlemen rejected messages with missing fields, causing outages"; "A piece of data should be validated by the consumer, but should not be validated by pass-through middlemen." — [HN 18196288](https://news.ycombinator.com/item?id=18196288); (2014) required-field parser enforcement "caused outages in Google Search and Gmail." — [HN 7855458](https://news.ycombinator.com/item?id=7855458)
- **Thrift (IDL spec, "Requiredness"):** "two explicit requiredness values, and a third one that is applied implicitly if neither" is given. Required: always written, "always read and are expected to be contained in the input stream"; a missing one should "indicate an unsuccessful read operation"; cannot be deprecated; removing/relaxing means "the data are no longer compatible between versions." Optional: written only when set, tracked by "isset" flags. Default (unmarked): "opt-in, req-out", described as "a good starting point"; defaults "may not be written"; "An unwritten default becomes part of the interface version." Implementations differ (per the spec itself and JIRA). — [apache/thrift idl.md](https://raw.githubusercontent.com/apache/thrift/master/doc/specs/idl.md). THRIFT-5264 reports Java generating three distinct behaviours while Python/PHP treat all three as optional. — [THRIFT-5264](https://jira.apache.org/jira/browse/THRIFT-5264)
- **Avro (spec 1.11.1):** a field `default` is "only used when reading instances that lack the field for schema evolution purposes"; "The presence of a default value does not make the field optional at encoding time"; "Avro encodes a field even if its value is equal to its default." Resolution: reader field missing from writer → use default, else "an error is signalled"; writer field unknown to reader → "is ignored." — [avro.apache.org](https://avro.apache.org/docs/1.11.1/specification/). Confluent: adding a field is compatible both ways when optional/defaulted; deleting a field compatibly requires it was "either specified as optional or given a default value in the original version." — [Confluent docs](https://docs.confluent.io/platform/8.0/schema-registry/fundamentals/schema-evolution.html)
- **JSON Schema:** "By default, the properties defined by the `properties` keyword are not required." `required` is an array of unique strings (Draft 4 required at least one). "In JSON a property with value `null` is not equivalent to the property not being present." — [json-schema.org](https://json-schema.org/understanding-json-schema/reference/object)
- **OpenAPI:** 3.0 "doesn't support a `null` type but instead allows you to mark a schema as being `nullable`"; 3.1 uses `type: ['null', 'string']`. Matrix: optional+non-null = value or omitted; required+nullable = "always be present, but it can be set to `null`"; optional+nullable = three states. "SDK generators need to use special wrapper types to let users express all three states"; "a simple pointer or `Optional` type can only distinguish between two states." Use optional+nullable only when the API "genuinely treats `null` and omitted differently" (e.g. PATCH: omit = don't change, null = clear). — [Speakeasy](https://www.speakeasy.com/openapi/schemas/null)
- **GraphQL (official docs):** "Most type systems which recognise 'null' provide both the common type and the _nullable_ version... However, in a GraphQL type system, every field is _nullable_ by default. This is because there are many things that can go awry in a networked service backed by databases and other services." Non-null is a guarantee; on error "the previous parent field will be 'null' instead." "Typically it is [appropriate], but occasionally, it's not. In those cases, use non-null types." — [graphql.org schema design](https://graphql.org/learn/schema-design/)
- **GraphQL input side (spec, as quoted by Hasura):** "nullable types are always optional and non-null types are always required." — [Hasura cheatsheet](https://hasura.io/blog/graphql-nulls-cheatsheet)
- **Smithy 2.0 (Kevin Stich, AWS blog, Aug 11 2022, "Fewer nulls in generated code"):** before 2.0 "Smithy code generators essentially treated every structure member as nullable" because modelers "didn't realize only some targeted shapes provide default values" and because `@required` "could be backward-compatibly removed at any time," so the spec "prohibited using it to influence generated types." In 2.0, removing `@required` is no longer free: the member must be given a default, which lets generators produce non-nullable properties. Goal: "reduce the amount of nullable properties in generated code" while letting services "safely evolve their models over long periods of time." — [AWS Developer Tools Blog](https://aws.amazon.com/blogs/developer/introducing-smithy-idl-2-0)
- **Smithy 2.0 spec, structure member optionality:** members with none of `required`/`default`/`clientOptional`/`input`/`addedDefault` are optional. Table: `@required` → present for authoritative consumers, present for non-authoritative "unless also `@clientOptional` or part of an `@input` structure"; same for `@default`. "The required trait indicates that a value MUST always be present for a member in order to create a valid structure." "Requirements change; what is required today might not be required tomorrow." "clientOptional trait is used to indicate that a member that is currently required by authoritative model consumers like servers MAY become completely optional in the future"; non-authoritative consumers "MUST treat the member as if it is not required and has no default value." "Replacing both the required and clientOptional trait with the default trait is _not_ a backward compatible change." Members of `@input` structures: clients "MUST treat each member as nullable regardless of the `required` or `default` trait." Clients MAY apply error correction (e.g. `false`, `0`, `""`, `{}`) when a misconfigured server omits a required member. — [smithy.io aggregate types](https://smithy.io/2.0/spec/aggregate-types.html)
- **Smithy type-refinement traits:** `clientOptional` "Requires that non-authoritative generators like clients treat a structure member as optional" and exists for when "a service is unsure if a member will be required forever"; after `required` is removed, `required`/`default` act "only as a server-side concern." `@input` structures: "Required top-level members of an `@input` structure are implicitly `clientOptional`"; the structure may be used only as one operation's input. `addedDefault` marks a default added after publication so tooling can "decide whether to ignore the `@default` trait if it will break backward compatibility." Root-level defaults may not change; a member default "should not change, though it may change in extreme cases." — [smithy.io type refinement traits](https://smithy.io/2.0/spec/type-refinement-traits.html). Smithy 1.72.0 changed `AddedRequiredMember` so it "no longer flags new members marked with the @clientOptional trait, which is the sanctioned way to add a @required member without breaking generated client code." — [smithy 1.72.0 release notes](https://newreleases.io/project/github/smithy-lang/smithy/release/1.72.0)
- **TypeSpec:** "Properties can be designated as optional by using the `?` symbol" (`address?: string`); "Properties can be assigned a default value using the `=` operator" (`age: uint8 = 0`, `address?: string = "wild"`). The docs never state "required by default" explicitly; it is implied by `?` being the only marker. — [TypeSpec models docs](https://github.com/microsoft/typespec/blob/main/website/src/content/docs/docs/language-basics/models.md). In OpenAPI emission: "a '?' following the parameter name indicates it is optional" (`required: false`), otherwise `required: true`; `answer?: int32 = 42` emits `default: 42`. — [TypeSpec for OpenAPI developers](https://typespec.io/docs/getting-started/typespec-for-openapi-dev/)
- **Fern Definition:** built-in `optional<T>` ("Optional value, e.g., `optional<string>`"); the `Address` example wraps only `line2` in `optional<>`; in sample JSON the `line2` key is omitted. Required-by-default is implied, not stated. Fern says the Fern Definition format is not recommended for new customers. — [buildwithfern.com types](https://buildwithfern.com/learn/api-definitions/ferndef/types)
- **Prisma:** `?` marks a field optional (e.g. `bio String?`) and nullable in the DB; generated create/update types mark defaulted/autoincrement fields optional even when the model field is required. — [prisma discussion #12703](https://github.com/prisma/prisma/discussions/12703)
- **Google AIP-203 (field_behavior):** "Fields with no annotation are interpreted as `OPTIONAL` for backwards-compatibility" yet "this annotation **must not** be omitted" because requiring it "forces the API author to explicitly consider the behavior." `REQUIRED` means present and "set to a non-empty value" (a required bool must be `true`); use only for user-provided inputs, never for fields always present in responses. Breaking: adding `REQUIRED` to an existing field, adding a new `REQUIRED` field. Compatible: `REQUIRED` → `OPTIONAL`. — [google.aip.dev/203](https://google.aip.dev/203)

### Inferences
- The two camps optimise for different failure modes. Language designers optimise for in-process null-dereference bugs, where the compiler sees both sides; wire-format designers optimise for cross-version, cross-team deploys where the two sides are compiled from different schema versions. Required-by-default wins the first; optional-by-default (or at least "required is never parser-enforced") wins the second.
- Smithy 2.0 is the clearest attempt to have both: required-by-default types in generated code, with `@clientOptional`/`@input` to keep the wire-evolution escape hatch. It is also the only system surveyed whose designers wrote down that their 1.0 rule was unusable because `@required` "could be backward-compatibly removed at any time."
- TypeSpec and Fern (REST-first, human-authored) picked `?` with no written rationale; the HN sentiment in Q4 suggests the choice was driven by TypeScript familiarity and OpenAPI's out-of-line `required` array.

### Gaps
- No primary design document for Kotlin's or Swift's non-null default was retrieved (Kotlin docs cite Hoare; Swift rationale only via interviews and forums).
- Smithy's IDL 1→2 migration guide page returned empty/404 from every URL tried (smithy.io HTML, `_sources` rst, GitHub blob and raw); its wording on `@box` removal is not quoted. The `smithy.io` spec and AWS blog cover the same ground.
- TypeSpec and Fern state no rationale for required-by-default; treat it as an unexplained convention.
- Thrift's per-language handling of default requiredness is reported as inconsistent in the spec itself; no 2025/2026 confirmation found.

## Key question 2: Documented API-evolution arguments

### Takeaway
Every source agrees on the mechanics: adding a required input field breaks old clients; a parser-enforced required field can never be removed or relaxed safely ("required is forever"); relaxing output non-null to nullable breaks consumers who stopped checking. Disagreement is about *where* requiredness should be enforced (parser vs application) and whether the type system or the compatibility checker should own it.

### Cited Findings
- **"Required is forever" / cannot remove:** protobuf proto2 docs: required fields are "permanent, immutable elements"; stale readers "will consider messages without this field to be incomplete." — [protobuf.dev proto2](https://protobuf.dev/programming-guides/proto2/). Buf: removing requires downgrading everywhere while still setting it, updating all users, then deleting and reserving; once a required field has spread beyond one team, removal is "impossible." — [buf.build](https://buf.build/blog/totw-8-never-use-required). Thrift spec: a required field "can't be deprecated" because it must always be present on read. — [thrift idl.md](https://raw.githubusercontent.com/apache/thrift/master/doc/specs/idl.md). libp2p specs discussion: "a required field is forever" and failing decodes "forces clients to add their own validation logic" anyway. — [libp2p/specs#465](https://github.com/libp2p/specs/issues/465)
- **Pass-through breakage:** Cap'n Proto FAQ and Varda's HN comments: intermediaries that merely forward messages rejected them, and relaxing a field to optional on one side broke whole data centers. — [capnproto.org/faq](https://capnproto.org/faq.html); [HN 18196288](https://news.ycombinator.com/item?id=18196288)
- **Adding a required input field breaks clients:** AIP-180: "New required fields **must not** be added to existing request messages or resources"; "Any field being populated by clients **must** have a default behavior matching the behavior before the field was introduced"; "Any field previously populated by the server **must** continue to be populated"; "Changing the default value is considered breaking." — [google.aip.dev/180](https://google.aip.dev/180). AIP-203: adding `REQUIRED` to an existing field is incompatible, `REQUIRED`→`OPTIONAL` is compatible. — [google.aip.dev/203](https://google.aip.dev/203). Apollo (Stubailo, 2018): "Non-null in arguments and input object types has serious implications for backwards compatibility"; prefer adding a new field over tightening an existing one. — [Apollo blog](https://www.apollographql.com/blog/using-nullability-in-graphql). Apollo GraphOS guide: "converting a nullable argument or input field for a mutation to non-null may lead to breaking changes," while "converting a non-nullable argument to nullable is not a breaking change." — [Apollo GraphOS nullability](https://www.apollographql.com/docs/graphos/schema-design/guides/nullability)
- **Output asymmetry (relaxing breaks consumers):** Stubailo: removing non-null from an output field "is also breaking, because consuming code may assume the value exists" (`restaurant.location is undefined`). — [Apollo blog](https://www.apollographql.com/blog/using-nullability-in-graphql). Hasura: nullable fields are "easier to evolve"; removing non-null "can break clients you don't control." — [Hasura](https://hasura.io/blog/graphql-nulls-cheatsheet). Lee Byron (wg#1700, 2025): output types should become more constrained as they gain adornments; "changing `Int` to `Int?` would break clients, while changing `Int` to `Int!` would not." — [rfcs.graphql.org wg1700](https://rfcs.graphql.org/rfcs/wg1700/). Semantic Nullability RFC solution 1: "Moving from a nullable type to a semantic non-nullable type (on output) is a non-breaking change." — [rfcs.graphql.org SemanticNullability](https://rfcs.graphql.org/rfcs/SemanticNullability/). captbaritone (wg#1394): nullable defaults let owners "turn a non-nullable field into a nullable field as a non-breaking change." — [rfcs.graphql.org wg1394](https://rfcs.graphql.org/rfcs/wg1394/)
- **Smithy's rule:** removing `@required` requires adding a default (so types stay non-null); `@clientOptional` exists for when "a service is unsure if a member will be required forever"; replacing `required`+`clientOptional` with `default` is not backward compatible; `addedDefault` lets tools ignore a late default that would break them. — [smithy.io type refinement traits](https://smithy.io/2.0/spec/type-refinement-traits.html); [smithy.io aggregate types](https://smithy.io/2.0/spec/aggregate-types.html)
- **Avro:** new fields need a default; a field can only be removed compatibly if it was optional or defaulted from the start; workaround for a required field is to add a default in one release, remove in the next. — [Confluent](https://docs.confluent.io/platform/8.0/schema-registry/fundamentals/schema-evolution.html); [Avro spec](https://avro.apache.org/docs/1.11.1/specification/). Note: Conduktor's matrix marks removing a non-defaulted field as backward compatible, contradicting Confluent/Oracle. — [Conduktor](https://conduktor.io/blog/schema-evolution-avro-compatibility-guide)
- **Presence-mode switches:** protobuf: switching explicit↔implicit presence is "a binary-compatible change for serialized values in wire format" but a round trip through an implicit-presence peer can drop an explicitly set default, so "This change may or may not be safe, depending on the application's semantics." — [protobuf.dev field_presence](https://protobuf.dev/programming-guides/field_presence/)
- **GraphQL versionless evolution rationale:** "GraphQL only returns the data that's explicitly requested, so new capabilities can be added via new types or new fields on existing types without creating a breaking change." — [graphql.org](https://graphql.org/learn/schema-design/)

### Inferences
- The asymmetry is directional and consistent across systems: tightening input breaks clients, loosening output breaks clients. A modelling language that uses one keyword for both sides must either accept that the same edit is breaking in one direction per side, or (as Smithy does) give clients a different reading of the keyword.
- "Required is forever" is specifically a property of *parser-enforced* required. Systems that enforce required at the application/validation layer (JSON Schema, OpenAPI, Smithy servers, AIP-203) can relax it compatibly, and all of them document that direction as safe.

### Gaps
- No quantitative incident data beyond Varda's and Buf's "many outages at Google" claims; these are first-hand but unaudited.
- Stripe's convention (fields "always present, possibly null") is inferred from a 2012 changelog ("Fields with null values are now included in API responses") and its versioning essay, not from a stated rule. — [Stripe changelog 2012-02-23](https://docs.stripe.com/changelog/2012-02-23/fields-null-values-included-api-responses)

## Key question 3: Server vs client asymmetry

### Takeaway
Only Smithy 2.0 formalises giving one field different nullability per side (authoritative vs non-authoritative consumers, `@clientOptional`, `@input`). Protobuf and GraphQL get asymmetry indirectly: protobuf through presence tracking and AIP field_behavior annotations, GraphQL through the input/output type split and, since 2024-25, client-side error handling (`@semanticNonNull`, `@catch`, `@throwOnFieldError`).

### Cited Findings
- **Smithy:** "Authoritative model consumers like servers MAY choose to determine optionality using more restrictive rules by ignoring the `@input` and `@clientOptional` traits." Non-authoritative generators ignore `@default` on `clientOptional` members and serialize whatever is given; servers keep `required` and `default` as "a server-side concern." Members of `@input` structures are implicitly `clientOptional`, so "Removing `required` from them is backward compatible." — [smithy.io aggregate types](https://smithy.io/2.0/spec/aggregate-types.html); [smithy.io type refinement traits](https://smithy.io/2.0/spec/type-refinement-traits.html). `NullableIndex.CheckMode` offers `CLIENT`, `CLIENT_CAREFUL` (treats members targeting structures/unions as optional "because these members can never transition to optional using a default trait"), and a server mode for "an authoritative consumer that does not honor the InputTrait and ClientOptionalTrait." — [smithy javadoc](https://smithy.io/javadoc/1.42.0/software/amazon/smithy/model/knowledge/NullableIndex.CheckMode.html)
- **Smithy real outcome (smithy-rs, Velfi, Aug 17 2023):** "The AWS Rust SDK and smithy-rs code generator have both been updated to respect smithy's @required trait," removing "unnecessary `Option`" from required simple-type members; for AWS SDKs required members targeting structures/unions stay optional because they "can never transition from `@required` to optional using a `@default` trait." Default modes: `CLIENT` for generic clients, `CLIENT_CAREFUL` for AWS SDKs. Upgrade: remove `.unwrap()` calls. The discussion had four thumbs-up and no complaints at retrieval. — [smithy-rs discussion #2929](https://github.com/smithy-lang/smithy-rs/discussions/2929). Opt-out mode `nullabilityCheckMode: "CLIENT_ZERO_VALUE_V1"` and list accessors returning `&[T]` instead of `Option<&[T]>` (`flattenCollectionAccessors`) were both shipped as breaking changes. — [smithy-rs changelog commit](https://telematik.prakinf.tu-ilmenau.de/gitlab/pub/smithy-rs/-/commit/aaf71c83117dd53d9337ab5ca3885089f659a298)
- **Protobuf/AIP:** `OUTPUT_ONLY` fields must be cleared by the server on input without erroring; `REQUIRED` applies only to request/resource input fields, never to "fields that are always present in responses." — [google.aip.dev/203](https://google.aip.dev/203)
- **GraphQL:** inputs: nullable = optional, non-null = required (spec). Outputs: nullable = "may be null on error." Relay: "if a client handles field errors out-of-band, it can treat a field exposed to user code as non-nullable," generating non-null types only when the query opts in with `@throwOnFieldError`. — [relay.dev semantic nullability](https://relay.dev/docs/guides/semantic-nullability/). Apollo Kotlin: `@semanticNonNull` + `@catch` "change the GraphQL default from 'handle every field error' to 'opt-in the errors you want to handle'"; `@semanticNonNullField` lets a client add the marking without editing the server schema. — [Apollo Kotlin nullability](https://www.apollographql.com/docs/kotlin/advanced/nullability). GAP-49: the Non-Null type "does two jobs at once," and authors "frequently make fields nullable purely to contain the blast radius of field errors." — [gaps.graphql.org GAP-49](https://gaps.graphql.org/GAP-49/draft/)
- **Cap'n Proto:** no requiredness on either side; the FAQ's position is that "Infrastructure shouldn't inspect content" and validation is for the consuming application. — [capnproto.org/faq](https://capnproto.org/faq.html)

### Inferences
- Smithy's `@input` rule is the designers' answer to "required by default breaks evolution": the type is required-by-default for the server (validation, non-null server structs), while the generated client builder treats every input member as optional so the service can later drop `@required` without a client breaking change. The cost is that client code for inputs sees `Option` everywhere, which is exactly what the 2.0 effort tried to reduce for outputs.
- GraphQL is converging on the same split from the other direction: the schema says "semantically non-null," and the client decides whether to see `T` or `T | null` based on its error-handling mode.

### Gaps
- No published post-mortem from AWS on whether `@clientOptional`/`@input` was later regretted or widely used outside AWS SDKs.
- Relay's and Apollo's semantic-nullability docs are explicitly "temporary"/experimental; spec PR 1165 (April 30 2025) was still a draft at the latest page revision found (2025-05-01). — [graphql-spec PR 1165](https://github.com/graphql/graphql-spec/pull/1165)

## Key question 4: Ergonomics evidence and practitioner sentiment

### Takeaway
Sentiment strongly favours required/non-null by default for *consumers' type ergonomics* (TypeScript, Rust, Kotlin users; GraphQL client authors; Lee Byron's own aesthetic preference), and equally strongly opposes *parser-enforced* required on the wire (protobuf/Cap'n Proto veterans). Evidence is anecdotal and HN/working-group opinion; no survey data was found. Reddit could not be queried (blocked to the crawler).

### Cited Findings
- **GraphQL designers' own ambivalence:** Lee Byron (wg#1700, March 2025): "I believe most systems will have more non-null fields than nullable. It bothers me that schema will be littered with `!`." He nonetheless proposes keeping unadorned = nullable because adornments should constrain output types, and error bubbling should become opt-in legacy behaviour via `@propagateError`. — [rfcs.graphql.org wg1700](https://rfcs.graphql.org/rfcs/wg1700/)
- **"Nullable epidemic":** the Semantic Nullability RFC (Benjie, created 2025-02-15) says the project has "strongly encourage[d] nullable usage throughout a schema," pushing null-handling onto consumers; `!` is nicknamed "kills parent on exception"; Jordan Eldredge's "true nullability" schema was judged to cause an "explosion" of question marks in Relay; Relay "wanted error propagation disabled entirely." — [rfcs.graphql.org SemanticNullability](https://rfcs.graphql.org/rfcs/SemanticNullability/). Earlier RFC 1153: advice to mark fields nullable "even when null is never a valid value" led to "client code full of unnecessary null checks, or code that bypassed type safety." — [rfcs.graphql.org/rfcs/1153](https://rfcs.graphql.org/rfcs/1153/)
- **Client-vendor view:** Apollo Kotlin: "This nullable default has one major drawback for frontend developers," requiring every field to be null-checked in UI code. — [Apollo Kotlin](https://www.apollographql.com/docs/kotlin/advanced/nullability)
- **Defenders of nullable-by-default:** PostGraphile: "Everything else is nullable, because **errors happen** and we don't want them to cascade to sibling fields"; only `nodeId` and `query` are non-null because they "can never error"; even FK-backed relations are nullable because row-level security may hide the row. — [postgraphile.org why-nullable](https://postgraphile.org/postgraphile/5/why-nullable). Hasura (Sezgi Ulucam, May 14 2020): "make everything nullable except when it doesn't make sense"; non-null means you "forfeit your right to partial data." — [Hasura](https://hasura.io/blog/graphql-nulls-cheatsheet). Apollo GraphOS: "it's often best to err on the side of embracing that default behavior as new fields are initially added," but non-null fields let clients "know exactly where to expect values." — [Apollo GraphOS](https://www.apollographql.com/docs/graphos/schema-design/guides/nullability). Stubailo (2018) calls nullable-by-default "a good decision" because over-using non-null "can be a risky proposition if you don't think ahead." — [Apollo blog](https://www.apollographql.com/blog/using-nullability-in-graphql)
- **Protobuf sentiment on HN (attributed):**
  - cletus (2020): "required vs optional fields was a design mistake" that can't be fixed without breaking changes. — [HN 23486722](https://news.ycombinator.com/item?id=23486722)
  - yongjik (2020): "there's nothing inherently wrong with required fields"; the problem is the API, since a new message starts with required fields missing, an invalid state. — [HN 24690930](https://news.ycombinator.com/item?id=24690930)
  - ghostwriter (2021): required fields are needed to tell missing-by-intent from missing-by-mistake; "required fields is a low-level 'must have' bit." — [HN 29502170](https://news.ycombinator.com/item?id=29502170)
  - repolfx (2018): required/optional is just nullability in the type system; "required considered harmful" is "completely wrong for any normal business" and specific to Google's circumstances. — [HN 18194923](https://news.ycombinator.com/item?id=18194923)
  - mattnewton (2019): "required was a mistake, in my opinion," pointing to the Cap'n Proto FAQ. — [HN 21873482](https://news.ycombinator.com/item?id=21873482)
  - sgeisenh (2022): protobuf "allows some things that tend to be design mistakes (e.g. required fields)," corrected by proto3 and field_behavior. — [HN 29988613](https://news.ycombinator.com/item?id=29988613)
  - kentonv (2025): "In practice, you want to declare all fields optional to give yourself maximum flexibility for change." — [HN 45140590](https://news.ycombinator.com/item?id=45140590); (2021) "optional fields (with default values) provide the right balance between making changes easy." — [HN 29500050](https://news.ycombinator.com/item?id=29500050); (2019) "Optional fields are not primarily about nullability but about compatibility." — [HN 21873418](https://news.ycombinator.com/item?id=21873418)
  - codeflo (2024, TypeSpec thread): lists required fields among TypeSpec features that stood out, criticising protobuf for being unable to distinguish a missing string from an empty string. — [HN 41603186](https://news.ycombinator.com/item?id=41603186)
- **proto3 presence backlash:** a 2015 Go maintainer reply: "That's working as intended, and a deliberate choice for proto3. You simply aren't supposed to differentiate fields explicitly set to their zero value from fields not touched at all." — [golang/protobuf#15](https://github.com/golang/protobuf/issues/15). Ivan Velichko (2019): an unknown age reads as `0`, "which would wrongly mark the person as a child"; recommends wrapper types. — [iximiuz.com](https://iximiuz.com/en/posts/truly-optional-scalar-types-in-protobuf3/). The protobuf team's own design note records the presence issue as the repository's most-commented. — [protobuf.dev implicit presence](https://protobuf.dev/design-decisions/implicit-presence/)
- **TypeScript `?` ergonomics:** TkDodo: with `exactOptionalPropertyTypes` a `Partial<User>` can no longer hold `{ id: undefined }`, which is "exactly what you'll get with the new flag turned on." — [tkdodo.eu](https://tkdodo.eu/blog/optional-vs-undefined). DOM lib issue: optional `lib.dom.d.ts` fields lack `| undefined`, so passing `signal: AbortSignal | undefined` to `fetch` fails under the flag, which the reporter says "makes their construction needlessly difficult." — [TypeScript-DOM-lib-generator#2119](https://github.com/microsoft/TypeScript-DOM-lib-generator/issues/2119)
- **Migration story (Smithy → Rust SDK):** required simple-type members lost their `Option`; upgrade guidance is to delete `.unwrap()`. Four positive reactions, no recorded complaints. — [smithy-rs #2929](https://github.com/smithy-lang/smithy-rs/discussions/2929)
- **Validation-library note:** Valibot explicitly chose not to distinguish missing from `undefined` and worries a second helper "could make the API harder to use." — [valibot.dev](https://valibot.dev/blog/should-we-change-the-object-schema/)

### Inferences
- Practitioners separate two questions that the keyword conflates: (a) what the generated type should look like (overwhelming preference: non-null unless marked) and (b) whether the deserializer should reject a message lacking the field (overwhelming preference among wire-format veterans: no). A modelling language can satisfy both by making `required` a type-level and validation-level fact while never making it a parse-level fact.
- The GraphQL community's decade-long arc (nullable default → "nullable epidemic" → semantic nullability) is the richest evidence that optional-by-default on outputs imposes a persistent tax on consumers that schema authors end up paying for later.
- Where most fields are required, `?` wins on visual noise; Byron's "littered with `!`" is the clearest designer admission of that cost.

### Gaps
- No surveys or quantitative measurements of either ergonomics or defect rates were found; everything above is designer or practitioner opinion.
- Reddit (r/programming, r/graphql, r/rust) is blocked to the search crawler; no Reddit threads are cited.
- HN threads on TypeSpec specifically returned only one relevant comment; sentiment on TypeSpec's `?` convention is thin.
- No "migration from nullable-by-default to non-null-by-default" case study with before/after numbers was found; the closest are the Relay/Apollo semantic-nullability guides and smithy-rs #2929.

## Key question 5: Defaults vs requiredness; "absent", "null" and "default" as wire states

### Takeaway
Systems disagree on whether a default makes a field "required with fallback" or merely a read-time substitution, and on whether absent, null and default-valued are distinguishable. Protobuf explicit presence, JSON Schema/OpenAPI 3.1, TypeScript (with the strict flag), Thrift optional, and Smithy keep absent distinct from default; proto3 implicit presence, Cap'n Proto, Avro (on write) and Thrift's implicit "default" requiredness collapse them. Smithy is the only surveyed IDL that spells out the type-level consequence: `@default` makes the generated property non-null while keeping the member omittable on the wire, and it warns that this makes defaults unusable for partial updates.

### Cited Findings
- **Protobuf explicit presence:** set = "contains a value that was explicitly set or parsed from the wire. It will be serialized"; unset = "will return the default value. It will not be serialized." Implicit presence: "no way of telling whether that field was explicitly set to the default value"; `-0` is the one default-like float that stays on the wire. Null is not a wire state; Kotlin's "nullable field accessor" is a language-API detail. — [protobuf.dev proto3](https://protobuf.dev/programming-guides/proto3/). Editions `EXPLICIT`: "An explicitly set value is always written to the wire, even when it equals the default"; `IMPLICIT`: "A default value is not written to the wire, even if it was set explicitly." — [protobuf.dev editions](https://protobuf.dev/editions/features/). Under implicit presence, partial updates cannot say "set to zero," which is why `FieldMask` exists. — [protobuf.dev implicit presence](https://protobuf.dev/design-decisions/implicit-presence/)
- **Proto2 explicit defaults:** `[default = 10]`; when omitted "The `results_per_page` field is not present" yet the getter returns 10; if sent, "the sender's value is returned." — [protobuf.dev proto2](https://protobuf.dev/programming-guides/proto2/)
- **AIP-203 treats default as unset:** "Zero, empty, and false values count as unset, so a required boolean must be set to `true`." — [google.aip.dev/203](https://google.aip.dev/203)
- **Cap'n Proto:** every primitive field always has a value (its default, zero unless declared); "default-valued fields will be compressed away if you enable packing"; for pointers, `getFoo()` on null "returns the default value, which is indistinguishable from a legitimate value" and only `hasFoo()` tells. Recommended optionality idiom: "give the field a bogus default value and interpret that value to mean 'not present'." — [capnproto.org/faq](https://capnproto.org/faq.html)
- **Thrift:** required fields: "Defaults are always written"; optional: defaults written "when the isset flag is set"; implicit default requiredness: defaults "may not be written"; "An unwritten default becomes part of the interface version. Changing that default changes the interface. If the default value is written into the output, the IDL default can change without affecting serialized data." Null cannot be transported ("especially null values, which Thrift can't transport"). — [thrift idl.md](https://raw.githubusercontent.com/apache/thrift/master/doc/specs/idl.md)
- **Avro:** "The presence of a default value does not make the field optional at encoding time"; "Avro encodes a field even if its value is equal to its default"; defaults are "only used when reading instances that lack the field." Null is a type (`["null","string"]` with `"default": null` is the optional idiom). — [Avro spec](https://avro.apache.org/docs/1.11.1/specification/)
- **JSON Schema / OpenAPI:** `null` present ≠ absent; `"email": null` fails a `string` type constraint even if `email` is required. — [json-schema.org](https://json-schema.org/understanding-json-schema/reference/object). Required+nullable = "always be present, but it can be set to `null`"; optional+nullable = three states, needing "special wrapper types" in SDKs; reserve for APIs that "genuinely treat `null` and omitted differently" such as PATCH (omit = don't change, null = clear). — [Speakeasy](https://www.speakeasy.com/openapi/schemas/null)
- **TypeScript:** `?` without the flag conflates absent and `undefined`; `exactOptionalPropertyTypes` separates them (`in` operator behaves differently). — [typescriptlang.org](https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html)
- **TypeSpec:** `=` may be placed on required (`age: uint8 = 0`) or optional (`address?: string = "wild"`) properties; emitted to OpenAPI as `default:`. No semantics stated for whether a defaulted required property may be omitted on the wire. — [TypeSpec models](https://github.com/microsoft/typespec/blob/main/website/src/content/docs/docs/language-basics/models.md); [TypeSpec for OpenAPI](https://typespec.io/docs/getting-started/typespec-for-openapi-dev/)
- **Smithy:** `@default` "gives a structure member a default value" (`days: Integer = 0`); migrating `@required` → `@default` keeps the member "always present to tools" while supplying a value if missing; "a member marked @required MUST be serialized, including members that have a default." The default trait "shouldn't be used for partial updates, because a server can't tell an omitted value from one set to the default." Non-authoritative implementations ignore `@default` on `clientOptional` members and "serialize whatever value is given." Root-level defaults cannot change; member defaults should not. — [smithy.io type refinement traits](https://smithy.io/2.0/spec/type-refinement-traits.html); [smithy.io aggregate types](https://smithy.io/2.0/spec/aggregate-types.html)
- **GraphQL:** no separate "absent vs null" on output (a field is either requested-and-present or errored-to-null); on input, "nullable types are always optional and non-null types are always required," and a nullable variable cannot be passed to a non-null argument. — [Hasura](https://hasura.io/blog/graphql-nulls-cheatsheet)
- **Prisma:** model fields with defaults/autoincrement are required on the model type but optional on the generated create/update input types. — [prisma discussion #12703](https://github.com/prisma/prisma/discussions/12703)

### Inferences
- "Default makes it required-with-fallback" is exactly Smithy's and (post-regret) protobuf's model: the *type* is non-null, the *wire* may omit, and presence tracking decides whether the two can be told apart. Every system that dropped presence tracking (proto3 implicit, Cap'n Proto, Thrift implicit) later documented the partial-update/merge problem as the price.
- A design that supports PATCH-style semantics needs three states on at least some fields (absent / null / value) and therefore cannot let `= default` erase absence; Speakeasy's and Smithy's guidance both say to keep defaults off fields used for partial updates.
- Changing a default is treated as breaking by AIP-180, Smithy, and Thrift-when-unwritten; it is safe only when the default value is always written (Avro, Thrift-when-written, protobuf `EXPLICIT` with the value set).

### Gaps
- TypeSpec does not document whether a defaulted non-optional property may be omitted by a client, nor how emitters other than OpenAPI treat `=`.
- Fern's handling of defaults and `nullable<>` vs `optional<>` was not found on the retrieved types page.
- No source was found giving measured frequency of three-state (absent/null/value) fields in real APIs.
