# Resources and lifecycle, custom metadata, and tooling/compiler distribution

Research notes, collected 2026-10-08. Scope: (A) first-class resource/lifecycle modelling, (B) custom metadata and project-defined annotations, (C) tooling and compiler-distribution expectations. Sources are primary docs, GitHub issues, vendor blogs and Hacker News threads; opinions are attributed to the handle or author that stated them.

---

## A1. How Smithy resources work and where users hit friction

### Takeaway
Smithy's resource construct is the most complete first-class lifecycle model in a mainstream IDL (identifiers, properties, six lifecycle slots, child resources, collection operations, name-based binding with `@property`/`@notProperty`/`@nestedProperties`/`@resourceIdentifier` escape hatches and `for Resource` elision). The friction users report is almost entirely about the *binding* rules: name-based inference plus validation that is strict in some places (every top-level member must bind) and incomplete in others (list output bindings), with error messages the maintainers themselves call unclear.

### Cited Findings
- Definition: "Smithy defines a resource as an entity with an identity that has a set of operations." Members are `identifiers`, `properties`, lifecycle operations (`create`, `put`, `read`, `update`, `delete`, `list`), `operations`, `collectionOperations`, and child `resources`. — [Smithy 2.0 spec, Service types](https://smithy.io/2.0/spec/service-types.html)
- Identifiers must target string shapes; child resources must repeat all parent identifiers verbatim ("all of the identifiers of the parent resource MUST be repeated verbatim in the child resource"); the spec recommends avoiding the bare name `id` and prefixing with the resource name (`forecastId`). — [Smithy spec](https://smithy.io/2.0/spec/service-types.html)
- Identifier binding is inferred by name: "Identifier bindings are only formed on input or output structure members that are marked as required." A required member whose name and target match an identifier binds implicitly; `@resourceIdentifier` is the explicit override when names differ; explicit wins over implicit. Instance operations bind all identifiers; collection operations omit one or more but must bind all parent identifiers. — [Smithy spec](https://smithy.io/2.0/spec/service-types.html)
- Property binding is also inferred by name: top-level input/output members bind to the property of the same name; `@property(name:)` renames; `@nestedProperties` makes a member's target structure the binding root (and then no adjacent members may bind); `@notProperty` exempts a top-level member. For `list` output, if the trait is omitted and exactly one output member targets a list of structures, the element is resolved automatically, and "automatic resolution treats property binding conflicts as warnings, not errors." — [Smithy spec](https://smithy.io/2.0/spec/service-types.html)
- Validation rules: every top-level member must bind to a declared property unless marked `@notProperty` (or carries a trait that is marked notProperty) or a sibling uses `@nestedProperties`; a declared property that resolves to no member is invalid; a member must target the same shape as the property it binds. — [Smithy spec](https://smithy.io/2.0/spec/service-types.html)
- Lifecycle semantics are constrained by traits: `put` must be idempotent and form instance operations; `create` must form collection operations and may be idempotent; `read` must be `@readonly` and instance; `update` instance and not readonly; `delete` instance and idempotent; `list` collection, readonly, and "should be paginated". — [Smithy spec](https://smithy.io/2.0/spec/service-types.html)
- `@notProperty` selector only matches "a top-level member of an operation's input or output shape, or a trait"; `@nestedProperties` targets' members "may not use property trait, or notProperty trait", so there is no exclusion mechanism one level down. — [Smithy resource traits](https://smithy.io/2.0/spec/resource-traits.html)
- Friction, issue #2294 (2024-05-21, closed by stale bot): `@nestedProperties` combined with `for Resource` elision (`$tenantId`) produced "Member tenantId does not target a property or identifier for resource TenantResource"; two users (libre-man, natehardison) report adding `@required` does not help but adding `@resourceIdentifier("tenantId")` does. Maintainer hpmellema: "The error messages returned for elided identifiers are currently a bit unclear and probably need to be updated." Commenter medwards: closely reading the property-binding validation section "to be very helpful in figuring out what was wrong." — [smithy-lang/smithy#2294](https://github.com/smithy-lang/smithy/issues/2294)
- Friction, issue #2968 (2026-02-13): a nested resource with only a `list` operation errors with "Resource property `Name` is not used in the input or output of create or an instance operation." Maintainer JordonPhillips: "we seem to not consider properties bound to the output list to be bound at all, for any purpose. The same is true for identifiers." A contributor notes `PropertyBindingIndex.getOutputPropertiesShape()` never looks through a list member into the element structure. — [smithy-lang/smithy#2968](https://github.com/smithy-lang/smithy/issues/2968)
- Friction, issue #2211 (2024-03-25): a user cannot document identifiers/properties inside the `resource` block; `///` and `@documentation` are invalid there, and documenting via elision "leads to a lot of duplication". Maintainer mtdowling: "Resource properties and identifiers aren't members so they can't bear traits. They point to root level shapes ... This turns out to be a very good thing. It encourages shape reuse and consistency across resource operations ... It also makes automatic identifier and resource property binding work." — [smithy-lang/smithy#2211](https://github.com/smithy-lang/smithy/issues/2211)
- Rationale from the Smithy lead on HN (May 2021): "Resources also help us to point service teams in the right direction to make their services work well over HTTP", and resource modelling lets AWS services automatically support CloudFormation resource schemas (mtdowling). — [HN 27081084](https://news.ycombinator.com/item?id=27081084)
- Smithy's CloudFormation integration derives a resource schema from the lifecycle: properties come from identifiers plus top-level members of `read` output, `put`/`create`/`update` input and `additionalSchemas`; mutability is derived (in `create` input only = create-only; in `read` output = read-only; in `update` input = write, or full if also in create/read) and overridable via `@cfnMutability(full|create|create-and-read|read|write)`, `@cfnExcludeProperty`, `@cfnName`, `@cfnAdditionalIdentifier`, `@cfnDefaultValue`. Rationale: "Automatically generating schemas from a service's API lowers the effort needed to generate and maintain them." — [Smithy aws.cloudformation traits](https://smithy.io/2.0/aws/aws-cloudformation.html)

### Inferences
- Name-based inference is the source of both Smithy's ergonomics (little boilerplate, `for Resource` elision) and its confusing failures: when inference misfires the user has to learn five traits and a validation section to understand why. A new language should make the binding rule trivially explainable and make every error name the rule that fired.
- The `list` gap (#2968, still being worked in 2026) shows that collection-element binding is a distinct case from instance binding and needs first-class treatment in the IR, not a validator afterthought.
- The CloudFormation trait set is a concrete checklist of what a lifecycle model must expose to an infrastructure generator: identifier set, per-property mutability derived from which operations carry it, rename, exclusion, additional identifiers, defaults.

### Gaps
- No GitHub issue mentions `@notProperty` by name (`gh search issues --repo smithy-lang/smithy "notProperty"` returned nothing); friction evidence is from `nestedProperties`/elision/list issues only.
- No quantitative data on how many non-AWS Smithy models use `resource` at all.

## A2. TypeSpec resource templates and Azure ARM resource modelling

### Takeaway
TypeSpec has no resource keyword; `@typespec/rest` supplies `@resource`/`@key`/`@parentResource` decorators plus `Resource*` interface templates and `@autoRoute`, and the Azure Resource Manager library layers a stricter, lint-enforced vocabulary (`TrackedResource`, `ProxyResource`, `@armResourceOperations`, `@armResourceRead`...). Public sentiment is thin: HN commenters saw TypeSpec as "only extremely simple CRUD" and asked for semantics; the concrete benefit claimed by Microsoft is reuse of API patterns and consistent generated SDKs, without published numbers.

### Cited Findings
- `@typespec/rest` decorators: `@resource` "Mark this model as a resource type with a name."; `@parentResource` "Mark model as a child of the given parent resource."; `@segment` "Defines the preceding path segment for a `@path` parameter in auto-generated routes."; `@autoRoute` resolves routes from segments on models; `@readsResource`/`@createsResource`/`@updatesResource`/`@deletesResource`/`@listsResource` tag an operation's lifecycle role for a resource; `@action` and `@collectionAction` for custom verbs. — [TypeSpec rest decorators](https://typespec.io/docs/libraries/rest/reference/decorators/)
- Interface templates: `ResourceRead<Resource, Error>` ("Represents the resource GET operation"), `ResourceCreate`, `ResourceCreateOrReplace`, `ResourceCreateOrUpdate`, `ResourceUpdate`, `ResourceDelete`, `ResourceList` (returns `CollectionWithNextLink<Resource>`), composites `ResourceOperations`, `ResourceCollectionOperations` (create, list), `ResourceInstanceOperations` (get, update, delete), plus `ExtensionResource*` and `SingletonResource*` variants. — [TypeSpec rest interfaces](https://typespec.io/docs/libraries/rest/reference/interfaces/)
- `@autoRoute` caveat: path parameters "must also be marked with the `@segment` decorator"; both `@route` and `@autoRoute` applied to an interface are "not 'portable'" to interfaces that extend it. — [TypeSpec resource routing](https://typespec.io/docs/libraries/rest/resource-routing/)
- ARM library: `@armResourceOperations` "is used to identify interfaces containing resource operations" and by default applies `@autoRoute` and a `@tag`; lifecycle decorators `@armResourceRead`, `@armResourceCreateOrUpdate`, `@armResourceUpdate` (PATCH), `@armResourceDelete`, `@armResourceList`, `@armResourceAction`; placement decorators `@resourceGroupResource` (default), `@subscriptionResource`, `@tenantResource`, `@extensionResource`, `@singleton`; `@armProviderNamespace` defaults to the namespace name. Lint rules enforce the shape: `arm-resource-interface-requires-decorator`, `use-interface`, `list-response-envelope` ("ARM collection GET response models must declare only the `value` and `nextLink` properties"), `no-resource-delete-operation`, `beyond-nesting-levels` (tracked resources at most 3 nesting levels), `arm-resource-provisioning-state`, `missing-operations-endpoint`. — [typespec-azure-resource-manager README](https://github.com/Azure/typespec-azure/blob/main/packages/typespec-azure-resource-manager/README.md)
- Microsoft's stated value: TypeSpec can "encapsulate common data types, API patterns, and API guidelines into high level, reusable components"; "Many Azure services within Microsoft have already adopted TypeSpec, and the number is growing daily" (no number given). — [typespec.io introducing](https://typespec.io/blog/introducing/)
- bterlson (TypeSpec lead) on HN: the team first tried a TypeScript DSL "but it didn't fit their Azure REST use cases"; TypeSpec needs HTTP metadata (verbs, params, routes) and pagination patterns TypeScript lacks; the design targets complex REST APIs in Azure. — [HN 41601728](https://news.ycombinator.com/item?id=41601728), [HN 39833321](https://news.ycombinator.com/item?id=39833321)
- Sceptical sentiment: angra_mainyu "It seems typespec deals only with extremely simple CRUD APIs"; danhudlow: the example with "zero semantic documentation" doesn't inspire confidence that it helps "author API definitions that are actually good"; vaylian "TypeSpec cares most about the methods/endpoints"; schnable asks about async/event-driven APIs (unanswered). — [HN 40206124](https://news.ycombinator.com/item?id=40206124)
- Positive sentiment: dajonker "It's so much better than writing OpenAPI by hand"; Petermarcu highlights reusable API patterns; lknuth uses TypeSpec PRs to agree contracts with mobile developers. — [HN 39833321](https://news.ycombinator.com/item?id=39833321), [HN 41601728](https://news.ycombinator.com/item?id=41601728)

### Inferences
- TypeSpec's approach (library templates + linter) shows resources can be a *library* feature on top of generic interfaces/decorators, but ARM needed ~10 lint rules to keep that library-level model consistent; a language-level construct can enforce the same invariants once.
- Interface templates parameterised on the resource model give the "generated-SDK benefit" (every resource gets identical get/list/create/update/delete signatures) without the IDL knowing about resources; the cost is that cross-cutting checks (nesting depth, mandatory delete, list envelope) must be re-implemented as linters.

### Gaps
- No published metric (lines of spec, SDK consistency scores) for the ARM TypeSpec migration was found; the "Migrate ARM spec" and "Tracked Resource" sample pages returned only navigation when fetched.
- `gh search issues --repo microsoft/typespec "ResourceOperations OR autoRoute OR parentResource"` returned no results through the search API; friction evidence for TypeSpec resources is from HN only.

## A3. Google AIPs and resource encoding in protobuf

### Takeaway
Google encodes resources in protobuf with no language construct: `google.api.resource` options on messages, `google.api.resource_reference` on string fields, naming conventions for standard methods, and a 342-rule linter that enforces the conventions. The resource "construct" is therefore the AIP document plus the linter, and most of the linter's weight is spent re-checking shapes that a first-class construct would guarantee.

### Cited Findings
- AIP-121: "A resource-oriented API should generally be modeled as a resource hierarchy"; "A resource must support at minimum Get"; "A resource must also support List, except for singleton resources"; APIs "should prefer standard methods over custom methods"; the resource schema "across all methods must be the same"; relationships "must be representable via a directed acyclic graph"; an API identical to the database schema "is actually an anti-pattern". — [AIP-121](https://google.aip.dev/121)
- AIP-123: "APIs should annotate the resource types for each resource in the API using the `google.api.resource` annotation" with `type` (`{Service Name}/{Type}`), `pattern` (`projects/{project}/topics/{topic}`), `singular`, `plural`; patterns must be mutually unique once ID segments are removed, and new patterns go at the end because reordering "breaks client library compatibility". Rationale: "a number of consumers benefit from the `{Type}` and `message` names matching". — [AIP-123](https://google.aip.dev/123)
- AIP-131 Get: RPC name `Get` + singular resource name, request named `<RPC>Request`, response is the resource itself ("there is no GetBookResponse"); `google.api.resource_reference` on the `name` field, `*` for arbitrary resources. — [AIP-131](https://google.aip.dev/131), [AIP-4231](https://google.aip.dev/client-libraries/4231)
- AIP-134 Update: "The request message must contain a field for the resource"; `update_mask` "must be of type google.protobuf.FieldMask, and it must be called update_mask"; "Google APIs generally use the PATCH HTTP verb only, and do not support PUT requests"; `allow_missing` for create-or-update; etag "must succeed if and only if the provided etag matches the server-computed value"; rationale: with PUT, adding a field later can silently erase data old clients never sent. — [AIP-134](https://google.aip.dev/134)
- api-linter core catalog: 342 rules across 40 AIPs; AIP-123 (resource annotation) 17 rules; AIP-131..135 (standard methods) 14/17/20/16/15 rules, mostly `http-body`, `http-method`, `http-uri-name`, `request-message-name`, `request-name-field`, `request-name-reference`, `response-message-name`, `request-unknown-fields`; AIP-162 (revisions) 36 rules. Approximate classification: request/response message shape ~80, HTTP binding ~63, naming ~40, field behavior ~30, resource annotations ~25, documentation ~9. — [api-linter core rules](https://linter.aip.dev/rules/core/)
- The linter "provides real-time checks for compliance with many of Google's API standards"; installed with `go install github.com/googleapis/api-linter/v2/cmd/api-linter@latest`; rules enabled/disabled via config file or `--enable-rule`/`--disable-rule`, and comment-level disables exist (`--ignore-comment-disables`). — [linter.aip.dev](https://linter.aip.dev/)

### Inferences
- Roughly half of Google's linter exists to verify by convention what Smithy's `resource` block or TypeSpec's `Resource*` templates guarantee by construction (request naming, `name` field present and required, response type equals resource). A first-class construct converts most of those rules into structural facts.
- The `pattern`/`singular`/`plural` fields in `google.api.resource` are the data client-library generators need to synthesise resource-name helpers; an IDL resource construct should carry the same (path pattern, singular/plural names) or generators will invent them.

### Gaps
- `google/api/resource.proto` field-level docs (`name_field`, `child_type`, `history`) were not fetched; AIP-123 page did not mention them.

## A4. Inferring resource bindings from names/types vs annotations: pitfalls

### Takeaway
Three live systems show the spectrum: Smithy infers identifier/property bindings by member name (with explicit overrides); dikhan's terraform-provider-openapi infers Terraform resources purely from path conventions (`POST /things`, `GET /things/{id}`) with no annotations; Speakeasy abandoned pure inference and requires `x-speakeasy-entity`/`x-speakeasy-entity-operation` annotations while inferring only property-level attributes (Required/Optional/Computed) from request/response presence. Inference failures surface as confusing validation errors (Smithy) or silently wrong providers (convention-based), so the common practice is: infer the cheap, unambiguous part (which fields are computed) and annotate the ambiguous part (which operation plays which role).

### Cited Findings
- Smithy name-based identifier/property binding and warnings-not-errors on automatic list-element resolution: see A1. The `@resourceIdentifier` explicit binding "is used when the member name differs from the identifier name" and takes precedence over implicit. — [Smithy spec](https://smithy.io/2.0/spec/service-types.html)
- Smithy issue #2294: inference failed under `@nestedProperties` + elision; users fixed it by making the binding explicit with `@resourceIdentifier`; maintainers acknowledged the error messages for elided identifiers are "a bit unclear". — [smithy-lang/smithy#2294](https://github.com/smithy-lang/smithy/issues/2294)
- dikhan terraform-provider-openapi (convention-based): "A resource to be considered terraform compliant must meet the following criteria" including at least a POST and a GET; PUT and DELETE optional; the POST request-body schema defines the resource's fields; "Resource names should be plural as per Google API Resource name Guidelines"; versioned paths mean "terraform will treat each resource version as it was a different resource"; data sources initially only for root-level GET paths (issue #154). — [dikhan how_to.md](https://github.com/dikhan/terraform-provider-openapi/blob/master/docs/how_to.md), [dikhan#154](https://github.com/dikhan/terraform-provider-openapi/issues/154)
- Speakeasy (annotation-based): `x-speakeasy-entity` marks the schema; `x-speakeasy-entity-operation: Pet#create` etc. maps endpoints to roles; without `#update` "any attribute change requires resource replacement (ForceNew)"; "Every parameter essential for READ, UPDATE, or DELETE operations must either be part of the CREATE API response body or be consistently required in the CREATE API request"; placement of the entity annotation changes flattening ("properties above the annotation are flattened, which could cause conflicts"). Type-level inference remains: required in CREATE body -> `Required: true`, else `Optional: true`; present in response but absent from CREATE request -> `Computed: true`. — [Speakeasy entity mapping](https://speakeasy.com/docs/terraform/entity-mapping), [Speakeasy create-terraform](https://www.speakeasy.com/docs/create-terraform)
- Smithy's CloudFormation generator infers per-property mutability from which lifecycle operation carries the member and lets `@cfnMutability` override. — [Smithy aws.cloudformation](https://smithy.io/2.0/aws/aws-cloudformation.html)

### Inferences
- The pitfalls of inference are: (1) ambiguity when names collide or the resource shape is nested (Smithy #2294); (2) silent misclassification when conventions aren't followed (convention-based providers require plural paths and specific verbs); (3) error messages that describe the inferred binding rather than the user's intent. Every system that scaled added explicit overrides.
- The one inference everyone keeps is "a field in the response but not the create request is computed/read-only"; that is derivable from lifecycle operation shapes and is what both Speakeasy and Smithy-CFN do.

### Gaps
- No academic or blog write-up comparing annotation vs inference error rates was found; the evidence is from docs and issues.

## A5. What infrastructure generators need from a resource model

### Takeaway
Terraform, Pulumi, CloudFormation and Crossplane converge on the same required facts: a primary identifier (and optionally additional identifiers), per-property classification into input-required / input-optional / computed (read-only) / write-only (secrets), which properties force replacement vs in-place update, import/lookup inputs, references to other resources, and which lifecycle handlers exist (no update handler means replace). CloudFormation's registry schema is the most explicit enumeration of this list.

### Cited Findings
- CloudFormation resource type schema: `primaryIdentifier` (required; "non-zero-length list of JSON pointers to properties that form a single key"), `additionalIdentifiers`, `createOnlyProperties` ("can be specified by the user only during resource creation"), `readOnlyProperties` ("can be returned by a `read` or `list` request, but can't be set by the user"), `writeOnlyProperties` ("often used to contain passwords, secrets"), `conditionalCreateOnlyProperties`, `deprecatedProperties`, `replacementStrategy` (`create_then_delete` | `delete_then_create`), `tagging`, and `handlers` for create/read/update/delete/list each with `permissions` and `timeoutInMinutes`; "If the resource type doesn't contain an `update` handler, CloudFormation can't update the resource ... and will instead replace it"; "The `list` handler must at least return the resource's primary identifier." Nested properties must go in `definitions` via `$ref`. — [CloudFormation resource type schema](https://docs.aws.amazon.com/cloudformation-cli/latest/userguide/resource-type-schema.html)
- Terraform Plugin Framework: attributes carry Required/Optional/Computed, validators and (resources only) plan modifiers; built-in plan modifiers `RequiresReplace()` ("If the value of the attribute changes, in-place update is not possible and instead the resource should be replaced"), `RequiresReplaceIf()`, `RequiresReplaceIfConfigured()`, `UseStateForUnknown()` ("Copies the prior state value, if not null") to reduce "(known after apply)"; "the framework marks computed attributes that are null in the configuration as unknown in the plan"; apply fails with "Provider produced inconsistent result" if planned and final values differ. — [Terraform plan modification](https://developer.hashicorp.com/terraform/plugin/framework/resources/plan-modification), [Terraform attributes](https://developer.hashicorp.com/terraform/plugin/framework/handling-data/attributes)
- Terraform import: "Resources can implement the ImportState method, which must either specify enough Terraform state for the Read method to refresh resource.Resource or return an error"; single-ID resources use `ImportStatePassthroughID`; multi-attribute IDs need custom parsing (comma-joined by convention). — [Terraform import](https://developer.hashicorp.com/terraform/plugin/framework/v1.15.x/resources/import)
- Pulumi schema: `inputProperties`, `requiredInputs`, `properties`/`required` ("must be set for inputs and will always be set for outputs"), `stateInputs` (lookup inputs for import; "if this is unset, only an ID is necessary"), `listInputs`, `aliases` (rename without delete/create), `deprecationMessage`, `isComponent`, `methods`; property-level `replaceOnChanges` and `willReplaceOnChanges`; cross-package `$ref` to `/provider/vX.Y.Z/schema.json#/resources/...`. — [Pulumi package schema](https://www.pulumi.com/docs/iac/packages-and-automation/pulumi-packages/schema/)
- Crossplane managed resources: `spec.forProvider` is "the 'source of truth' for external resources"; late initialization fills empty optional fields from the provider; `initProvider` for create-only settings; `crossplane.io/external-name` annotation is "The name of the managed resource inside the Provider"; management policies `Create`, `Delete`, `Observe`, `Update`, `LateInitialize`; references by `xxxRef`, `xxxSelector` or `matchControllerRef`; "Crossplane never deletes a resource based on a `forProvider` change". — [Crossplane managed resources](https://docs.crossplane.io/latest/managed-resources/managed-resources/)
- Smithy's generator derives CloudFormation mutability from lifecycle operations (A1) and `@cfnAdditionalIdentifier` for ARN/alias lookups; `additionalSchemas` lets a generator add properties that aren't in any lifecycle operation. — [Smithy aws.cloudformation](https://smithy.io/2.0/aws/aws-cloudformation.html)

### Inferences
- The minimal resource IR for infra generators: identifier tuple (+ additional identifiers), per-property mutability class (create-only, read-only, write-only, full, conditional), replacement strategy, presence of each lifecycle op (missing update => replace), lookup/import inputs, references (typed links to other resources), deprecation and defaults. Everything else (timeouts, permissions, tagging) is provider-specific and belongs in annotations.
- Mutability can be *derived* from lifecycle operation shapes (as Smithy-CFN and Speakeasy do) with an override trait; the IR should expose the derived classification so each generator does not recompute it.

### Gaps
- CDK construct requirements were not fetched directly; CDK L1 constructs are generated from the CloudFormation registry schema, so the CFN list stands in for CDK. No source confirming that mapping was captured in this session.

## B1. How IDLs let projects attach typed metadata, and how it is consumed

### Takeaway
Five designs: Smithy traits are shapes in the model (declarative, selector-scoped, with `conflicts`, `structurallyExclusive`, `breakingChanges`, validated like any value); protobuf custom options are extensions of descriptor option messages with runtime/source retention; OpenAPI `x-` extensions are untyped JSON that "may or may not be supported by the available tooling"; TypeSpec decorators are JS functions with an optional typed `extern dec` signature and a new no-code `auto dec` form; GraphQL directives are declared in SDL with typed input arguments and explicit locations. The trend in both TypeSpec (auto decorators) and Buf (custom lint plugins reading options) is toward declaring metadata in the IDL and consuming it through a typed accessor, while keeping an escape hatch to general-purpose code for validation.

### Cited Findings
- Smithy: "Traits are defined by applying smithy.api#trait to a shape"; `@trait` properties: `selector` ("A valid selector that defines where the trait can be applied", default `*`), `conflicts` (traits that cannot coexist), `structurallyExclusive` ("member" => "only a single member of a structure can be marked with the trait"), `breakingChanges` ("Defines the backward compatibility rules of the trait" with `change`, `path`, `severity`, `message`). "The value provided for a trait MUST be compatible with the shape of the trait"; "A structure trait with no members is called an annotation trait"; "A member can be safely added to an annotation trait if the member is not marked as required"; "Members and references within a model MUST NOT target trait shapes." — [Smithy model spec](https://smithy.io/2.0/spec/model.html)
- Smithy custom-trait tooling: `smithy-trait-codegen` is a build plugin that "generates Java code implementations of traits from a Smithy model"; integrations discovered via Java service loader. — [smithy traitcodegen javadoc](https://smithy.io/javadoc/1.54.0/software/amazon/smithy/traitcodegen/package-summary.html)
- Smithy on HN: mtdowling describes traits as "a self-describing way to add more information to models"; phjordon: "Smithy is designed to be auth agnostic so new auth traits can be added by anyone." — [HN 27081084](https://news.ycombinator.com/item?id=27081084)
- Protobuf: "Protobuf also allows you to define and use your own options. Note that this is an advanced feature which most people don't need"; "creating custom options uses extensions, which are permitted only for custom options in proto3"; declared as `extend google.protobuf.MessageOptions { ... = 50000; }`; "Options have runtime retention by default ... visible at runtime in the generated descriptor pool"; `retention = RETENTION_SOURCE` keeps them out of the runtime pool but "still visible to `protoc` and `protoc` plugins"; read via descriptor reflection (`options().GetExtension(string_name)`). — [protobuf.dev proto3 guide](https://protobuf.dev/programming-guides/proto3/)
- OpenAPI 3.1 §4.9: "The field name MUST begin with `x-`"; "The value can be `null`, a primitive, an array or an object"; "The extensions may or may not be supported by the available tooling"; "Field names beginning `x-oai-` and `x-oas-` are reserved". — [OAS 3.1.0](https://spec.openapis.org/oas/v3.1.0.html)
- TypeSpec: a decorator has an optional TypeSpec signature (`extern dec logType(target: unknown, name: string);`, target unions restrict where it applies) and a JS implementation `$logType(context, target, name)` that stores data in `context.program.stateMap(key)`; "Do not save the data in a global variable"; validation via `reportDiagnostic`, `onTargetFinish` (conflicts between decorators on one type) and `onGraphFinish` (cross-type checks). New `auto dec label(target: Model, value: valueof string);` means "the compiler auto-generates the storage logic", read back with `getAutoDecoratorValue(program, "MyLib.label", type)` or generated typed accessors (`tspd gen-extern-signature`); `auto` and `extern` are mutually exclusive. — [TypeSpec create decorators](https://typespec.io/docs/extending-typespec/create-decorators/)
- TypeSpec limits: "Aliases cannot be decorated, as they do not create new Types, nor can any type expressions such as unions that use the | syntax or anonymous models". — [TypeSpec decorators](https://typespec.io/docs/language-basics/decorators/)
- GraphQL: `directive @name(args) repeatable? on LOCATIONS`; type-system locations SCHEMA, SCALAR, OBJECT, FIELD_DEFINITION, ARGUMENT_DEFINITION, INTERFACE, UNION, ENUM, ENUM_VALUE, INPUT_OBJECT, INPUT_FIELD_DEFINITION; arguments must be input types; "Directives are the preferred way to extend GraphQL with custom or experimental behavior"; recommends prefixing custom names (e.g. `@fb_auth`); directive order "may be significant". — [GraphQL spec Oct 2021 §3.13](https://spec.graphql.org/October2021/#sec-Type-System.Directives)
- Buf custom lint/breaking plugins (2024-09-18): rules are binaries implementing the Bufplugin API, authored with bufplugin-go over protoreflect, configured like built-in rules; example `FIELD_OPTION_SAFE_FOR_ML` checks a custom field option; "Bufplugin is coming to the BSR" for org-wide distribution; Buf migrated all 100+ built-in rules to the same framework "transparently to all of our users". — [Buf custom plugins blog](https://buf.build/blog/buf-custom-lint-breaking-change-plugins)
- Spectral custom functions (OpenAPI linting): JavaScript default exports in a `functions/` folder, `(input, options, context)` signature, options validated via JSON Schema with `createRulesetFunction`; "the code isn't executed in a sandbox environment"; functions "may run hundreds of thousands of times on large documents". — [Spectral custom functions](https://github.com/stoplightio/spectral/blob/develop/docs/guides/5-custom-functions.md)

### Inferences
- Smithy's declarative traits are the only design where the IDL itself can validate (a) where the annotation may appear (selector), (b) its value type, (c) mutual exclusion, and (d) what counts as a breaking change to the annotation's value. Every other system pushes at least one of those into tool code.
- TypeSpec adding `auto dec` is an admission that most custom decorators are pure metadata and should not need JavaScript; the escape hatch remains for computed/validating decorators.
- Consumption pattern worth copying: protobuf's retention flag (source vs runtime) and Smithy's selector-scoped validators mean a server runtime can be handed only the metadata it needs.

### Gaps
- No dedicated Smithy blog post announcing `smithy-trait-codegen` was found; only javadoc.
- No direct source describing how Smithy Java tooling accesses traits at runtime was fetched (the model-spec page was truncated at the Java section).

## C1. Table-stakes tooling for a schema language

### Takeaway
Across Buf, TypeSpec, Smithy and GraphQL the consistent minimum is: a language server (diagnostics, completion, go-to-definition, rename), a formatter, a linter with configurable rules, a breaking-change checker usable in CI against a git ref, a docs/preview generator, and a browser playground. Buf's 2026 LSP launch and TypeSpec's VS Code extension show LSP is now expected rather than optional; HN commenters explicitly asked about Smithy's missing click-to-definition in 2024.

### Cited Findings
- Buf CLI v1 (2022-02-23): the goal was "a kind of 'one-stop shop' for Protobuf development"; `buf lint` checks sources "comply with chosen best practices"; `buf breaking` performs "breaking change detection between any two Protobuf inputs" such as git branches; `buf generate` replaces "one of the rougher edges in Protobuf-based API development"; dependency management replaces vendoring; BSR for versioned modules, plugins, remote generation and docs; "Our policy is to never make breaking changes within a version of the CLI." — [Buf CLI v1 blog](https://buf.build/blog/buf-cli-v1)
- Buf Protobuf LSP (2026-01-14): "Before today, Protobuf lacked the same LSP support other major programming languages enjoy"; provides go-to-definition, completion, find references, precise diagnostics (flags a duplicate `repeated` that protoc does not); "the CLI bundles the LSP server" (`buf lsp serve`); VS Code extension installs the CLI if needed; Neovim uses the CLI directly. — [Buf LSP blog](https://buf.build/blog/protobuf-lsp)
- HN on the Buf LSP (Aug 2026, 173 points / 158 comments): deepsun says editors invest less in native integration once an LSP exists; sudorandom notes Buf's LSP is spec-complete unlike projects built on a parser that "readily accepts broken Protobuf"; bheadmaster says Buf removed "writing arcane flags into scripts nobody wants to touch" and accepts the paid cloud offering as long as "Buf CLI and the related toolchain remains free software"; bufbuild replied "the Buf CLI will always be free and OSS." — [HN 49322573](https://news.ycombinator.com/item?id=49322573)
- Breaking-change nuance from the same thread: ventana notes "it's forbidden to move a field into or out of a `oneof`" (wire-compatible but breaks generated Go); eterm: breaking changes matter even in controlled codebases because requests straddle upgrade boundaries. — [HN 49322573](https://news.ycombinator.com/item?id=49322573)
- TypeSpec VS Code extension: IntelliSense, syntax highlighting, autocompletion, formatting, live diagnostics, quick fixes, rename and go-to-definition; commands "TypeSpec: Create TypeSpec Project", "TypeSpec: Generate From TypeSpec", "TypeSpec: Preview API Documentation"; importing from OpenAPI 3. — [TypeSpec VS Code](https://typespec.io/docs/introduction/editor/vscode/)
- TypeSpec playground praised: henry_pulver "Playground is great for getting a feel for it fast too." bterlson: the editor story is LSP plus a VS Code extension. — [HN 39833321](https://news.ycombinator.com/item?id=39833321)
- Smithy language server: completions and hover in Smithy files and `smithy-build.json`, "Diagnostics for Smithy validation events", jump to definition, find references, rename, formatting, automatic imports, document symbols, folding, inlay hints; distributed as pre-built zips ("self-contained"), Maven Central ("Java 21+ is required"), Coursier; VS Code extension "manages the smithy-language-server installation itself". — [smithy-language-server README](https://github.com/smithy-lang/smithy-language-server/blob/main/README.md)
- Smithy CLI (2023-04-27): commands `validate`, `build`, `diff`, `ast`, `select`, `clean`, `migrate`; motivation: the Gradle workflow "is overly complex for developers who aren't already familiar with these tools"; the CLI lets developers "build their models quicker and with a single command, without any knowledge of Java or Gradle". `smithy diff --old ... --new ...` reports e.g. `ChangedMemberTarget` as a backwards-compatibility error. — [AWS blog: Introducing the Smithy CLI](https://aws.amazon.com/blogs/developer/introducing-the-smithy-cli)
- GraphQL ecosystem: graphql.org recommends a CI pipeline ordered syntax validation -> linting -> breaking-change detection -> composition; "fail CI builds when breaking changes appear unless the pull request is explicitly marked for breaking change approval"; GraphQL Inspector classifies changes as BREAKING / DANGEROUS / NON_BREAKING; remove deprecated fields only after usage drops to zero (e.g. "zero requests in the past 30 days"). — [graphql.org schema review](https://graphql.org/learn/schema-review/), [GraphQL Inspector diff](https://the-guild.dev/graphql/inspector/docs/commands/diff)
- Smithy's 2021 HN thread already asked for IDE support and templating examples; mtdowling: "It's not really a fully finished project yet." — [HN 27081084](https://news.ycombinator.com/item?id=27081084)

### Inferences
- The order practitioners ask for things: lint/breaking in CI first (Buf's original product), then LSP (asked of Smithy in 2021 and 2024, delivered for Protobuf only in 2026), then playground/preview. A new language should ship LSP + formatter + diff from the same binary from day one; Buf's "bundles the LSP server" in the CLI is the model.
- A breaking-change checker needs language-specific knowledge beyond wire compatibility (oneof moves, generated-code breaks), so the IR must carry enough to reason about generated-code compatibility, not just wire compatibility.

## C2. Sentiment on compiler runtime dependencies (JVM, Node, native binary) and Rust tooling precedent

### Takeaway
Explicit complaints are moderate but consistent: "I don't want/need all of node to make this happen" (TypeSpec), the Smithy team itself calling its Gradle workflow "overly complex" and building a standalone CLI, and Buf/Google shipping single Go binaries. The Rust-tooling wave (Ruff, Biome, Oxc, SWC) was adopted on speed and drop-in compatibility with a near-zero migration path, with single-binary distribution through existing package managers (pip/npm/brew) as the enabler; the recurring cost is a smaller plugin/contributor pool.

### Cited Findings
- kkukshtel on TypeSpec: "I don't want/need all of node to make this happen." — [HN 40206124](https://news.ycombinator.com/item?id=40206124)
- Smithy team: the Gradle-based approach "is overly complex for developers who aren't already familiar with these tools"; the CLI works "without any knowledge of Java or Gradle"; CLI docs: "makes it easy to get started working with Smithy without setting up Java or using the Smithy Gradle Plugins." Release assets are per-platform zips (`smithy-cli-darwin-aarch64.zip`, `-linux-x86_64.zip`, `-windows-x64.zip`, 1.74.0) installed via Homebrew tap, Scoop or an `install` script. — [AWS blog](https://aws.amazon.com/blogs/developer/introducing-the-smithy-cli), [Smithy CLI guide](https://smithy.io/2.0/guides/smithy-cli/index.html), [Smithy CLI installation](https://smithy.io/2.0/guides/smithy-cli/cli_installation.html), [smithy releases via gh api, tag 1.74.0]
- Smithy on HN 2021: scrubs "I know JAVA from previous jobs, but not Gradle"; mtdowling (2024): "You don't have to use Gradle with Smithy." — [HN 27081084](https://news.ycombinator.com/item?id=27081084), [HN 40206124](https://news.ycombinator.com/item?id=40206124)
- Smithy-Java GA (2026-03) is built on Java 21 virtual threads, tying the runtime to a recent JVM. — [AWS What's New](https://aws.amazon.com/about-aws/whats-new/2026/03/smithy-java-client-framework)
- Buf: described as a single binary that reads `buf.yaml` and figures out what to do; protoc is "minimal, fast, but you wire everything else (linting, breaking checks, dependency management) yourself with plugins and shell scripts." — [Buf ecosystem docs](https://buf.build/docs/ecosystem/)
- Google api-linter: a Go binary installed with `go install ...@latest`. — [linter.aip.dev](https://linter.aip.dev/)
- Conjure: the compiler and each generator are JVM apps distributed as tgz with `bin/` launcher scripts and `lib/*.jar`; "Conjure generators may be distributed as a tgz containing a platform independent executable"; `gradle-conjure` is "the recommended way of interacting with the Conjure ecosystem". — [Conjure RFC002](https://github.com/palantir/conjure/blob/develop/docs/rfc/002-contract-for-conjure-generators.md), [Conjure README](https://github.com/palantir/conjure)
- Rust tooling thesis (leerob, 2021, updated 2026): "nearly every major JavaScript build tool now has a Rust-based alternative or has been rewritten in Rust"; SWC gave Next.js "~3x faster Fast Refresh and ~5x faster builds"; napi-rs publishes prebuilt native binaries to npm "without needing node-gyp or postinstall scripts"; caveats: Rust's learning curve, "Writing plugins in Rust isn't as approachable for many JavaScript developers", and WASM was 10-20x slower than native in Parcel's tests; developers would still rather have "a faster tool that's harder to contribute to". Oxlint is in production at Shopify, Airbnb and Mercedes-Benz; Ruff cited as the same pattern in Python. — [leerob.com/n/rust](https://leerob.com/n/rust)
- Ruff: "10-100x faster than existing linters (like Flake8) and formatters (like Black)"; ships as a standalone binary with no runtime dependencies; the PyPI wheel bundles the compiled binary; adoption includes FastAPI, Hugging Face, Pandas, Apache Airflow; Charlie Marsh's view is that the rewrite "isn't a silver bullet" and gains also come from caching and rethinking internals. — [ruff on PyPI](https://pypi.python.org/pypi/ruff), [pydevtools Ruff guide](https://pydevtools.com/handbook/explanation/ruff-complete-guide/), [JetBrains interview with Charlie Marsh](https://blog.jetbrains.com/pycharm/2023/02/ruff-python-linter-interview-with-charlie-marsh/)
- Biome adoption: sources conflict (one puts Biome at ~1.5M weekly npm downloads vs ESLint 50M+; another, May 2026, ~8.8M vs ~134M); migration via `npx biome migrate eslint --write`; "when a Rust tool reaches API parity with its JS predecessor and the migration path is < 1 hour, teams switch"; main obstacle is missing rules/plugins. — [reintech 2026 comparison](https://reintech.io/blog/eslint-vs-biome-javascript-linting-comparison-2026), [pkgpulse guide](https://www.pkgpulse.com/guides/why-developers-moving-to-rust-based-tools-2026)
- fbthrift (2014-02-20): Facebook rewrote the Thrift compiler and shipped a new C++ generator (`cpp2`) and async server because "Thrift was missing a core set of features" and teams kept rebuilding compression, auth and counters; measured "up to a 50% decrease in latency"; kept wire compatibility ("backward compatible with all the previous Thrift transports and protocols"). — [engineering.fb.com](https://engineering.fb.com/2014/02/20/open-source/under-the-hood-building-and-open-sourcing-fbthrift/)

### Inferences
- Both JVM-based IDLs (Smithy, Conjure) ended up wrapping the JVM in launcher scripts/zips to hide it; users still perceive a Java dependency (the Smithy install page never says whether a JRE is bundled). A native static binary removes an entire category of install questions and matches what Buf, protoc, api-linter already deliver.
- Rust tooling adoption formula from the sources: (1) order-of-magnitude speed, (2) output-compatible with the incumbent so migration is <1 hour, (3) distributed through the ecosystem's existing package manager as a prebuilt binary, (4) accept a thinner plugin ecosystem and compensate with a declarative config/rule layer. The last point directly favours IDL-declared metadata and selector-based lint rules over code plugins.

- No HN thread specifically criticising Smithy's JVM dependency was found (the 2021 thread barely mentions it); the Avro-tools JVM sentiment was not researched.
- Biome download figures conflict by ~6x between sources; treat as rough.

## C3. How lint/policy rule sets are structured and which rule types dominate

### Takeaway
Buf (opt-in strictness tiers MINIMAL < BASIC < STANDARD plus orthogonal COMMENTS/UNARY_RPC), Spectral (JSONPath `given` + function `then` + severity, extendable rulesets, JS custom functions), Smithy (metadata `validators` with selectors, `EmitEachSelector`/`EmitNoneSelector` needing no code, NOTE/WARNING/DANGER/ERROR with suppressions) and Google's api-linter (rules keyed to AIP numbers, core/client-libraries/cloud groups) all converge on: naming/casing, request/response shape conventions, documentation presence, package/file layout, and compatibility (breaking-change) checks, with per-rule severity and file/shape-level suppression.

### Cited Findings
- Buf lint: "Rules are grouped into categories so you can opt in to a strictness level rather than enabling rules one at a time"; `STANDARD` is the default. MINIMAL = package/directory layout (`PACKAGE_DIRECTORY_MATCH`, `PACKAGE_DEFINED`, `PACKAGE_NO_IMPORT_CYCLE`) because failures "usually cause real problems in downstream Protobuf tooling"; BASIC adds casing (`MESSAGE_PASCAL_CASE`, `FIELD_LOWER_SNAKE_CASE`, `ENUM_VALUE_UPPER_SNAKE_CASE`), enum hygiene (`ENUM_FIRST_VALUE_ZERO`), imports; STANDARD adds `SERVICE_SUFFIX`, `ENUM_VALUE_PREFIX`, `ENUM_ZERO_VALUE_SUFFIX`, `PACKAGE_VERSION_SUFFIX`, `RPC_REQUEST_STANDARD_NAME`, `RPC_RESPONSE_STANDARD_NAME`, `RPC_REQUEST_RESPONSE_UNIQUE`, `PROTOVALIDATE`; COMMENTS (leading comments on enum/field/message/oneof/rpc/service) and UNARY_RPC are independent; the linter "does not check specific file option values or custom options", leaving that to plugins. — [Buf lint rules](https://buf.build/docs/lint/rules/)
- Spectral: "Rulesets are collections of rules written in JSON, YAML, or JavaScript"; each rule has `description`, `message`, `severity`, `given` ("tells Spectral what part of the JSON or YAML file to target by using JSONPath"), `then` with `function`/`functionOptions`; `extends` reuses `spectral:oas`, `spectral:asyncapi`, `spectral:arazzo`. — [Spectral rulesets](https://github.com/stoplightio/spectral/blob/develop/docs/getting-started/3-rulesets.md)
- `spectral:oas` has 57 rules: schema validity 14, description presence 5 (`info-description`, `operation-description`, `tag-description`, parameter descriptions), naming/casing 2 (`operation-operationId`, `-valid-in-url`), operationId uniqueness 1, unused components 2, security 2, and 31 "other" (tags, servers, path hygiene such as `path-keys-no-trailing-slash`, `path-params`). — [Spectral OpenAPI rules](https://github.com/stoplightio/spectral/blob/develop/docs/reference/openapi-rules.md)
- Smithy validators: metadata `validators` entries have `name`, `id`, `message` (`{super}` injects the original), `severity`, `namespaces`, `selector`, `configuration`; `EmitEachSelector` "Emits a validation event for each shape that matches the given selector" with `bindToTrait` and `messageTemplate`; `EmitNoneSelector` fires when nothing matches (catch a missing constraint trait); rationale: enforce rules "without needing to write code". Severities: ERROR "cannot be suppressed" and cannot be emitted by user validators; DANGER "very likely wrong", unsuppressed DANGER makes the model invalid; WARNING; NOTE. Suppression via `@suppress([...])` on shapes or `suppressions` metadata with `id`, `namespace`, `reason`, matched hierarchically by dot segments. — [Smithy model validation](https://smithy.io/2.0/spec/model-validation.html)
- Smithy linter package (`smithy-linters`): `AbbreviationName`, `CamelCase`, `ReservedWords` (with selector and wildcard words), `StandardOperationVerb`, `RepeatedShapeName`, `InputOutputStructureReuse`, `MissingPaginatedTrait` (verbs that require/suggest pagination), `ShouldHaveUsedTimestamp`, `MissingSensitiveTrait` (term list), `NoninclusiveTerms`, `UnreferencedShape`, `MissingClientOptionalTrait`; default severities DANGER for most, WARNING for sensitive/noninclusive/repeated, NOTE for unreferenced. — [Smithy model linters guide](https://smithy.io/2.0/guides/model-linters.html)
- Google api-linter: rules grouped by AIP block; core and client-library rules enabled by default, cloud rules disabled; 342 core rules dominated by request/response shape (~80) and HTTP binding (~63), then naming (~40), field behavior (~30), resource annotations (~25), documentation (~9). — [api-linter rules index](https://linter.aip.dev/rules/), [core rules](https://linter.aip.dev/rules/core/)
- Smithy compatibility: `smithy diff` reports `ChangedMemberTarget` as an error; the "Evolving models" guide lists which edits are backward-compatible (adding operations) vs not (removing a resource or operation); traits can declare their own `breakingChanges` rules. — [AWS Smithy CLI blog](https://aws.amazon.com/blogs/developer/introducing-the-smithy-cli), [Smithy evolving models](https://smithy.io/2.0/guides/evolving-models.html), [Smithy model spec](https://smithy.io/2.0/spec/model.html)

### Inferences
- Most-used rule types across all four: (1) naming/casing and suffix/prefix conventions, (2) presence of docs/comments, (3) presence of required metadata (pagination, sensitive, constraints; Spectral's description rules; Smithy's `EmitNoneSelector`), (4) package/file layout, (5) compatibility. Google's catalog is skewed toward request/response shape because protobuf lacks a resource construct; Buf's is skewed toward layout and naming because that is all the proto file carries.
- A selector/JSONPath-style query language plus severity tiers and hierarchical suppression IDs is the shared design; strictness tiers (Buf) are the adoption-friendly packaging.

### Gaps
- No usage telemetry on which rules teams actually enable; "most used" is inferred from what each vendor ships by default.

## C4. Lessons from "we built our own IDL" stories (Conjure, Cadl->TypeSpec, Thrift->fbthrift)

### Takeaway
The consistent lessons: constraints are a feature (Conjure kept its deliberately small YAML type system and credits it for velocity); a build-tool-centric distribution (gradle-conjure, Smithy Gradle) eventually needs a standalone CLI; naming matters enough that Microsoft renamed Cadl->TypeSpec with a migration tool and deprecated aliases; and forks/rewrites (fbthrift) are justified by cross-cutting runtime features and performance, not syntax, while preserving wire compatibility.

### Cited Findings
- Conjure: "a simple but opinionated toolchain for defining APIs once and generating client/server interfaces in multiple languages"; "battle-tested across hundreds of repos"; type system limited to objects, enums, aliases, unions, `list/map/optional/set`, built-ins (`rid`, `safelong`, `datetime`, `bearertoken`, `uuid`, `any`), structured errors with name/namespace/code/args; external references are an "escape hatch ... not recommended for normal APIs"; compiler emits a JSON IR and each generator is a CLI conforming to RFC002 (`conjure-<lang> generate <input-json> <output-directory>`); `conjure-backcompat` (wire-compat checker) "not yet open-sourced". — [Conjure README](https://github.com/palantir/conjure), [Conjure concepts](https://github.com/palantir/conjure/blob/develop/docs/concepts.md), [RFC002](https://github.com/palantir/conjure/blob/develop/docs/rfc/002-contract-for-conjure-generators.md)
- Conjure launch post (search summary; the Medium page returned 403 twice): the team "first intended Conjure as a stepping stone toward gRPC" but "came to value the constraints it placed on API design, which produced focus and clarity"; "Its simplicity has become a driver of engineering velocity across teams and developers." — [Palantir blog (via search)](https://blog.palantir.com/introducing-conjure-palantirs-toolchain-for-http-json-apis-2175ec172d32)
- Cadl -> TypeSpec (2023-03-13 release): the change reflected the product "becoming more mature, stable and one step closer to release"; "the name TypeSpec aligns better with what the product does and its benefits"; packages moved `@cadl-lang` -> `@typespec`, `.cadl` -> `.tsp`, `cadl-project.yaml` -> `tspconfig.yaml`, old names kept as deprecated aliases plus a migration tool. — [TypeSpec Cadl migration notes](https://typespec.io/docs/release-notes/cadl-typespec-migration), [March 2023 release](https://typespec.io/release-notes/release-2023-03-13/)
- fbthrift: see C2; motivations were missing framework features, async performance and per-request features; `THeader` added per-request headers so "services can add features like compression or timeout changes without modifying core libraries"; "not all Apache Thrift changes are reflected in fbthrift". — [engineering.fb.com](https://engineering.fb.com/2014/02/20/open-source/under-the-hood-building-and-open-sourcing-fbthrift/)
- HN fatigue with new IDLs: 62951413 groups TypeSpec with "CORBA, Avro RPC, Thrift RPC, gRPC, now this"; paxys "do we really need another standard? Just use OpenAPI directly folks"; Alupis finds it hard "to justify yet another new DSL" until AsyncAPI support arrives; that70sshow asks "why should one use this if both thrift and protobuf solves 90% of the needs". — [HN 40206124](https://news.ycombinator.com/item?id=40206124), [HN 41601728](https://news.ycombinator.com/item?id=41601728)
- Spec-first justification practitioners give: mnahkies "APIs are forever, the choice of language/framework is an implementation detail"; Alupis: generating from code only works "if you are deploying a monorepo"; sroussey: code-first for prototyping, "then switch as soon as you have customers". — [HN 39833321](https://news.ycombinator.com/item?id=39833321), [HN 41601728](https://news.ycombinator.com/item?id=41601728)
- Smithy's own answer to "why another IDL": a lineage of internal tools "in use at Amazon since the early 2000s"; goals were a flexible meta-model, built-in validation, protocol-agnostic serialization and extensible codegen; required-ness treated as server-side validation so teams can "remove the required trait" later without breaking clients. — [HN 27081084](https://news.ycombinator.com/item?id=27081084)

### Inferences
- The recommendations that fall out: keep the core type system small and let metadata extend it; define a stable JSON IR and a generator CLI contract early (Conjure RFC002, Smithy JSON AST) so generators can be written in any language; ship a standalone CLI, not just a build-tool plugin; pick the final name before 1.0; publish breaking-change tooling (Conjure never open-sourced theirs, which is a gap users notice).
- Expect "yet another IDL" pushback; the credible counter in the threads is concrete generated-client quality and a migration path from OpenAPI (TypeSpec added an OpenAPI 3 importer in its VS Code extension).

### Gaps
- No explicit "regrets" post from Palantir, Microsoft or Meta was found; lessons are inferred from design docs, launch posts and release notes.
- Thrift->fbthrift coverage is from 2014; no later retrospective was located.
