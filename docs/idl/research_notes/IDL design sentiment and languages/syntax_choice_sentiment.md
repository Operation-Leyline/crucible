# Designer rationale and practitioner sentiment on surface-syntax choices in API modelling languages

Scope note: researched 2026-10-08. Primary sources (language specs, design docs, maintainer blog posts) were fetched directly where possible; secondary sources (tutorials, forum threads) are labelled as such. Where a claim is widely repeated but I could not find a primary statement, it is listed under Gaps rather than asserted.

## 1. Anonymous operation inputs/outputs vs named message types

### Takeaway
The two camps have converged on the same *observable* outcome, a dedicated, operation-named type per input and output, but arrived at it differently: protobuf/Google make the author write `FooRequest` by rule and justify it with independent evolvability; Smithy 2.0 and TypeSpec let the author write parameters inline and synthesize the named type by convention (`<Op>Input`/`<Op>Output` in Smithy; an unnamed "parameters model" in TypeSpec that emitters name). The explicit rationale for dedicated per-operation types is documented (protobuf 1-1-1, Smithy `@input`/`@output`); explicit rationale for *inline* syntax beyond "more succinct" was not found in the Smithy IDL spec.

### Cited Findings
- AIP-131 (Google API Improvement Proposals) prescribes "The request message must match the RPC name, with a `Request` suffix" (e.g. `GetBookRequest`), and that "The request message must not contain any other required fields, and should not contain other optional fields except those described in another AIP." The page itself states no rationale for one request message per RPC. — [AIP-131](https://google.aip.dev/131)
- Protobuf's official "1-1-1" best practice says "The top-level request and response protos are unique to each service+method", while shared domain types (e.g. a student or name message) can be reused, so that shared types can be updated without touching every top-level message; it also argues even simple identifiers are worth wrapping in a message because that "gives the type semantics and consolidates documentation." — [protobuf.dev 1-1-1 Best Practice](https://protobuf.dev/best-practices/1-1-1/)
- Protobuf's "API Best Practices" page contains a section titled "Don't Include Primitive Types in a Top-level Request or Response Proto" alongside guidance on creating unique protos per method (existence confirmed via search results; the body could not be fetched, see Gaps). — [protobuf.dev API Best Practices](https://protobuf.dev/best-practices/api)
- Protobuf's "Proto Best Practices" (dos and don'ts) separately argues for distinct wire vs storage messages: "the needs of long-term storage and live RPC services tend to later diverge" and "Using separate types even if they are largely duplicative initially gives freedom to change your storage format"; it concedes "There is a cost in maintaining the translation layer, but it quickly pays off". — [protobuf.dev dos-donts](https://protobuf.dev/best-practices/dos-donts/)
- Secondary/community restatement of the rationale: a DEV Community post warns against reusing one message across methods because dedicated messages "allow you to modify request and response messages for a single service method without introducing accidental changes to other methods", with exceptions "usually made for a single well-defined entity or an empty message." — [dev.to, gRPC proto files best practices](https://dev.to/sonny_ad/grpc-proto-files-best-practices-2aab)
- Secondary: a JDriven tutorial argues that if a call returned a bare primitive, adding data later would require a new RPC or a V2, concluding "Protobuf has some very fancy ways to cope with extensibility on the field level, but if the request or response messages itself are wrong, that's bad." — [JDriven, Practical Protobuf 02](https://blog.jdriven.com/2020/04/Practical-Protobuf-02-First-Call)
- Smithy's `@input` trait "Specializes a structure for use only as the input of a single operation"; input structures "cannot serve as input for more than one operation, and should be named after the operation that targets them (for example, `GetSprocketInput`)". The stated rationale: the constraints "allow tooling to specialize operation input shapes" in ways that would otherwise require complex model transformations, and "Required members of a structure marked with the @input trait are implicitly considered clientOptional", so "It is backward compatible to remove the @required trait from top-level members." `@output` mirrors this. — [Smithy type-refinement traits](https://smithy.io/2.0/spec/type-refinement-traits.html)
- Smithy IDL 2.0 inline syntax (`input := { ... }`): "A structure defined using inline syntax is automatically marked with the input trait... for inputs and the output trait for outputs"; "the generated name is the name of the operation shape with the suffix `Input` added" (likewise `Output`), and the suffixes are configurable via the `$operationInputSuffix` / `$operationOutputSuffix` control statements. The spec's only stated purpose is that input and output "can be defined using a more succinct, inline syntax." — [Smithy IDL spec](https://smithy.io/2.0/spec/idl.html)
- TypeSpec: "The parameters of an operation represent a model"; the `parameters` meta-reference points to "the parameters model expression" (i.e. an unnamed model); models can be spread into parameters (`op feedDog(...CommonParams, name: string): void;`); signatures are reused with `op is`. The language-basics page does not say how emitters name the generated request type. — [TypeSpec operations](https://typespec.io/docs/language-basics/operations/)
- TypeSpec HTTP: "The set of parameters that are not marked @header, @query, or @path form the request body" (implicit body); `@body` makes a property "exactly the http request or response body". — [TypeSpec HTTP operations](https://typespec.io/docs/libraries/http/operations/)
- GraphQL: field arguments are named ("all arguments in GraphQL are passed by name specifically"); Input Object types exist because "you can't mix input and output types in your schema", they "can't have arguments on their fields", and they are "particularly valuable in the case of mutations, where you might want to pass in a whole object to be created." — [graphql.org, Schemas and Types](https://graphql.org/learn/schema/)
- Caleb Meredith (Apollo, 28 Mar 2017): "Mutations should only ever have one input argument", named `input`, a non-null unique input object. Reasons: "much easier to use client-side" (one variable per mutation), "when you have mutations that need 10+ arguments your mutation GraphQL file will become much smaller", and nesting leaves room to evolve/deprecate sections. Example naming `CreateTodoInput` / `CreateTodoPayload`; "If you want to pick a different naming convention that's fine, but stick to it!" — [Apollo blog, Designing GraphQL Mutations](https://www.apollographql.com/blog/designing-graphql-mutations)
- Practitioner debate example: a GitLab issue observed its GraphQL API had "two competing patterns for mutation arguments" (inline arguments vs input types) and noted input types "are reusable, which I think is perhaps the main advantage", asking whether to standardize. — [GitLab issue 34311](https://gitlab.com/gitlab-org/gitlab/-/issues/34311)
- Azure's TypeSpec linter rule `no-route-parameter-name-mismatch` exists because "a route/parameter name mismatch can produce awkward SDK operation signatures", and the rule page admits "a relatively high false-positive rate" (evidence that SDK generators are sensitive to parameter/route naming when inputs are inline). — [typespec-azure rule](https://azure.github.io/typespec-azure/docs/libraries/azure-core/rules/no-route-parameter-name-mismatch/)

### Inferences
- The "boilerplate `FooRequest`" complaint is addressed by Smithy 2.0 and TypeSpec through *syntax* (inline declaration) while preserving the *semantics* protobuf wants (a unique, operation-owned type). The design question is therefore not "named vs anonymous" but "who types the name": the author (protobuf/AIP), or the compiler by suffix convention (Smithy `Input`/`Output`, configurable).
- Smithy's `@input` trait is the clearest documented statement of *why* an input type should be owned by exactly one operation: it changes the backward-compatibility rules (required -> clientOptional) in a way that is only safe if no other operation shares the shape.
- GraphQL's ecosystem independently converged on the single-input-object convention (Relay/Apollo) for the same evolvability reason, despite the language natively supporting inline arguments.

### Gaps
- I could not fetch the body of protobuf.dev's "API Best Practices" page (404 under two URL variants; the search engine confirms the headings exist). Its exact wording on unique protos per method is unverified here.
- AIP-131 states the naming rule but no rationale; I did not find a Google AIP page that explicitly argues *why* request messages must not be shared. JJ Geewax's "API Design Patterns" (Manning, 2021) is widely cited for this but I could not access the chapter text; the search returned only retailer pages.
- No primary critique of `FooRequest` boilerplate from a language designer was found; the "boilerplate" framing appears in community posts only.
- TypeSpec docs do not state the naming convention emitters use for the anonymous parameters model; this is emitter-specific and not documented on the pages fetched.

## 2. Annotations/decorators vs keywords/modifiers

### Takeaway
TypeSpec and Smithy both state the same rationale for an open annotation system: extensibility of a small core without changing the language. Documented *complaints* are about argument typing (TypeSpec issue 2046: decorator args were limited to string/number/boolean with models misused as values) and emitter-side restrictions on argument kinds; the best available readability evidence (a 2024 survey of 332 Java developers) found no consensus that annotations hurt readability.

### Cited Findings
- TypeSpec docs: "Decorators form the core of TypeSpec's extensibility, providing the flexibility to describe a wide variety of APIs and associated metadata such as documentation, constraints, samples, and more." Decorators "must be placed before the entity they are decorating." Newer "auto decorators" (`auto dec label(target: Model, value: valueof string);`) store metadata with no JavaScript implementation. — [TypeSpec decorators](https://typespec.io/docs/language-basics/decorators/)
- TypeSpec issue #2046 (argument typing): "Currently we have a very limited set of types in TypeSpec that are used as values (String, Number, Boolean) as well as a misuse of other types (Model and Tuple) in order to fill that gap"; an OpenAPI `@info` decorator typed as a model meant "previous signature allows other types to be passed as well, for example a union which is in this case not at all what we want"; `valueof` was limited to string/numeric/boolean scalars; the issue proposes object/tuple literals and a clearer value/type split. — [microsoft/typespec#2046](https://github.com/microsoft/typespec/issues/2046)
- Azure TypeSpec Client Generator Core emits `unsupported-generic-decorator-arg-type` when a decorator argument's kind is unsupported, suggesting "strings, numbers, booleans, values, or enum members" (decorator args are a recurring tooling boundary). — [TCGC diagnostic](https://azure.github.io/typespec-azure/docs/libraries/typespec-client-generator-core/reference/diagnostics/unsupported-generic-decorator-arg-type/)
- Smithy: "Traits are used to extend a model and add capabilities that are not part of the core specification"; AWS's stated motivation was that "Existing IDLs available outside of AWS were not extensible enough to meet those needs"; "Smithy's extensible meta-model can evolve and capture more information about services without breaking changes"; extension is paired with "a built-in validation system that ensures models adhere to a configurable set of rules and policies"; "Traits MAY be used to influence how messages are serialized (for example, jsonName trait and xmlAttribute trait)." — [smithy.io overview](https://smithy.io/2.0/); [Smithy protocol traits](https://smithy.io/2.0/spec/protocol-traits.html)
- Empirical readability evidence (Java): Guerra et al. (arXiv 2404.17417, 2024) surveyed 332 developers with 15 snippet pairs; "Preferences were scattered for all categories of annotation usage, revealing no consensus among participants"; participants "often praised annotation impacts on design, maintainability, and productivity but expressed contrasting views on understandability and code clarity." — [arXiv 2404.17417](https://arxiv.org/abs/2404.17417)
- Historical complaint (Java, 2007): Ted Neward on the JSR 308 list warned that combining two or three annotation sets "could really quickly make 'annotation hell'" and that limiting where annotations can appear "will (I hope) reduce the potential for unreadable code." — [JSR308 list archive](https://types.cs.washington.edu/list-archives/jsr308/2007-February/000115.html)
- Historical analogue (Python, 2004): a Python-Dev thread proposed built-in keywords for static/class methods instead of decorators, reserving decorators for metadata. — [Python-Dev Aug 2004](https://www.python.org/pipermail/python-dev/2004-August/047498.html)

### Inferences
- Both TypeSpec and Smithy chose annotations primarily so that third parties (AWS teams, Azure, emitter authors) can add semantics without a language change; keywords would centralize every new concept in the compiler. Neither documents a comparison against keyword alternatives.
- The practical pain reported in TypeSpec is typing of decorator *arguments*, not discoverability; the fix direction (typed `valueof`, object literals) moves decorators closer to keyword-like static checking.
- Smithy's "trait + validator" pairing and TypeSpec's "auto decorator" both suggest designers consider annotations acceptable only when tooling can check their arguments.

### Gaps
- No TypeSpec design document or team blog post titled or framed as "why decorators (not keywords)" was found; the rationale is only implied by the docs quote above.
- No primary source complaining about decorator *discoverability* in TypeSpec or Smithy was found.
- Rust attributes and C# attributes: no rationale documents were retrieved within the call budget; not covered.

## 3. Constraint syntax: range literals, keyword forms, JSON-Schema keys, CEL

### Takeaway
Shipping schema languages mostly use keyword/decorator forms (`@range(min:, max:)`, `@length`, `minimum`/`maximum`) or boolean predicates (CUE bounds `>=1 & <=100`, Pkl `Int(this >= 1 && this <= 100)`/`isBetween`, protovalidate CEL). No evidence was found of an API IDL using bare `1..100` range literals for constraints, and no usability study comparing the forms was found. Buf's stated reason for moving from annotation-only (PGV) to CEL was maintainability and cross-language consistency, not readability.

### Cited Findings
- CUE expresses constraints as bounds with comparison operators (`>`, `<=`, `!=`) combined with `&`, e.g. `float425: 42.5 & #notNull & <100 & #floatOver5`, `#floatOver5: >5.0`; bounds work on numbers, strings, bytes and null; "It permits values where the comparison would return true". No rationale stated. — [CUE tour: bounds](https://cuelang.org/docs/tour/types/bounds/)
- Pkl type constraints: `name: String(length >= 3)`, `parent: String(this != name)`, `email: String(emailAddress)`, `Map<String(!isEmpty), String(emailAddress)>(length <= 5)`, and a predefined `Int(isBetween(0, 1023))`. Rationale: "Type constraints enable advanced runtime validation that goes beyond the capabilities of static type checking"; "Boolean expressions are convenient for ad-hoc type constraints"; lambdas allow "the abstraction and reuse of type constraints." — [Pkl language reference](https://pkl-lang.org/main/current/language-reference/index.html)
- Buf (Chris Roche, 24 Apr 2023) on why protovalidate adopted CEL: PGV's template-based generator "has fossilized in the face of feature requests and bug fixes"; per-language codegen differences "caused inconsistent rule support, even across official targets"; early design made it infeasible to add "custom error messages, arbitrary constraint expressions, shareable rules"; the new core "will be based on Common Expression Language ('CEL'), and will provide a much better foundation for validation going forward", enabling "user-defined expressions for complex field constraints and cross-field comparisons." — [Buf blog](https://buf.build/blog/protoc-gen-validate-v1-and-v2)
- Protovalidate keeps standard annotation-style rules (`min_len`, `max_len`, `email`, etc.) for common checks and reserves CEL for cross-field/custom logic; CEL expressions are "compiled once and evaluated consistently across languages"; custom error text lives in the rule. — [protovalidate docs](https://buf.build/docs/protovalidate); [How Protovalidate uses CEL](https://protovalidate.com/cel/how-cel-works/)
- In the Rust implementation CEL support is a feature flag so users of only standard rules get a lighter dependency footprint (evidence that CEL carries a cost some users opt out of). — [prost-protovalidate](https://docs.rs/prost-protovalidate)
- Community: a kmcd.dev post notes both frontend and backend logic "can be powered by the same declarative schema" (secondary, positive sentiment). — [kmcd.dev](https://kmcd.dev/posts/protovalidate/)
- Smithy 2.0 constraint traits are keyword-form (`@range(min:, max:)`, `@length(min:, max:)`); Smithy IDL spec and trait pages fetched above confirm the trait-based style (see §2 citations). — [Smithy IDL spec](https://smithy.io/2.0/spec/idl.html)

### Inferences
- Languages that are also *evaluation* languages (CUE, Pkl, CEL) express constraints as predicates because the predicate is already executable; pure IDLs (Smithy, TypeSpec, OpenAPI/JSON Schema) use closed keyword vocabularies because every target language must reimplement them.
- Buf's experience is the strongest evidence that a closed keyword vocabulary becomes a maintenance bottleneck across many codegen targets; its remedy (an expression language) trades readability of simple cases for extensibility of hard ones, which is why protovalidate kept the keyword shortcuts.
- Range-literal syntax (`1..100`) has precedent in general-purpose languages (Ada/Pascal subranges, Kotlin ranges) but I found no API IDL adopting it; this choice would be novel and unevidenced either way.

### Gaps
- No usability study or practitioner survey comparing `1..100` vs `length(min:, max:)` vs JSON-Schema keys vs CEL was found.
- No documented complaints about Smithy `@range`/`@length` or TypeSpec `@minValue`/`@maxLength` syntax were found.
- Pkl's `Int(this >= 1 && this <= 100)` exact example was not on the page; only `isBetween` and `String(length >= 3)` forms were confirmed.

## 4. Error declaration: `error` keyword vs annotated structure vs status-keyed responses; modelled vs generic envelopes

### Takeaway
All surveyed IDLs model errors as named types with an annotation (Smithy `@error("client"|"server")` + recommended `@httpError`, TypeSpec `@error` model, Fern `errors:` block with `status-code`); none use a dedicated `error` keyword. For the wire envelope, Zalando's widely-cited guidelines mandate RFC 9457 Problem JSON for every endpoint but *deliberately* reject resolvable `type` URIs and allow "custom problem types as extensions", i.e. a generic envelope with modelled extensions.

### Cited Findings
- Smithy `@error`: "Indicates that a structure shape represents an error"; value must be "client" or "server" (which party is at fault); every shape in an operation's errors list must carry it; "it is recommended to add an httpError trait to use an appropriate HTTP status code" (separate trait); "The message member of an error structure is special-cased" (without it generated code may lack an idiomatic message accessor). — [Smithy type-refinement traits](https://smithy.io/2.0/spec/type-refinement-traits.html)
- TypeSpec `@error`: "Specify that this model is an error type. Operations return error types when the operation has failed." The core page does not mention status codes or emitter treatment; `@errorsDoc` documents only the error members of a union return. Operations express failure via union returns, e.g. `op getDog(name: string): Dog | DogNotFound;`. — [TypeSpec built-in decorators](https://typespec.io/docs/standard-library/built-in-decorators/); [TypeSpec operations](https://typespec.io/docs/language-basics/operations/)
- Fern Definition: errors are declared in a top-level `errors:` block, each with a name (e.g. `UserNotFoundError`), a `status-code`, and an optional body `type`; "Errors represent failed (non-200) responses from endpoints." The page warns "Fern Definition isn't recommended for new customers" and Fern "isn't accepting feature requests for this format." — [Fern errors](https://buildwithfern.com/learn/api-definition/fern/errors)
- RFC 9457 (July 2023, obsoletes 7807): purpose is to carry "machine-readable details of errors in HTTP response content" so API designers don't invent a new format each time; media type `application/problem+json`; "Consumers MUST use the 'type' URI (after resolution, if necessary) as the problem type's primary identifier"; extension members (e.g. `balance`, `accounts` in its example) are permitted. — [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457)
- Zalando RESTful API Guidelines, rule #176 "MUST support problem JSON": "every endpoints must be capable of returning a Problem JSON on client usage errors" (4xx) and 5xx; "Clients must be robust and **not rely** on a Problem JSON object being returned"; "Problem `type` and `instance` identifiers in our APIs are not meant to be resolved" because "all important API parts must be documented in OpenAPI anyway" and "URLs are fragile and can drift out of sync over time"; relative identifiers like `/problems/out-of-stock` are proposed; "You may define custom problem types as extensions of the Problem JSON object". — [Zalando guidelines #176](https://opensource.zalando.com/restful-api-guidelines/#176)
- Inconsistency noted: Zalando's published Problem schema still says `type`, when dereferenced, "SHOULD provide human-readable documentation for the problem type", contrary to rule #176. — [Zalando problem schema.yaml](https://opensource.zalando.com/problem/schema.yaml)
- A CAMARA project proposal (Mar 2024) cites Zalando's non-resolvable `type` decision when considering URN-based problem types, showing the choice is being re-litigated by other API programs. — [CAMARA Issue 133 RFC 9457 URN option (PDF)](https://wiki.camaraproject.org/download/attachments/14778510/20240304-CAMARA-Issue%20133%20-%20RFC%209457%20URN%20Option.pdf?api=v2)
- Smithy `@examples` allows an `error` example whose `shapeId` "MUST be bound as an error to the operation this example trait is applied to" (errors are first-class enough to be exemplified and validated). — [Smithy documentation traits](https://smithy.io/2.0/spec/documentation-traits.html)

### Inferences
- The annotation-on-structure approach is universal among the surveyed IDLs because errors need the full structure vocabulary (members, constraints, docs) plus a small amount of extra metadata (fault party, status); a dedicated keyword would duplicate the structure grammar.
- Smithy's separation of `@error` (fault party, protocol-agnostic) from `@httpError` (status, protocol-specific) reflects its protocol-neutral stance; TypeSpec keeps `@error` protocol-neutral and lets the HTTP library derive status from `@statusCode` on the model (not verified on the page fetched).
- Sentiment on envelopes: the strongest practitioner guideline (Zalando) treats Problem JSON as the mandatory outer shape and modelled error data as extensions, i.e. "both", not "either".

### Gaps
- No source arguing *against* RFC 9457 in favour of fully bespoke modelled errors was found.
- OpenAPI's status-code-keyed `responses` map sentiment: no primary critique retrieved within budget.
- TypeSpec's HTTP-library rules for mapping `@error` models to status codes (`@statusCode`, default 4xx/5xx ranges) were not fetched; the core-decorator page is silent on status.

## 5. HTTP binding inference vs explicit per-member binding

### Takeaway
TypeSpec, FastAPI and Spring all infer path binding by name match with the route template; Smithy requires an explicit `@httpLabel` and validates that every label is bound and every labelled member is `@required`. Documented pitfalls of inference are: silent misclassification when names drift (TypeSpec appends unmatched `@path` params to the URL; Azure added a lint for cross-operation name mismatches with a high false-positive rate), route-order shadowing (FastAPI), and runtime dependence on compiler flags for parameter names (Spring 6.1 removed bytecode-based name recovery).

### Cited Findings
- TypeSpec: "Route path parameters are declared using `{}`"; "Providing `@path` on the model property with the matching name is optional" (so `@route("/pets/{petId}") op get(petId: string)` binds by name); "Path parameters are appended to the URL unless a substitution with that parameter name exists on the resource path"; unannotated parameters "form the request body". — [TypeSpec HTTP operations](https://typespec.io/docs/libraries/http/operations/)
- Azure TypeSpec lint `no-route-parameter-name-mismatch` flags operations that use different names for corresponding path parameters because the mismatch "can produce awkward SDK operation signatures"; the rule "has a relatively high false-positive rate". — [typespec-azure rule](https://azure.github.io/typespec-azure/docs/libraries/azure-core/rules/no-route-parameter-name-mismatch/)
- TypeSpec OpenAPI3 emitter rejects query strings inside `@route` (`path-query` diagnostic) and directs authors to `@query` or URI-template `{?filter}` syntax. — [TypeSpec openapi3 path-query](https://typespec.io/docs/emitters/openapi3/reference/diagnostics/path-query/)
- Smithy `httpLabel`: "any member of the structure with the `httpLabel` trait MUST have a corresponding URI label with the same name as the member"; each URI label needs a matching input member that is required and carries `httpLabel`; `httpLabel` applies only to `@required` members; members with no binding "are serialized in a protocol-specific document sent in the body of the message"; multiple greedy labels are reported as `DANGER` events. — [Smithy HTTP bindings](https://smithy.io/2.0/spec/http-bindings.html)
- FastAPI binds by name: "The value of the path parameter `item_id` will be passed to your function as the argument `item_id`." Pitfall: "Because path operations are evaluated in order, you need to make sure that the path for `/users/me` is declared before the one for `/users/{user_id}`... Otherwise, the path for `/users/{user_id}` would match also for `/users/me`, 'thinking' that it's receiving a parameter `user_id` with a value of 'me'." — [FastAPI path params](https://fastapi.tiangolo.com/tutorial/path-params/)
- Spring Framework 6.1 removed `LocalVariableTableParameterNameDiscoverer`; code depending on parameter names must compile with `-parameters` (Maven `<parameters>true</parameters>`, Gradle compiler arg, Kotlin `-java-parameters`). Spring Security's migration guide says this affects method-security SpEL references to argument names. — [Spring 6.1 release notes](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-6.1-Release-Notes); [Spring Security migration](https://docs.spring.io/spring-security/reference/6.4/migration/authorization.html)

### Inferences
- Smithy's explicit binding makes label/member mismatches a *model* error at build time; TypeSpec's inference turns the same mistake into a different-but-valid model (parameter appended to the path or demoted to body), which is why Azure needed a lint on top.
- Name-based inference couples the API's URL vocabulary to member names; renaming a member becomes a wire change. Explicit binding (`@httpLabel`, `@PathVariable("id")`) decouples the two at the cost of one annotation.
- Spring's 6.1 change is the clearest case of inference depending on an environmental detail (debug/parameter metadata) rather than on the model itself.

### Gaps
- The Spring release notes do not mention `@PathVariable` by name; the `-parameters` requirement is documented generally, and its application to `@PathVariable` without an explicit name is inferred from Spring's general parameter-name dependency.
- No TypeSpec GitHub issue was found documenting a user bitten specifically by a `{name}`/parameter mismatch; the Azure lint is the only direct evidence of the problem class.
- Fern's path-parameter syntax was not fetched.

## 6. Doc comments and link checking

### Takeaway
Smithy uses `///` (CommonMark), TypeSpec `/** */` with JSDoc-style tags (functionally equivalent to `@doc`), GraphQL `"""`/`"` descriptions (Markdown, exposed via introspection). Only rustdoc among the surveyed systems documents resolving cross-reference links against the symbol table and warning on breakage (`broken_intra_doc_links`, warn-by-default); neither Smithy's nor TypeSpec's documentation pages mention link resolution.

### Cited Findings
- Smithy: a documentation comment forms when three slashes are "the first non-whitespace characters on a line"; "Documentation comments are defined using CommonMark"; successive comments are joined with newlines; the comment must precede traits on the shape. The `@documentation` trait "Adds documentation to a shape or member using the CommonMark format"; member documentation falls back to the target shape's; a separate `@externalDocumentation` trait maps names to URLs. The pages do not mention link checking or cross-references. — [Smithy IDL spec](https://smithy.io/2.0/spec/idl.html); [Smithy documentation traits](https://smithy.io/2.0/spec/documentation-traits.html)
- TypeSpec: "Doc comments start with `/**` and continue until the closing `*/`"; they are "treated as if they were attached using the `@doc` decorator" and are the "less intrusive" preferred form; tags `@param`, `@returns`, `@template` (and unofficial `@example`); "TypeSpec Documentation support CommonMark markdown formatting"; emitters "may render it as-is, convert it, or strip it." The page does not describe link or cross-reference syntax. `@doc` accepts `formatArgs` for interpolation. — [TypeSpec documentation](https://typespec.io/docs/language-basics/documentation/); [TypeSpec built-in decorators](https://typespec.io/docs/standard-library/built-in-decorators/)
- GraphQL: "the GraphQL specification encourages you to do this in all cases unless the name of the type, field, or argument is self-descriptive. Schema descriptions are defined using Markdown syntax and can be multiline or single line"; descriptions "are available in introspection queries and visible in developer tools such as GraphiQL"; examples use `"""` block strings and `"` single-line strings. — [graphql.org, Schemas and Types](https://graphql.org/learn/schema/)
- Rust RFC 1946 motivation: existing relative/absolute Markdown links in doc comments are fragile across rendering depths and hosting, so "we propose extending Rustdoc to be able to generate relative links that work in all contexts." Syntax: `[Iterator](std::iter::Iterator)`, reference form, and implied shortcut `[std::iter::Iterator]`; namespace disambiguators (`struct@`, `fn@`, trailing `!`/`()`); paths resolve relative to the item's scope. The RFC left unresolved-path handling as an open question ("print a warning (or an error)"). — [RFC 1946](https://rust-lang.github.io/rfcs/1946-intra-rustdoc-links.html)
- Rustdoc today: `broken_intra_doc_links` "warns by default" and "detects when an intra-doc link fails to be resolved"; `private_intra_doc_links` warns by default when public docs link to private items. Caveats: links "containing `/` or `[]` characters will be ignored", cross-crate failures are silent, ambiguity warns and suggests a disambiguator. — [rustdoc lints](https://doc.rust-lang.org/rustdoc/lints.html); [rustdoc linking by name](https://doc.rust-lang.org/rustdoc/write-documentation/linking-to-items-by-name.html)
- Protobuf's dos-and-don'ts favours "a single top-level entry point... per file" because "This makes refactoring easier" (organizational, not doc-related, but relevant to how doc cross-references resolve). — [protobuf.dev dos-donts](https://protobuf.dev/best-practices/dos-donts/)

### Inferences
- Rustdoc is the only precedent found where documentation links are compiler-checked symbols; its history (RFC 2017 -> warn-by-default lint) shows the feature was motivated by link rot in rendered docs, which is the same failure Zalando cites for problem-type URLs (§4).
- Smithy and TypeSpec treat documentation as an opaque CommonMark string trait; any `[Name]` cross-reference checking would have to be added by a validator, and I found no evidence either project does so.

### Gaps
- I could not confirm from primary sources that Smithy does *not* validate links in documentation; the absence is inferred from the spec pages, which do not mention it.
- No practitioner sentiment on "documentation as first-class" in IDLs (surveys, blog posts) was retrieved.
- Fern and protobuf doc-comment conventions were not fetched.

## 7. Inline examples next to the operation

### Takeaway
Smithy (`@examples`, validated by `ExamplesTraitValidator`) and TypeSpec (`@example`/`@opExample` since 0.58, July 2024, with values that "MUST be assignable to the type") both keep examples in the model and type-check them. OpenAPI's examples are only "suggested" to match schemas, and practitioners report they rot; linters (42Crunch, Spectral) exist to catch drift. No source was found on practitioners *preferring* to keep examples outside the model.

### Cited Findings
- Smithy `@examples` (operation-only): "Provides example inputs and outputs for operations"; each example has required `title`, optional `documentation`, `input`/`output` documents keyed by top-level member, or `error` (an `ErrorExample` whose `shapeId` "MUST be bound as an error to the operation"); "both MUST NOT be defined for the same example"; `allowConstraintErrors` lowers input constraint validation to warnings and can only be set when `error` is provided. — [Smithy documentation traits](https://smithy.io/2.0/spec/documentation-traits.html)
- Smithy ships an `ExamplesTraitValidator` that "Validates that examples traits are valid for their operations." — [Smithy javadoc, validators package](https://smithy.io/javadoc/1.52.0/software/amazon/smithy/model/validation/validators/package-summary.html)
- TypeSpec `@example` / `@opExample` arrived in 0.58 (July 2024): "provide a way to specify some canonical examples for data types and operations. Each emitter is then able to serialize those examples in their own format." The example value "MUST be assignable to the type it is targeting"; scalar examples must use the scalar constructor so emitters render them "following the encoding of those scalar and the values set by @encode". — [TypeSpec 0.58 release notes](https://typespec.io/release-notes/typespec-0-58/); [TypeSpec examples](https://typespec.io/docs/standard-library/examples/)
- Practitioner caveat (Japanese blog, secondary): multiple `@example` decorators on one declaration resolve to the last one, while `@opExample` allows multiple; decorators cannot be applied to alias statements. — [zenn.dev post](https://zenn.dev/fairydevices/articles/1f9e9b26e4d248)
- OpenAPI: "the OpenAPI specification only suggests that examples should conform to their schemas. This means there's no inherent validation mechanism", so examples "tend to go stale like unchecked code comments" (secondary). — [Kitemetric blog](https://kitemetric.com/blogs/openapi-examples-the-unsung-heroes-and-hidden-pitfalls-of-api-documentation)
- 42Crunch's OpenAPI conformance tooling has a warning rule "Example is not consistent with the underlying schema" advising to "make sure that the example objects you define match the schemas of their associated values." — [42Crunch docs](https://docs.42crunch.com/latest/content/oasv3/oasconformance/bestpractices/v3-warning-example-schema-not-consistent.htm)

### Inferences
- Both modern IDLs chose to make examples *typed values* checked by the compiler, which is a direct response to the OpenAPI drift problem; this is design-level evidence that examples belong in the model only if the toolchain validates them.
- Smithy's `allowConstraintErrors` shows that error examples need an escape hatch from input validation (an example that *should* fail constraints), which a naive "examples must validate" rule would forbid.

### Gaps
- No survey or discussion of practitioners keeping examples outside the model (e.g. in test suites or docs repos) was found.
- Whether Spectral's built-in OAS ruleset validates examples against schemas was not confirmed.

## 8. Member reuse: spread, mixins, inheritance

### Takeaway
Smithy's mixin design doc explicitly rejects inheritance ("Inheritance isn't supported because of the problems it has with distributed systems"; "specializing structures can break clients") and makes mixins a compile-time copy with no runtime polymorphism. TypeSpec offers all three (`...` spread copies with no nominal relationship; `is` copies properties and decorators; `extends` creates an explicit relationship for languages with inheritance). Protobuf has no type inheritance at all; OpenAPI's `allOf`-as-inheritance is a documented source of code-generator disagreement.

### Cited Findings
- Smithy mixins design (smithy-lang/smithy `designs/mixins.md`): motivation "the same members often need to be duplicated across multiple related structures"; "This repetition is tedious and error-prone" and causes "drift between related shapes over time." Inheritance considered under "Add inheritance to Smithy" and rejected: "Inheritance isn't supported because of the problems it has with distributed systems"; "Emulating inheritance over the wire introduces backward compatibility concerns"; "it is not well-supported in every programming language"; "Clients of a service are not forced to update each time an update is made to a service. However, specializing structures can break clients." Mixins "do not introduce any kind of runtime polymorphism" and so "avoid the downsides of polymorphic subtyping." — [smithy-lang/smithy designs/mixins.md](https://github.com/smithy-lang/smithy/blob/main/designs/mixins.md)
- Smithy mixins spec: mixins are "an implementation detail of models and are only intended to reduce duplication in Smithy shape definitions"; they "do not provide any kind of runtime polymorphism"; copied members take the target shape's ID, which "allows members of a shape to be backward compatibly refactored and moved into a mixin"; removing a mixin is backward compatible if equivalent members are applied directly; mixins "cannot be targeted by members or used as operation input, output, or errors"; member ordering is depth-first with mixin members first; later mixins and local traits override earlier ones. — [Smithy mixins](https://smithy.io/2.0/spec/mixins.html)
- TypeSpec: "The spread operator (`...`) copies the members of a source model into a target model" and "doesn't create any nominal relationship between the source and target"; `extends` is for "when you want to create an explicit relationship between two models", e.g. generating class definitions in languages with inheritance; `is` copies properties and "also copies decorators as well" without a nominal relationship; for `extends Record<T>` the docs recommend `is Record<T>` instead. The page does not say `extends` maps to `allOf`. — [TypeSpec models](https://typespec.io/docs/language-basics/models/)
- TypeSpec operations: models can be spread into operation parameters (`op feedDog(...CommonParams, name: string)`), and `op is` reuses a whole signature. — [TypeSpec operations](https://typespec.io/docs/language-basics/operations/)
- Protobuf: "There is no type inheritance" and nesting "is strictly a tree, and never a graph" (Red Hat Data Grid guide summarizing protobuf semantics; secondary). — [Red Hat Data Grid docs](https://docs.redhat.com/en/documentation/red_hat_data_grid/6.2/html/infinispan_query_guide/about_protobuf_messages)
- Protobuf's own best practices: "Messages and enums are intended to be **atomic** with regards to reuse"; "You should not use another message's nested types as reusable vocabulary"; shared types are to be defined top-level. — [protobuf.dev dos-donts](https://protobuf.dev/best-practices/dos-donts/)
- Downstream effect: generated C++ message classes became `final`, so a project (SiLA) "cannot inherit from them anymore" and moved to composition (wrapper holding the generated type). — [SiLA C++ issue 32](https://gitlab.com/SiLA2/sila_cpp/-/issues/32)
- OpenAPI `allOf` as inheritance: the OpenAPI maintainers' position in issue 2500 is that `allOf` "is simply model composition and does not imply a hierarchy between the models", and that "the general approach is to add keywords to disambiguate validation constructs for code generation, rather than make assumptions about their meaning"; a generator had stopped treating single-`$ref` `allOf` as inheritance after a version change. — [OAI/OpenAPI-Specification#2500](https://github.com/OAI/OpenAPI-Specification/issues/2500)
- Generator disagreements: NSwag "can handle both types of property locations when generating client code, but it seems that the others only generate properties when they are in allOf"; a schema project hit a multiple-inheritance clash where a type "cannot both be a NetworkService and ExchangeLanNetworkServicePartial". — [NSwag#1136](https://github.com/RSuter/NSwag/issues/1136); [ix-api-schema#160](https://gitlab.com/ix-api/ix-api-schema/-/issues/160)
- GraphQL: input polymorphism is limited; the `@oneOf` input-object RFC was still opt-in/draft per Hot Chocolate docs. — [Hot Chocolate input object types](https://chillicream.com/docs/hotchocolate/defining-a-schema/input-object-types)

### Inferences
- Smithy's rejection rests on a wire-compatibility argument (old clients receiving new subtypes lose data), not a language-ergonomics one; TypeSpec sidesteps the argument by making `extends` explicit and leaving wire meaning to emitters.
- Compile-time copy semantics (Smithy mixins, TypeSpec spread) deliberately make reuse invisible on the wire and in generated types, which is why both specs stress that removing the reuse mechanism is backward compatible.
- The OpenAPI `allOf` experience is the main cautionary evidence against *implicit* inheritance: when a composition keyword is reinterpreted as inheritance by some generators, output diverges per tool.

### Gaps
- No official protobuf FAQ entry or maintainer statement explaining *why* messages have no inheritance was found; only third-party restatements and the "atomic reuse" guidance.
- No TypeSpec design discussion on why spread, `is` and `extends` all exist (vs one mechanism) was found.
- Fern's `extends` (Fern Definition) and its sentiment were not researched; Fern's own docs now steer new users to OpenAPI.
