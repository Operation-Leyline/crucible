# How Protobuf/gRPC, GraphQL SDL and OpenAPI/JSON Schema handle the core IDL design axes, and what their communities concluded

Scope note: three ecosystems × eight axes. Each axis below is one section. "Sentiment" is always attributed (author, venue, date). Primary sources (specs, protobuf.dev, aip.dev, Buf docs, GraphQL RFC tracker, OAI) are preferred; blog posts and HN comments are labelled as such. Research cut-off: 2026-10-08.

---

## 1. Nullability / presence / required

### Takeaway
All three ecosystems started with a different default and all three have been pulled toward the same place: *explicit presence, with "required" treated as an application-level validation concern rather than a wire-format one*. Protobuf is the clearest documented case (proto2 `required` → proto3 removes both `required` and presence → `optional` returns in 3.12/3.15 → Editions make `EXPLICIT` presence the default and the team publicly "regrets" implicit presence). GraphQL is nullable-by-default *because of error propagation*, not because of data semantics, and a working group has spent 2021–2026 trying to separate the two. OpenAPI 3.1 dropped its own `nullable` keyword in favour of JSON Schema `type: [..., "null"]`, and `required` remains a per-object array.

### Cited Findings

**Protobuf — the arc**

- proto2: "Singular fields (of all types) track presence explicitly in the generated API." proto3: "Without the `optional` label, proto3 APIs do not track presence for basic types" (numeric, string, bytes, enums); message fields and oneofs track presence regardless. Editions: presence is explicit "unless `features.field_presence` is set to `IMPLICIT`"; messages and oneofs cannot use implicit presence. — [protobuf.dev Field Presence](https://protobuf.dev/programming-guides/field_presence/)
- Presence tracking for proto3 scalars needed `--experimental_allow_proto3_optional` in protoc v3.12; "Presence tracking for proto3 messages is enabled by default since v3.15.0 release." The page recommends `optional` because it "provides a smoother path to editions, which uses explicit presence by default." — [protobuf.dev Field Presence](https://protobuf.dev/programming-guides/field_presence/)
- The protobuf repo's own implementation note says proto3 presence tracking "was added to proto3 in response to user feedback" and that wrapper types had previously been the only supported presence mechanism for proto3; it describes 3.12 as experimental and 3.15 as default. — [implementing_proto3_presence.md](https://github.com/protocolbuffers/protobuf/blob/f75fd051d68136ce366c464cea4f3074158cd141/docs/implementing_proto3_presence.md)
- proto2 language guide, heading "Required is Strongly Deprecated", warning box "Required Is Forever": "`required` must not be used for new fields"; reason 1: changing `required`→`optional` is nearly impossible safely because a stale reader treats messages lacking the field as incomplete and rejects/drops them; reason 2: an unrecognised enum value is treated as missing, so the required check fails. — [protobuf.dev proto2 guide](https://protobuf.dev/programming-guides/proto2/)
- Dos and Don'ts: "Never add a required field, instead add `// required` to document the API contract." "Required fields are considered harmful by so many they were removed from proto3 completely." "Make all fields optional or repeated." — [protobuf.dev Dos and Don'ts](https://protobuf.dev/best-practices/dos-donts/)
- Protobuf team design-decision page "Implicit Presence": "We do not recommend using implicit presence for new fields." Why proto3 adopted it: to enable open-struct APIs in languages without cheap optionality (Go, Java, Objective-C); the page says that premise did not hold (the team now prefers opaque APIs) and that implicit presence "is not faster" (explicit presence allows batch skipping and branchless sizing). Semantic problems listed: merge of `Timestamp{seconds:200,nanos:0}` onto `{seconds:100,nanos:50}` yields 200.000000050s matching neither input; `x.MergeFrom(Parse(bytes))` ≠ `x.MergeFrom(bytes)`; a patch cannot express "set to zero" (hence `FieldMask`); zero-valued fields vanish from ProtoJSON (hence serializer options). Workarounds judged worse: wrapper types (`Int32Value`) are not wire-compatible with the primitives they replace and cost allocations; single-field oneofs misrepresent the schema. The GitHub issue asking to re-add presence "became the most-commented issue in the Protobuf repository." Editions "removed the `optional` keyword and added a `field_presence` feature that defaults to `EXPLICIT`." — [protobuf.dev Design Decisions: Implicit Presence](https://protobuf.dev/design-decisions/implicit-presence/)
- Sibling design decision: no nullable getters/setters, "we have decided it's not worth the inconsistencies and difficulty it introduces"; "Explicit presence is not a concept that directly maps to the traditional notion of nullability." Fields are not nullable, but you can check whether a field was explicitly assigned. — [protobuf.dev Nullable Getters/Setters](https://protobuf.dev/design-decisions/nullable-getters-setters/)
- Editions overview: `field_presence` values `LEGACY_REQUIRED`, `EXPLICIT`, `IMPLICIT`; "would default to EXPLICIT if it wasn't set". Edition 2023 "established the baseline and combined proto2 and proto3 definitions into a new single definition format"; "Editions won't break existing binaries and don't change a message's binary, text, or JSON serialization format." Latest released edition: 2024. — [protobuf.dev Editions Overview](https://protobuf.dev/editions/overview/)
- Editions announced 2023-06-29 (planned for H2 2023; Prototiller migration tool promised; first edition would need no code changes). — [protobuf.dev news 2023-06-29](https://protobuf.dev/news/2023-06-29). GA with protoc 27.0 per Buf (2024-05-09): "Protobuf Editions will become generally available with the release of protoc 27.0"; "Edition 2023 unifies proto2 and proto3 functionality and semantics." — [Buf: Protobuf Editions are here](https://buf.build/blog/protobuf-editions-are-here). The protobuf.dev news index lists "June 27, 2025 - Edition 2024" and "July 13, 2026 - Edition 2026" (index entries only; posts not opened). — [protobuf.dev news](https://protobuf.dev/news/)
- Buf "Protobuf Tip #8: Never use required" (M. C. Sunny Young de la Sota, 2025-06-03): "All of `required`'s semantics conspire to make it impossible to safely" downgrade to optional or remove; "removing a `required` field that has escaped the scope of your team is *impossible*"; TL;DR "You won't be able to get rid of it later when you realize it was a bad idea"; links required to outages in Google's early use; a parser discards the whole message when a required field is missing even deep in a nested repeated field. — [Buf blog](https://buf.build/blog/totw-8-never-use-required)
- Buf lint ships `FIELD_NOT_REQUIRED` in its BASIC category (v2 configs). — [Buf lint rules](https://buf.build/docs/lint/rules/)
- A 2016 protobuf-group thread quoting the proto3 release notes: removal of required was aimed at making the language easier to implement in open-struct languages (Java, Objective-C, Go); one participant "loved removing required fields but disliked losing field presence." — [groups.google.com protobuf thread](https://groups.google.com/d/msg/protobuf/bO2L6-_t91Q/-zIaJAR9AAAJ)
- Third-party claim (QuickBuffers project notes): not having field presence "turned out to be a major design flaw," and Google's internal protobuf traffic was still "96% based on proto2 5 years after the proto3 release." Unverified vendor claim. — [QuickBuffers proto3.md](https://github.com/HebiRobotics/QuickBuffers/blob/main/proto3.md)
- Google's answer to "required" in its API ecosystem: AIP-203 `google.api.field_behavior` values `REQUIRED`, `OPTIONAL`, `OUTPUT_ONLY`, `INPUT_ONLY`, `IMMUTABLE`, `IDENTIFIER`, `UNORDERED_LIST`; the vocabulary "does not itself add any validation"; a missing REQUIRED request field "must cause an error (usually `INVALID_ARGUMENT`)"; CLIs and SDKs rely on the annotation to generate code; `optional` presence and `OPTIONAL` behaviour "are not mutually exclusive" (see AIP-149). — [AIP-203](https://google.aip.dev/203)

**GraphQL — nullable by default, and the decade-long attempt to fix it**

- Official docs: "Types are assumed to be nullable and singular by default in GraphQL." Non-Null (`!`): "if the resolver produces a null value, then that will trigger a GraphQL execution error." — [graphql.org Schemas and Types](https://graphql.org/learn/schema/)
- Spec §6.4.4 Handling Field Errors: "If the parent field may be null then it resolves to null," otherwise "if it is a `Non-Null` type, the field error is further propagated to its parent field." §7: "A response may contain both a partial response as well as any field errors." — [GraphQL spec October 2021](https://spec.graphql.org/October2021/#sec-Errors)
- Sashko Stubailo (Apollo, 2018-06-05): "By default, every field in GraphQL is nullable, and you can opt in to mark it non-null"; null "bubbles up to the nearest nullable parent"; "When using non-null, you need to decide if you'd rather have a partial result, or no result at all"; "For input arguments and fields, adding non-null is a breaking change"; removing non-null from an output field is breaking, nullable→non-null on outputs is safe; cites Caleb Meredith: "Non-null fields make it hard to evolve your schema." — [Apollo blog](https://www.apollographql.com/blog/using-nullability-in-graphql)
- Apollo Kotlin docs: from the schema alone "it is impossible to tell if null is a valid business value or only happens for errors"; the default "requires to carefully check every field in your UI code." — [Apollo Kotlin nullability](https://www.apollographql.com/docs/kotlin/advanced/nullability)
- Semantic Nullability RFC (opened 2025-02-15, stage "RFC 0 / Strawman"): the core gap is that "GraphQL needs to be able to represent semantically nullable and semantically non-nullable types" once error propagation can be disabled. Eight candidate designs are catalogued: `*` postfix Semantic Non-Null type (champion @benjie), `@strictNullability` + `?` (rejected; @leebyron), `!`/`!!` with document-level directive (rejected; @benjie), `?` for nullable (rejected), "use `!` and encourage disabling error propagation" (rejected; @martinbonnin, "Breaks existing error boundaries"), `@semanticNonNull` field directive (champion @benjie; "the only option that avoids new syntax"), `@propagateError` (champion @leebyron), `@noPropagate` transitional appendix (champion @benjie). — [rfcs.graphql.org SemanticNullability](https://rfcs.graphql.org/rfcs/SemanticNullability/)
- Client-Controlled Nullability (Yelp/Netflix engineers, April 2021): `?`/`!` sigils in operations; "stalled for more than two years"; semantics of `?` were contentious; status page (updated 2026-01-26): "not being worked on at the moment, instead the Nullability working group is currently exploring an alternative solution, namely Semantic Nullability." — [rfcs.graphql.org ClientControlledNullability](https://rfcs.graphql.org/rfcs/ClientControlledNullability/)
- Meta strawman (wg#1394, 2023): "it is considered a best practice to type schema fields as nullable by default in order to allow the GraphQL server to return null for fields who's resolvers throw"; proposes an opt-out of server null bubbling. — [rfcs.graphql.org wg1394](https://rfcs.graphql.org/rfcs/wg1394/)
- RFC #1165 (`@noPropagate` appendix) marked stale 2026-03-19. — [rfcs.graphql.org 1165](https://rfcs.graphql.org/rfcs/1165/). wg#1871 proposes "omit-on-error" (omit the field entirely from `data`). — [rfcs.graphql.org wg1871](https://rfcs.graphql.org/rfcs/wg1871/). wg#1700 proposes making the unadorned type semantically nullable with bubbling as opt-in legacy. — [rfcs.graphql.org wg1700](https://rfcs.graphql.org/rfcs/wg1700/)
- Relay ships an experimental `@semanticNonNull` schema directive that generates non-nullable types when `@throwOnFieldError` is enabled; docs warn behaviour is "subject to change." — [Relay Semantic Nullability](https://relay.dev/docs/guides/semantic-nullability/)
- GraphQL Conf 2024: Jordan Eldredge (Meta), "Semantic Nullability: A Path Toward Safe Non-Null Fields." — [graphql.org conf 2024](https://graphql.org/conf/2024/sessions/8daaf10ac70360a7fade149a54538bf9). GraphQL Conf 2023: Coinbase talk on Client Controlled Nullability. — [graphql.org conf 2023](https://graphql.org/conf/2023/sessions/888b77af90aa0ff776adc9669a29cb3f)
- nullability-wg discussion #58 argues the original reason for nullable-by-default "doesn't still hold" once semantic non-null and no-bubbling exist. — [github graphql/nullability-wg #58](https://github.com/graphql/nullability-wg/discussions/58)
- Practitioner critique (Atomic Object): a non-null resolver that gets null can only report "it wasn't expecting one"; "quite difficult to work through a list of a hundred items to determine which item is missing a particular field"; placeholder values like `""`/`"INVALID"` are "terrible options." — [spin.atomicobject.com](https://spin.atomicobject.com/api-nullable-fields/). advancedweb.hu shows a single denied field nulling a whole parent via bubbling and advises nullable where access is partial, non-null where null means backend error. — [advancedweb.hu](https://advancedweb.hu/shorts/graphql-non-nullable-fields-can-lead-to-cascading-null-errors/)
- HN sentiment: hamandcheese (2023-04-29): GraphQL "lets you be more expressive in your schema, like declaring (non)nullability," but adding a required non-nullable input field "leads to awkward situations." — [HN 35752153](https://news.ycombinator.com/item?id=35752153). tango12 (2020-06-20): "Impedance mismatch with nullability and union types because support is not uniform across languages." — [HN 23581248](https://news.ycombinator.com/item?id=23581248)

**OpenAPI / JSON Schema**

- OpenAPI 3.1.0 (2021-02-18) "now supports 100% compatibility with the latest draft (2020-12) of JSON Schema." Marsh Gardiner (Google, OAI TSC): "Great care was taken in evolving to version 3.1.0 to ensure it is an incremental upgrade for existing users." Ben Hutton (JSON Schema lead): "Full alignment of OpenAPI 3.1.0 with JSON Schema draft 2020-12 will not only save users much pain." — [openapis.org 3.1 release](https://www.openapis.org/blog/2021/02/18/openapi-specification-3-1-released)
- Phil Sturgeon (APIs You Won't Hate, 2020-02-03, updated 2021-01-10): OAS 3.0's "extended subset" of JSON Schema "caused confusion for years"; in 3.1 `nullable: true` is removed and replaced with `type: [string, "null"]`, "probably the biggest breaking change" but "such an easy find and replace"; "Keywords in schema objects generally should not effect other keywords in unexpected ways" (why `exclusiveMinimum` became numeric). — [apisyouwonthate.com](https://apisyouwonthate.com/blog/openapi-v3-1-and-json-schema/)
- Migration write-up: `nullable` was removed "entirely instead of deprecate" to let JSON Schema tools read OpenAPI documents; keyword independence principle: "keywords should only add constraints, but adding one more keyword should not remove a constraint." — [apichangelog.substack.com](https://apichangelog.substack.com/p/migrating-from-openapi-30-to-31)
- JSON Schema 2020-12 object keywords include `required` and `dependentRequired` (required-ness is a property of the containing object, not the property schema). — [json-schema.org 2020-12 validation](https://json-schema.org/draft/2020-12/json-schema-validation)
- OAS 3.1 Schema Object "is a superset of the JSON Schema Specification Draft 2020-12." — [spec.openapis.org 3.1.0](https://spec.openapis.org/oas/v3.1.0.html)
- Zalando RESTful API Guidelines: rule 123 "MUST use same semantics for `null` and absent properties" (with a table of `required`×`nullable` combinations); rule 122 "MUST not use `null` for boolean properties"; rule 124 "SHOULD not use `null` for empty arrays"; rule 101 notes 3.1 removed `example`, `nullable`, `discriminator`, `xml` from the Schema Object. — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/)
- Tooling fallout: a Go OpenAPI library failed to unmarshal a 3.1 `type` array. — [gitlab jamietanna/httptest-openapi #3](https://gitlab.com/jamietanna/httptest-openapi/-/issues/3)

### Inferences
- The protobuf arc is the strongest evidence that *wire-level required* is a trap in evolvable schemas, while *loss of presence* is an equal and opposite trap; Editions resolve this by making presence explicit by default and leaving "required" to validation (protovalidate/field_behavior). A new IDL can start where Editions ended: explicit presence always, `required` as a validation/documentation annotation that generators enforce at the boundary rather than in the parser.
- GraphQL's problem is not nullability per se but conflating "may be absent" with "may fail"; every active proposal separates the two. An IDL that models errors out-of-band (per-operation error types) does not need nullable-by-default for error reasons and can use nullability purely for data semantics.
- OpenAPI's move shows the cost of a bespoke keyword (`nullable`) that collides with a general type system; reusing a well-defined union-with-null is the more durable choice.

### Gaps
- No protobuf.dev page was found that uses the literal phrase "required is forever" beyond the proto2 guide's warning-box title; the Dos-and-Don'ts page does not contain it.
- No HN thread specifically about proto3 `optional` or about GraphQL null bubbling was found via Algolia; the comments cited are from adjacent threads.
- The source of the exact phrase "nullability is a usability problem" was not found.

## 2. Operation inputs: named request/response messages vs arguments vs bodies

### Takeaway
gRPC/Google and Buf both mandate a unique `FooRequest`/`FooResponse` message per RPC, justified entirely by evolvability (fields can be added without touching other RPCs); the cost is boilerplate, which practitioners grumble about. GraphQL exposes named arguments on fields but the dominant mutation convention (Relay/Apollo) converges on the same shape: one required `input` object per mutation. OpenAPI inlines freely, and code generators punish it with auto-named anonymous types, so style guides push everything into `components` and `$ref`.

### Cited Findings

**gRPC / protobuf**

- AIP-131 (Get, created 2019-01-22): "The request message **must** match the RPC name, with a `Request` suffix." "The response **must** be the resource itself. (There is no `GetBookResponse`.)" "The request message **must not** contain any other required fields, and **should not** contain other optional fields except those described in another AIP." — [AIP-131](https://google.aip.dev/131)
- Buf lint STANDARD category ships `RPC_REQUEST_STANDARD_NAME`, `RPC_RESPONSE_STANDARD_NAME`, `RPC_REQUEST_RESPONSE_UNIQUE`: messages named `MethodNameRequest`/`MethodNameResponse` (or service-prefixed) and unique across the schema. Rationale: "A unique request and response message per RPC is one of the most important rules in modern Protobuf development." "Sharing a Protobuf message between RPCs means every change to that message ripples across every RPC that references it." "Even in trivial cases, define a wrapper message for the request and response." Escape hatches (`rpc_allow_same_request_response`, `rpc_allow_google_protobuf_empty_requests/responses`) exist and "Buf does not recommend them." — [Buf lint rules](https://buf.build/docs/lint/rules/)
- Dos and Don'ts: "**Do** Use Different Messages For RPC APIs and Storage"; "the needs of long-term storage and live RPC services tend to later diverge"; "Messages and enums are intended to be atomic with regards to reuse"; "You should not use another message's nested types as reusable vocabulary." — [protobuf.dev Dos and Don'ts](https://protobuf.dev/best-practices/dos-donts/)
- Sentiment: frde_me (HN, 2024-09-11) shows `rpc doSomething(DoSomethingRequest) returns (DoSomethingResponse);` with empty `message DoSomethingRequest {}` / `DoSomethingResponse {}` and describes it as boilerplate they would like to automate. — [HN 41515022](https://news.ycombinator.com/item?id=41515022)
- Mechanically, request/response types are opaque to the transport: a 2010 RProtoBuf list post explains that from the RPC layer's view the messages are "unknown classes" handled as serialized raw bytes, which is why RPC libraries define a generic envelope. — [rprotobuf-yada list](https://lists.r-forge.r-project.org/pipermail/rprotobuf-yada/2010-September/000170.html)

**GraphQL**

- "Every field on a GraphQL Object type can have zero or more arguments"; "all arguments in GraphQL are passed by name"; Input Object types exist to "pass complex objects as arguments," "particularly valuable in the case of mutations"; "you can't mix input and output types in your schema. Input Object types also can't have arguments on their fields." — [graphql.org Schemas and Types](https://graphql.org/learn/schema/)
- Apollo "Designing GraphQL Mutations" (2017-03-28): mutations "should only ever have one input argument, named input, with a non-null unique input object type." — [Apollo blog](https://www.apollographql.com/blog/graphql/basics/designing-graphql-mutations)
- graphql-rules (2018): single input object "makes it much easier to track changes in your API" with static typing; "the GraphQL specification does not have the ability to deprecate arguments. But deprecating field inside the type of input is possible" (a 2018 claim; see Gaps). — [graphql-rules mutation-input-arg](https://graphql-rules.onrender.com/rules/mutation-input-arg/)
- Golden Path guidance: "Keep room for additive optional inputs over time… Keep mutation construction stable as optional input fields are added." — [goldenpath.graphql.org](https://goldenpath.graphql.org/solutions/mutation-input-objects/)
- Input polymorphism was missing until 2025: RFC 825 "OneOf Input Objects" (champion @benjie, opened 2021-02-19, spec PR merged 2025-09-01, "RFC 3 / Accepted") addresses "the InputUnion problem"; an input object marked `@oneOf` requires that "exactly one of the fields must be set and non-null, all others being omitted." — [rfcs.graphql.org 825](https://rfcs.graphql.org/rfcs/825/)

**OpenAPI**

- Request Body Object: `content` is required, `required` defaults to `false`; `requestBody` on GET/HEAD/DELETE has vague semantics and "should be avoided." Components "have no effect on the API unless they are referenced." Reference Object "cannot be extended with additional properties and any properties added SHALL be ignored." — [spec.openapis.org 3.1.0](https://spec.openapis.org/oas/v3.1.0.html)
- APIMatic: inline schemas "can result in poorly named classes"; large definitions "end up with generic or similar class names like status1, status2, and inlineResponse200." — [apimatic.io](https://www.apimatic.io/openapi/array-of-objects)
- An SDK generator author needed libopenapi to tell whether a type was "shared ie defined as a reference or defined inline so I don't duplicate types while generating." — [github pb33f/libopenapi #25](https://github.com/pb33f/libopenapi/issues/25)
- Spectral's `oas3-unused-component` is on by default (warn), with the note it "may false-positive on libraries." — [Spectral OpenAPI rules](https://raw.githubusercontent.com/stoplightio/spectral/develop/docs/reference/openapi-rules.md)

### Inferences
- All three communities independently arrived at "one named, evolvable input structure per operation." The disagreement is only about whether the IDL should *force* it (Buf/AIP) or leave it as convention (GraphQL, OpenAPI). An IDL that makes the operation's input/output *implicitly* a named structure (Smithy-style `input := { ... }` sugar) gets the evolvability without the empty-message boilerplate that frde_me complains about.
- GraphQL's 4.5-year `@oneOf` journey shows that an input type system without unions is a recurring pain point; a new IDL should have input unions from day one.

### Gaps
- No Reddit threads on request/response wrappers surfaced through search (the `site:reddit.com` operator was ineffective).
- Whether `@deprecated` on arguments/input fields was later added to the GraphQL spec (after the 2018 graphql-rules claim) was not verified in this pass.
- AIP-131 gives no explicit rationale for the `Request` suffix; the rationale is only in Buf's lint docs.

## 3. Custom metadata and extensions

### Takeaway
Protobuf custom options are first-class, numbered, and registry-governed, and the whole Google API ecosystem (HTTP transcoding, field behaviour, validation) is built on them. OpenAPI's `x-` extensions are free-form and explicitly "may or may not be supported by tooling." GraphQL directives are the most contested: they exist in SDL but are invisible to introspection, a gap open since 2017 (#300) with a 2022 "Metadata Directives" proposal still unresolved in late 2024; Federation shows how heavily tooling nonetheless depends on them.

### Cited Findings

**Protobuf**

- "Protobuf also allows you to define and use your own options. Note that this is an **advanced feature** which most people don't need." Custom options use extensions, "which are permitted only for custom options in proto3." Example: `extend google.protobuf.EnumValueOptions { optional string string_name = 123456789; }`. — [protobuf.dev proto3 guide](https://protobuf.dev/programming-guides/proto3/)
- Defining one means extending the options messages in `google/protobuf/descriptor.proto` (`FileOptions`, `FieldOptions`, …); 50000–99999 "is reserved for internal use within individual organizations"; public options need globally unique numbers from the global extension registry on GitHub. Extensions are fields "defined outside its container message," reducing imports and letting systems attach data "with minimal dependency and coordination." — [protobuf.dev proto2 guide](https://protobuf.dev/programming-guides/proto2/)
- Consumers: AIP-127 `google.api.http` (approved, 2019-08-22) — "each RPC must define the HTTP method and path using the `google.api.http` annotation"; `body: "*"` means the whole request is the HTTP body; GET/DELETE must not define a body. — [AIP-127](https://google.aip.dev/127). AIP-203 `field_behavior` is consumed by CLIs and SDKs for code generation. — [AIP-203](https://google.aip.dev/203). PGV used `(validate.rules)` options; protovalidate uses `(buf.validate.field)` / `(buf.validate.message)` options. — [protoc-gen-validate README](https://github.com/bufbuild/protoc-gen-validate), [protovalidate.com](https://protovalidate.com/)

**OpenAPI**

- Specification Extensions: field names MUST begin with `x-` (e.g. `x-internal-id`); "Field names beginning x-oai- and x-oas- are reserved for uses defined by the OpenAPI Initiative"; "The extensions may or may not be supported by the available tooling." — [spec.openapis.org 3.1.0](https://spec.openapis.org/oas/v3.1.0.html)
- Zalando mandates `#/info/x-api-id` (rule 215) and `#/info/x-audience` (rule 219), and rule 111 "MUST treat OpenAPI specification as open for extension by default." — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/)
- Spectral's ruleset format supports custom rules in YAML/JS (see §8).

**GraphQL**

- graphql-spec #300, "Expose user-defined meta-information via introspection API in form of directives," opened 2017-04-28 by OlegIlyenko; still open, labelled "Strawman (RFC 0)". Oleg: directive info "is the only schema detail missing from introspection"; use cases: field cost/complexity, auth, caching. — [github graphql-spec #300](https://github.com/graphql/graphql-spec/issues/300)
- Practical consequence: graphql-kotlin maintainers attribute missing-directive problems to "IDE plugins that rely on introspection to get the schema (which does not include directive information, see graphql/graphql-spec#300)"; workaround is printing SDL. — [github ExpediaGroup/graphql-kotlin PR 1350](https://github.com/ExpediaGroup/graphql-kotlin/pull/1350). graphql-java ships `IntrospectionWithDirectivesSupport` because "the graphql specification does not allow you to retrieve the directives and their argument values." — [graphql-java javadoc](https://javadoc.io/static/com.graphql-java/graphql-java/21.1/graphql/introspection/IntrospectionWithDirectivesSupport.html). Apollo forum: custom directives won't show in Studio "until/unless the GraphQL spec… supports exposing user-defined server-side directives via introspection." — [community.apollographql.com](https://community.apollographql.com/t/custom-directives-not-in-the-apollo-studio-schema/3711)
- graphql-wg discussion #1096 "Metadata Directives" (leebyron, 2022-08-04): mark a directive `metadata` (like `repeatable`), add `__Directive.isMetadata`, a `metadata: [__Metadata!]` list on introspection types, values as GraphQL-literal strings; "My goal here is to introduce something with as few additional moving parts as possible." Positions: michaelstaib (2022-08-06) "we should take directives and improve them rather than introducing something new"; rivantsov and bbakerman note `appliedDirectives` already shipped in HotChocolate and graphql-java; IvanGoncharov (2022-08-09): "We can't parse values in GraphQL format without access to `parseLiteral` of custom scalars"; benjie (2022-08-29, again 2024-11-25): "This definitely needs solving, and comes up frequently" but prefers a representation "that does not require a parser"; LunaticMuch (2024-11-25): "Is there any appetite to carry on with this?" Last activity 2024-11-27; no decision. — [github graphql-wg #1096](https://github.com/graphql/graphql-wg/discussions/1096)
- Federation as the dominant directive consumer: subgraphs `@link` the federation spec and import `@key`, `@shareable`, `@external`, `@requires`, `@provides`, `@override`, `@inaccessible`, `@tag`, `@composeDirective`, `@interfaceObject`; "by default, composition omits most directives from the supergraph schema"; custom directives survive only when listed in `@composeDirective`. — [Apollo Federation directives](https://www.apollographql.com/docs/graphos/reference/federation/directives)

### Inferences
- Protobuf shows that typed, declared options (with a schema for the option itself) are what let an ecosystem of independent tools (transcoding, validation, SDK generators) coexist. OpenAPI's untyped `x-` namespace is cheap but gives tools no contract. GraphQL's directives are typed and declared but not introspectable, so every tool re-parses SDL.
- The design lesson is: metadata should be typed, declared, namespaced, and reachable through the same reflection surface as the rest of the model.

### Gaps
- The Redocly page listing consumed `x-` extensions (x-logo, x-codeSamples, x-tagGroups, …) returned 404; no first-party list of tool-consumed extensions was captured.
- graphql-spec #300's comment thread (positions of leebyron, IvanGoncharov, etc.) was not retrievable; only the opening post was.

## 4. Constraints and validation

### Takeaway
Protobuf validation moved from per-language code generation (PGV, 2017→maintenance, archived 2026) to runtime CEL evaluation (protovalidate) specifically because keeping N generators consistent proved infeasible. JSON Schema has a mature keyword vocabulary but `format` is annotation-only by default. GraphQL has nothing in the spec; `@constraint` exists as a family of mutually incompatible community directives.

### Cited Findings

- PGV history (Chris Roche, Buf, 2023-04-24): "PGV emerged from a 2017 Lyft hackathon project"; moved to the Envoy org in 2019; "Buf subsequently took over maintenance of PGV in 2022"; "The current code generator's template-based implementation has fossilized in the face of feature requests and bug fixes"; early decisions made "custom error messages, arbitrary constraint expressions, shareable rules" infeasible; v2 is "A CEL-based implementation, promoting consistent behavior across all targeted languages." — [Buf blog PGV v1 and v2](https://buf.build/blog/protoc-gen-validate-v1-and-v2)
- PGV README: "protoc-gen-validate (PGV) has reached a stable state and is in maintenance mode… We recommend that new and existing projects transition to using `protovalidate`." Repository archived 2026-05-27. PGV generated `Validate` methods per language (Go, Java at compile time; Python at runtime) from `(validate.rules)` options. — [github bufbuild/protoc-gen-validate](https://github.com/bufbuild/protoc-gen-validate)
- Why CEL: with PGV, adding the UUID string rule "had to consistently implement the definition of a UUID string in Go, Java, and C++"; protovalidate "defines a library of CEL expressions for common rules that work across all of its supported languages"; it "doesn't rely on any code generation"; core is "one Protobuf file using the proto2 syntax to define options." — [Buf docs: how CEL works](https://protovalidate.com/cel/how-cel-works/), [Buf protovalidate docs](https://buf.build/docs/protovalidate)
- protovalidate.com: "the semantic validation library for Protobuf"; standard annotations plus CEL; example message rule `option (buf.validate.message).cel = { … expression: "!has(this.first_name) || has(this.last_name)" }`; runtimes for Go, JS/TS, Java, Python, C++; "Plug validation interceptors into your Connect/gRPC services." — [protovalidate.com](https://protovalidate.com/)
- Buf lint's STANDARD category includes a `PROTOVALIDATE` rule (validates rule usage at lint time). — [Buf lint rules](https://buf.build/docs/lint/rules/)
- Google's stance: field_behavior "does not itself add any validation"; enforcement is the service's job. — [AIP-203](https://google.aip.dev/203)
- JSON Schema 2020-12 validation keywords: `type`, `enum`, `const`; `multipleOf`, `maximum`, `exclusiveMaximum`, `minimum`, `exclusiveMinimum`; `maxLength`, `minLength`, `pattern`; `maxItems`, `minItems`, `uniqueItems`, `maxContains`, `minContains`; `maxProperties`, `minProperties`, `required`, `dependentRequired`. Format-Annotation vocabulary: "The value of format MUST be collected as an annotation"; assertion "MUST be disabled by default"; Format-Assertion vocabulary is optional and syntactic only. `contentEncoding`/`contentMediaType`/`contentSchema` are annotations; malformed content "MUST NOT cause the containing instance to be considered invalid." — [json-schema.org 2020-12 validation](https://json-schema.org/draft/2020-12/json-schema-validation)
- Spectral validates examples against schemas (`oas3-valid-schema-example`, `oas3-valid-media-example`, error severity, recommended). — [Spectral OpenAPI rules](https://raw.githubusercontent.com/stoplightio/spectral/develop/docs/reference/openapi-rules.md)
- GraphQL: Apollo blog describes `@constraint` to "see validation logic in the schema and avoid repetitive code in resolver functions or models." — [Apollo blog: validation using directives](https://www.apollographql.com/blog/graphql-validation-using-directives). bahn-x implementation supports `format: "email"`, `min`, `max`, `exclusiveMin`, `exclusiveMax`, `multipleOf`. — [github bahn-x/graphql-constraint-directive](https://github.com/bahn-x/graphql-constraint-directive). Mercurius uses JSON-Schema-named keywords (`maximum`, `minimum`, `maxLength`, `minLength`, `pattern`, `required`, `uniqueItems`). — [mercurius-validation docs](https://cdn.jsdelivr.net/npm/mercurius-validation@7.0.0/docs/directive-validation.md). SmallRye declares `@constraint` `repeatable`. — [smallrye.io](https://smallrye.io/smallrye-graphql/2.0.0/directives/). One package says it is "inspired by Constraints Directives RFC and OpenAPI." — [npm graphql-constraint-directive-plus](https://www.npmjs.org/package/graphql-constraint-directive-plus)

### Inferences
- The PGV→protovalidate story is the single most relevant precedent for a multi-language generator project: a shared, language-neutral rule semantics (a small expression language plus a conformance suite) beats per-language templates once the target-language count grows.
- JSON Schema's "format is advisory" default is a recurring interoperability surprise; an IDL should decide explicitly whether `format`-like constraints are assertions.
- GraphQL's fragmented `@constraint` ecosystem demonstrates the cost of leaving constraints out of the core: N incompatible vocabularies.

### Gaps
- No official GraphQL "Constraints Directives RFC" document was located; it is referenced only by implementations.
- Runtime cost of CEL vs generated validators was not covered by any retrieved source.
- Publication date of Buf's "Protovalidate is now v1.0" post was not captured.

## 5. Errors

### Takeaway
gRPC deliberately keeps errors *out* of the service definition: a fixed set of 16 canonical codes plus optional `google.rpc.Status` details in trailers; Google's AIPs forbid per-API error enums and require `ErrorInfo{reason, domain}` for machine-readable discrimination; Connect keeps the same 16 codes but serialises errors as JSON with HTTP status mapping. OpenAPI models errors per status code with `default` as a catch-all, and RFC 9457 (2023, obsoleting 7807) is the de-facto body format. GraphQL's spec-level `errors` array is minimally specified, so the community's "errors as data" (union result types) pattern grew up to get typed, documented errors; its known drawback is that it is one-way.

### Cited Findings

**gRPC / Connect / Google**

- grpc.io: "If an error occurs, gRPC returns one of its error status codes instead, with an optional string error message"; richer model: "additional error details expressed as one or more protobuf messages," "provided as trailing metadata in the response"; supported in C++, Go, Java, Python, Ruby; "the grpc-core library written in C will not likely ever support it" because it is data-format agnostic; grpc-web and Node had open requests. — [grpc.io error guide](https://grpc.io/docs/guides/error/)
- .NET docs: the richer-model error "is encapsulated by an instance of Google.Rpc.Status and returned in the trailing response metadata with well-known key grpc-status-details-bin"; `details` is "a repeating field of Any values"; recommended payload types `BadRequest`, `PreconditionFailure`, `ErrorInfo`, `ResourceInfo`, `QuotaFailure`; warning that response headers "are often limited to 8 KB." — [learn.microsoft.com gRPC error handling](https://learn.microsoft.com/en-us/aspnet/core/grpc/error-handling)
- AIP-193 (created 2019-07-26, changelog to 2024-10-18): "Services must return a google.rpc.Status message when an API error occurs," using canonical `google.rpc.Code`; "All error responses must include an ErrorInfo within details"; "The (reason, domain) pair form a machine-readable way of identifying a particular error"; rationale: "it is difficult to disambiguate one error from another across an entire API Service" and messages contain dynamic values; "Status.message is implicitly part of the API contract, so must not be updated"; `LocalizedMessage` carries BCP 47 locale. — [AIP-193](https://google.aip.dev/193). (cloud.google.com/apis/design/errors now redirects to AIP-193.)
- Connect protocol: "An `Error` is a code, an optional message, and an optional array of details"; details are typed Protobuf messages base64-encoded, with an optional `debug` JSON field clients must not depend on; 16 codes "chosen to match gRPC" with a fixed HTTP mapping (`invalid_argument`→400, `not_found`→404, `already_exists`→409, `permission_denied`→403, `resource_exhausted`→429, `unimplemented`→501, `unavailable`→503, `unauthenticated`→401, …); design goals: "human-readable and debuggable with general-purpose HTTP tools," "Remain conceptually close to gRPC's HTTP/2 protocol," "Depend only on widely-implemented HTTP features"; "The protocol doesn't use HTTP trailers at all." — [connectrpc.com protocol](https://connectrpc.com/docs/protocol/)

**OpenAPI / HTTP**

- Responses Object "MUST contain at least one response code," a `default` entry for undeclared responses, wildcard ranges `1XX`–`5XX`, explicit codes take precedence over ranges. — [spec.openapis.org 3.1.0](https://spec.openapis.org/oas/v3.1.0.html)
- RFC 9457 (July 2023, Standards Track) obsoletes RFC 7807: members `type` (URI, defaults to `about:blank`), `status` ("only advisory"), `title`, `detail`, `instance`; extension members that clients "MUST ignore… that they don't recognize"; media types `application/problem+json` / `+xml`; new "HTTP Problem Types" IANA registry (Specification Required; only `about:blank` registered by the RFC itself); clarified handling of multiple problems and non-dereferenceable type URIs. — [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)
- Zalando rule 176 "MUST support problem JSON," rule 177 "MUST not expose stack traces," rule 243 "MUST use official HTTP status codes," rule 150 "SHOULD only use most common HTTP status codes," rule 151 "MUST specify success and error responses." — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/)
- Redocly's `operation-4xx-problem-details-rfc7807` lint rule expects every 4xx to use `application/problem+json` with `title` and `type`; it is off by default. — [redocly.com rule docs](https://redocly.com/docs/cli/rules/oas/operation-4xx-problem-details-rfc7807)
- Spectral: `operation-success-response` (needs at least one 2xx/3xx) is recommended. — [Spectral OpenAPI rules](https://raw.githubusercontent.com/stoplightio/spectral/develop/docs/reference/openapi-rules.md)

**GraphQL**

- Spec §7.1.2: "Every error must contain an entry with the key `message`"; `locations` when tied to the document; `path` when tied to a response field; `extensions` "is reserved for implementors to add additional information to errors however they see fit"; "GraphQL services should not provide any additional entries to the error format." — [GraphQL spec October 2021](https://spec.graphql.org/October2021/#sec-Errors)
- Apollo Server: each error's `extensions` carries a `code` (and stack trace in dev); non-`ApolloError` throws become `INTERNAL_SERVER_ERROR`; errors can be returned "alongside data/fields that resolved successfully." — [Apollo Server errors docs](https://www.apollographql.com/docs/apollo-server/data/errors), [Apollo blog 2018-06-13](https://apollographql.com/blog/full-stack-error-handling-with-graphql-apollo)
- "Errors as data": Sasha Solomon's talk "200 OK! Error Handling in GraphQL" proposes that "expected errors" be modelled "not as errors, but as different response types" (Stefan Judis' summary). — [stefanjudis.com](https://www.stefanjudis.com/blog/should-every-error-result-in-an-error-in-graphql-too). codecentric credits the talk, uses `union OrderResult = Order | OrderNotFound | OrderLocked`, and names the limitation: "communication is one-way, server to client. The backend cannot tell which clients handle which errors." — [codecentric blog](https://www.codecentric.de/en/knowledge-hub/blog/graphql-business-error-responses-revisited). The Guild (Ghislain Thau, 2022-03-07): union errors give type safety and a self-documented schema; "GraphQL Union is available for Types only, not for Inputs." — [the-guild.dev](https://www.the-guild.dev/blog/graphql-error-handling-with-fp)
- Vendure's framework formalises an `ErrorResult` union convention. — [docs.vendure.io](https://docs.vendure.io/current/core/reference/typescript-api/errors/error-result-union)

### Inferences
- gRPC's choice (errors outside the IDL) optimises for a uniform client runtime and infrastructure (retries, load balancers) at the cost of discoverability; Google compensates with the `ErrorInfo.reason/domain` convention, i.e. a *stringly-typed modelled error* bolted on. OpenAPI and GraphQL both grew explicit modelled-error layers (RFC 9457 types; union results) because consumers want enumerable, documented failure modes.
- A new IDL can model errors per operation (the Smithy approach) *and* carry a canonical code so transports (gRPC/Connect/HTTP) get their uniform behaviour; the two are not in tension.

### Gaps
- The original "200 OK!" talk transcript was not retrieved; only secondary summaries.
- Marc-André Giroux's "Guide to GraphQL errors" returned 403.

## 6. Reuse: inheritance, interfaces, composition

### Takeaway
Protobuf offers no inheritance and no official rationale page was found; its documented stance is that messages are "atomic with regards to reuse," with `oneof`/`Any`/nesting as the tools. GraphQL has interfaces (including interface-implements-interface since 2020), unions of concrete object types, and fragments, with docs cautioning that interfaces must be "semantically meaningful." OpenAPI `allOf` is composition that "does not imply a hierarchy," and the single-`$ref` `allOf` has been fought over because generators read inheritance into it.

### Cited Findings

- Protobuf: Red Hat's Infinispan docs on protobuf constraints: nesting yields "strictly a tree, and never a graph. There is no type inheritance." — [docs.redhat.com](https://docs.redhat.com/en/documentation/red_hat_data_grid/6.2/html/infinispan_query_guide/about_protobuf_messages). "Messages and enums are intended to be atomic with regards to reuse." — [protobuf.dev Dos and Don'ts](https://protobuf.dev/best-practices/dos-donts/). `oneof`: "at most one field can be set at the same time"; `Any` "contains an arbitrary serialized message as `bytes`, along with a URL that acts as a globally unique identifier." — [protobuf.dev proto3 guide](https://protobuf.dev/programming-guides/proto3/). Generated classes became `final`, forcing composition in a SiLA C++ project: "we cannot inherit from them anymore… all other classes simply have a member of the corresponding protobuf generated SiLA Type." — [gitlab SiLA2/sila_cpp #32](https://gitlab.com/SiLA2/sila_cpp/-/issues/32). protobuf-net (C#) requires explicit `[ProtoInclude]` and rejects `IExtensible` "in structs or classes with inheritance." — [protobuf-net README](https://cdn.jsdelivr.net/gh/protobuf-net/protobuf-net@main/README.md)
- GraphQL: interfaces define fields "a concrete Object type or other Interface type must also include"; "Interface types may not implement themselves or contain any cyclic references"; "While types may share common fields… that may not always warrant the use of an Interface type"; unions "cannot define any shared fields" and members "need to be concrete Object types." — [graphql.org Schemas and Types](https://graphql.org/learn/schema/). RFC #373 "Allow interfaces to implement other interfaces" merged 2020-01-11 (RFC 3 / Accepted); rules "essentially identical to the rules governing implementation of an interface by an object." — [rfcs.graphql.org 373](https://rfcs.graphql.org/rfcs/373/). RFC #460 (interfaces must implement at least one object) was rejected October 2018. — [rfcs.graphql.org 460](https://rfcs.graphql.org/rfcs/460/)
- OpenAPI: "allOf takes an array of object definitions that are validated independently but together compose a single object"; "While composition offers model extensibility, it does not imply a hierarchy between the models"; "the discriminator field MUST be a required field"; "When using the discriminator, inline schemas will not be considered." — [spec.openapis.org 3.1.0](https://spec.openapis.org/oas/v3.1.0.html)
- OAI issue #2500: removing inheritance treatment for single-`$ref` `allOf` "broke things in the OpenAPI Generator"; one commenter argues a single reference "could very well be treated as an inheritance type relationship even without the use of a discriminator"; the counter-position is "add keywords to disambiguate validation constructs for code generation, rather than make assumptions about their meaning that will never hold true globally"; another contributor found a doc tool "kept assuming that schema organization… had OO inheritance meaning, which made the tool worthless for me." — [github OAI/OpenAPI-Specification #2500](https://github.com/OAI/OpenAPI-Specification/issues/2500)
- Generators flatten: without a discriminator, APIMatic "merges all referenced properties into a single structure." — [docs.apimatic.io](https://docs.apimatic.io/generate-sdks/sdk-features/inheritance-and-polymorphism-with-all-of/). TM Forum review found discriminator mappings containing themselves and mixed `oneOf`/`allOf` that one generator could not resolve. — [engage.tmforum.org](https://engage.tmforum.org/discussion/tmf931-open-gateway-operate-api-onboarding-and-ordering-v511-issues)

### Inferences
- Across all three, "inheritance" is either absent (protobuf), nominal-only (GraphQL interfaces carry no field reuse at the implementation level; each object restates fields), or structural-and-ambiguous (OpenAPI `allOf`). The recurring failure is tools *inferring* hierarchy from structure. An IDL should have explicit, named constructs for the two different intents (mixin/field reuse vs. tagged polymorphism) so generators never guess.

### Gaps
- No primary protobuf source (protobuf.dev or a maintainer statement) explaining *why* inheritance was excluded was found; the "atomic reuse" guidance is the closest official text. Treat the common explanation (field-number wire format; language neutrality) as unsourced.
- OAI #2500's date and resolution status were not captured.

## 7. Documentation: comments and how they reach generated code

### Takeaway
Protobuf attaches `//`/`/* */` comments to declarations via `SourceCodeInfo` (leading, trailing, leading-detached) and plugins such as protoc-gen-go and protoc-gen-doc copy leading comments into generated doc comments; blank lines detach a comment. GraphQL distinguishes `"""descriptions"""` (introspectable, Markdown) from `#` comments (ignored). OpenAPI `description` fields are CommonMark, which tooling may partially ignore for security.

### Cited Findings

- Protobuf style: "Prefer C/C++/Java line-end-style comments '//' on the line before the .proto code element"; `/* */` also accepted, "a margin line of '*' is preferred." — [protobuf.dev proto3 guide](https://protobuf.dev/programming-guides/proto3/)
- `SourceCodeInfo.Location`: `leading_comments` holds comments "that seem attached to" a declaration; `leading_detached_comments` holds paragraphs before but not connected; comment markers are stripped and block-comment asterisks removed. — [SourceCodeInfo.Location docs (via Temporal TS types)](https://typescript.temporal.io/api/interfaces/proto.google.protobuf.SourceCodeInfo.ILocation)
- protoc-gen-go (2019 change): replaced `PrintLeadingComments` with per-descriptor `CommentSet` (leading, trailing) after finding "there can actually be duplicate locations for certain paths"; later reads `SourceLocations().ByPath(...)` and emits `LeadingComments`/`LeadingDetachedComments`. — [go.googlesource.com protobuf commit](https://go.googlesource.com/protobuf/+/70fdd5d140c5bd6b2a9609069ecf679ecf120b25%5E%21/), [follow-up commit](https://go.googlesource.com/protobuf/+/42cc4c592f87f9c4fa8c52df6a1c0abd6c7fb571%5E%21/)
- protoc-gen-doc: generates HTML/JSON/DocBook/Markdown "from comments in your .proto files"; leading comments work everywhere; "Fields, Service Methods, Enum Values and Extensions support trailing comments"; file-level docs are leading comments on the `syntax` directive. — [github thethingsindustries/protoc-gen-doc](https://github.com/thethingsindustries/protoc-gen-doc). A blank line between comment and element makes it detached and omitted. — [pkg.go.dev protoc-gen-docjson](https://pkg.go.dev/github.com/cuberat/protoc-gen-docjson)
- Buf lint `COMMENTS` category requires leading comments on enums, enum values, fields, messages, oneofs, RPCs and services. — [Buf lint rules](https://buf.build/docs/lint/rules/)
- GraphQL: "the GraphQL specification encourages you to do this in all cases unless the name… is self-descriptive. Schema descriptions are defined using Markdown syntax"; descriptions "are available in introspection queries and visible in developer tools such as GraphiQL"; a `#` comment "is treated like whitespace and ignored by GraphQL." — [graphql.org Schemas and Types](https://graphql.org/learn/schema/)
- OpenAPI: description fields support CommonMark; "Tooling may ignore some CommonMark features to address security concerns." — [spec.openapis.org 3.1.0](https://spec.openapis.org/oas/v3.1.0.html). Spectral enforces `info-description` and `operation-description` by default and flags `<script>`/`eval(` in Markdown (`no-script-tags-in-markdown`, `no-eval-in-markdown`). — [Spectral OpenAPI rules](https://raw.githubusercontent.com/stoplightio/spectral/develop/docs/reference/openapi-rules.md)

### Inferences
- GraphQL's explicit doc-string vs comment distinction avoids the "detached comment" ambiguity protobuf tooling has to handle; an IDL benefits from a syntactic doc-comment form that is part of the model (and therefore of reflection/introspection), separate from throwaway comments.

### Gaps
- No pseudomuto/protoc-gen-doc authoritative conventions document was found; behaviour is inferred from forks' READMEs.

## 8. Linting and compatibility checking

### Takeaway
Buf ships tiered lint categories (MINIMAL ⊂ BASIC ⊂ STANDARD, plus COMMENTS and UNARY_RPC) and four breaking-change levels (FILE ⊃ PACKAGE ⊃ WIRE_JSON ⊃ WIRE). Spectral's `oas` ruleset is a flat list with a `recommended` subset, heavy on hygiene (operationIds, tags, descriptions, example validity). GraphQL Inspector classifies diffs as breaking/dangerous/non-breaking and lets usage data soften "breaking."

### Cited Findings

- Buf lint: MINIMAL (`DIRECTORY_SAME_PACKAGE`, `PACKAGE_DEFINED`, `PACKAGE_DIRECTORY_MATCH`, `PACKAGE_NO_IMPORT_CYCLE`, `PACKAGE_SAME_DIRECTORY`); BASIC adds naming/casing (`ENUM_FIRST_VALUE_ZERO`, `ENUM_NO_ALLOW_ALIAS`, `FIELD_LOWER_SNAKE_CASE`, `FIELD_NOT_REQUIRED`, `IMPORT_NO_PUBLIC`, `IMPORT_USED`, `MESSAGE_PASCAL_CASE`, `SYNTAX_SPECIFIED`, seven `PACKAGE_SAME_<option>`); STANDARD (default) adds `ENUM_VALUE_PREFIX`, `ENUM_ZERO_VALUE_SUFFIX`, `FILE_LOWER_SNAKE_CASE`, `PACKAGE_VERSION_SUFFIX`, `PROTOVALIDATE`, `RPC_REQUEST_STANDARD_NAME`, `RPC_RESPONSE_STANDARD_NAME`, `RPC_REQUEST_RESPONSE_UNIQUE`, `SERVICE_SUFFIX`; COMMENTS; UNARY_RPC (`RPC_NO_CLIENT_STREAMING`, `RPC_NO_SERVER_STREAMING`); `STABLE_PACKAGE_NO_IMPORT_UNSTABLE` opt-in. — [Buf lint rules](https://buf.build/docs/lint/rules/)
- Buf breaking: FILE (default, strictest, "necessary for C++ and Python"), PACKAGE (types may move within a package; suggested for Go), WIRE_JSON (recommended minimum), WIRE ("Detects changes that break wire (binary) encoding"); "If you don't know which to pick, start with `FILE`… you can always relax later." Rules include `FIELD_SAME_TYPE`, `FIELD_SAME_CARDINALITY` (optional/repeated/map/required), `FIELD_SAME_JSON_NAME` (also in WIRE_JSON), `ENUM_VALUE_NO_DELETE` (deprecate instead). — [Buf breaking rules](https://buf.build/docs/breaking/rules/)
- Spectral `oas` ruleset (recommended unless noted): `duplicated-entry-in-enum`, `info-contact`, `info-description`, `no-$ref-siblings` (error), `no-eval-in-markdown`, `no-script-tags-in-markdown`, `openapi-tags-uniqueness` (error), `operation-description`, `operation-operationId`, `operation-operationId-unique` (error), `operation-operationId-valid-in-url`, `operation-parameters`, `operation-success-response`, `operation-tags`, `operation-tag-defined`, `path-declarations-must-exist`, `path-keys-no-trailing-slash`, `path-not-include-query`, `path-params` (error), `typed-enum`, `array-items` (error); OAS3: `oas3-api-servers`, `oas3-examples-value-or-externalValue`, `oas3-operation-security-defined`, `oas3-schema` (error), `oas3-server-trailing-slash`, `oas3-unused-component`, `oas3-valid-media-example` (error), `oas3-valid-schema-example` (error), `oas3-server-variables` (error), `oas3_1-servers-in-webhook`, `oas3_1-callbacks-in-webhook`, `oas3_2-no-deprecated-xml-attribute`. Not recommended: `contact-properties`, `info-license`, `license-url`, `openapi-tags`, `openapi-tags-alphabetical`, `operation-singular-tag`, `tag-description`, `oas3-parameter-description`, `oas3-server-not-example.com`. — [Spectral OpenAPI rules](https://raw.githubusercontent.com/stoplightio/spectral/develop/docs/reference/openapi-rules.md)
- GraphQL Inspector (introduced by Kamil Kisiela, The Guild, 2019-01-18): "GraphQL Inspector defines three kinds of changes" — non-breaking, dangerous, breaking; "When there's at least one breaking change, the process fails." Rules: `dangerousBreaking` ("Turns every dangerous change to be a breaking change"), `suppressRemovalOfDeprecatedField` (downgrades removal of a deprecated field to dangerous), `ignoreDescriptionChanges`, `safeUnreachable` (breaking changes to unreachable types are not breaking), `considerUsage` (requires an `--onUsage` script; example checks whether a field was used in the last 30 days), plus custom JS/TS rules via `--rule`. — [the-guild.dev Inspector diff docs](https://the-guild.dev/graphql/inspector/docs/essentials/diff), [Introducing GraphQL Inspector (2019)](https://the-guild.dev/blog/introducing-graphql-inspector)
- Secondary (unverified against official docs) classification examples: breaking = remove field/type, add required argument, change field type, add non-null, remove enum value; dangerous = change default value, add enum value, add union member, make nullable output non-null; safe = add field/type/optional argument. — [skills.cat summary](https://skills.cat/skills/thebushidocollective/han/graphql-inspector-diff)

### Inferences
- Buf's layered model (lint tiers + compatibility levels keyed to *what the consumer depends on*: generated code vs JSON vs binary) is the most transferable design: compatibility is not binary, it is relative to a consumer class. GraphQL Inspector's `considerUsage` makes the same point empirically.
- Spectral's rule list is a useful checklist of "hygiene" defaults an IDL compiler could enforce natively (unique operation ids, no unused shapes, examples validate, descriptions present).

### Gaps
- GraphQL Inspector's official docs do not enumerate which change kinds fall in each category; only secondary sources do.
- Spectral's rule severities were only partly stated in the source (error vs default warn).
