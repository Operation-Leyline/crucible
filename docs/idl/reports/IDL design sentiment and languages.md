# Keep Smithy's semantics, drop its ceremony

The record across twelve modelling languages supports most of crucible's draft IDL decisions. It also shows where each one can go wrong. Required-by-default with `?` for optional is what every human-authored REST IDL designed in the last decade chose: TypeSpec, Fern, Avro's Kotlin-style `T?`, and Smithy 2.0 in effect. Every general-purpose language that retrofitted null safety chose it too. The famous "required is forever" warnings from protobuf and Cap'n Proto are about required fields *enforced by the parser*, not about required types. So the choice is safe as long as requiredness stays a validation-layer fact, and as long as `crucible-policy` knows the rule cuts in opposite directions for inputs and outputs. Anonymous operation bodies named by a package-wide convention match where protobuf, GraphQL and Smithy all ended up, which is one dedicated, operation-owned type per input and output. The difference is who types the name. First-class errors, typed inline examples, compiler-checked doc links, copy-style `include`, positively bound resources and typed custom metadata each have either a direct precedent or documented pain in the alternative. The weakest evidence covers the most visible choices. No API IDL uses `1..100` range literals for constraints, and nobody has measured whether `@annotations` or keywords read better. Sentiment on Smithy and TypeSpec outside AWS and Microsoft is thin and mostly comes from Hacker News, and in both cases the toolchain runtime (JVM, Node) is the most-cited objection. The biggest risk to crucible's language is therefore tooling, not grammar. Every company-built IDL that lasted shipped a standalone CLI, a stable JSON intermediate form and a compatibility checker. Since Buf's 2026 launch, a language server bundled into the same binary is expected rather than a bonus.

## Required-by-default wins on types and loses only when the parser enforces it

The two camps in this debate optimise for different failures, and once that is clear the evidence stops looking contradictory. General-purpose languages chose non-null-by-default with an opt-in marker because the compiler sees both sides of every call. Mads Torgersen wrote for C# that "it is more common to want a reference _not_ to be null" and that "Nulls, not the absence of them, should be the thing that you explicitly have to opt in to" ([Torgersen, .NET Blog](https://devblogs.microsoft.com/dotnet/nullable-reference-types-in-csharp/)). Dart made "all types _non-nullable by default_" because most existing code already behaved that way ([dart.dev](https://dart.dev/null-safety/understanding-null-safety)). Rust calls `Option<T>` "a deliberate design decision for Rust to limit null's pervasiveness" ([The Rust Book](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html)). Wire formats split along a different line. Their authors were burned by required fields checked during parsing, where two sides compiled from different schema versions disagree at deploy time. Protobuf's proto2 guide now says of `required`: "**Do not use.** Required fields are so problematic they were removed from proto3 and editions" ([protobuf.dev](https://protobuf.dev/programming-guides/proto2/)). Kenton Varda's Cap'n Proto FAQ answers "How do I make a field required?" with "You don't", calling protobuf's version "a horrible mistake" because "the validation is baked into the parser, and there's nothing you can do about it" ([capnproto.org](https://capnproto.org/faq.html)). His specific complaint is that **pass-through middlemen rejected messages with missing fields, causing outages** in Google Search and Gmail ([HN 18196288](https://news.ycombinator.com/item?id=18196288), [HN 7855458](https://news.ycombinator.com/item?id=7855458)).

The newer REST-oriented IDLs sided with the languages. TypeSpec marks optional properties with `?` and allows `=` defaults on both required and optional properties ([TypeSpec models](https://github.com/microsoft/typespec/blob/main/website/src/content/docs/docs/language-basics/models.md)). Fern wraps optional fields in `optional<T>` ([Fern types](https://buildwithfern.com/learn/api-definitions/ferndef/types)). Avro IDL 1.12 added `string? optionalString2 = null;` as an explicitly "Kotlin style" shorthand ([Avro IDL](https://avro.apache.org/docs/1.12.0/idl-language/), [AVRO-3257](https://issues.apache.org/jira/browse/AVRO-3257)). None of the three wrote down a rationale. Smithy is the instructive exception. It keeps optional-by-default syntax ("Structure members in Smithy are automatically considered optional"), but Smithy 2.0 spent most of its design effort making `@required` reach generated types. Before 2.0, generators "essentially treated every structure member as nullable" because `@required` "could be backward-compatibly removed at any time" ([AWS blog](https://aws.amazon.com/blogs/developer/introducing-smithy-idl-2-0)). When smithy-rs switched in November 2023, required simple-type members lost their `Option` wrappers, and the upgrade advice was to delete `.unwrap()` calls ([smithy-rs #2929](https://github.com/smithy-lang/smithy-rs/discussions/2929)). The cost of the opposite default is clearest in GraphQL. It is nullable by default for error-containment reasons, and its designers now describe a "nullable epidemic" that left "client code full of unnecessary null checks" ([Semantic Nullability RFC](https://rfcs.graphql.org/rfcs/SemanticNullability/), [RFC 1153](https://rfcs.graphql.org/rfcs/1153/)). Lee Byron himself wrote in 2025: "I believe most systems will have more non-null fields than nullable. It bothers me that schema will be littered with `!`" ([wg#1700](https://rfcs.graphql.org/rfcs/wg1700/)). Crucible's own corpus points the same way: `docs/idl/decisions.md` counts 1,198 `@required` annotations in Leyline and Pigeon against zero uses of `@clientOptional`, `@input` or `@output`.

What required-by-default must not inherit is evolution fragility, and here the asymmetry is consistent across every system. **Tightening an input breaks old clients; loosening an output breaks consumers who stopped checking.** Google's AIP-180 forbids adding required request fields and treats changing a default as breaking ([AIP-180](https://google.aip.dev/180)). Apollo's guidance says nullable→non-null is safe on outputs and unsafe on inputs ([Apollo GraphOS](https://www.apollographql.com/docs/graphos/schema-design/guides/nullability)). A third case is subtler and matters for a 14-language SDK generator. Loosening a required input to optional is compatible on the wire, but it is a source break for every typed client that exposed the member as `T` rather than `Option<T>`. Smithy's answer was `@input`, which makes every input member optional in clients so services can drop `@required` freely. The price was `Option` on every input member, which is exactly what 2.0 was trying to remove. The same rule still confuses people. In July 2026 a user found that `smithy diff` did not flag making an existing input member required. Michael Dowling (mtdowling), Smithy's creator, replied that the guidance should change so that "the member remains required when validation is performed but is 'optional' in generated types regardless of client or server" ([smithy #3203](https://github.com/smithy-lang/smithy/issues/3203)). Crucible's decision 20 picks the other horn, `client_optional` always false. That is defensible while the only consumers are Leyline and Pigeon, but `crucible-policy` must then report "required input became optional" as an SDK-source break and not wave it through as wire-compatible.

Defaults are where systems diverge most, and the precise semantics matter more than the spelling. Smithy's `@default` makes the generated property non-null while leaving the member omittable on the wire. Its spec warns that defaults "shouldn't be used for partial updates, because a server can't tell an omitted value from one set to the default" ([Smithy type refinement traits](https://smithy.io/2.0/spec/type-refinement-traits.html)). Protobuf's implicit-presence era is the cautionary tale for collapsing absent into default. The team now says "We do not recommend using implicit presence for new fields", lists merge and patch bugs it caused, and notes the issue asking for presence back "became the most-commented issue in the Protobuf repository" ([protobuf.dev](https://protobuf.dev/design-decisions/implicit-presence/)). Thrift supplies the subtle rule on who owns a default: "An unwritten default becomes part of the interface version. Changing that default changes the interface" ([Thrift IDL](https://raw.githubusercontent.com/apache/thrift/master/doc/specs/idl.md)). Combining a marker with a default is murky everywhere. TypeSpec allows `address?: string = "wild"` without defining it, FlatBuffers rejects `(required)` alongside an explicit default ([FlatBuffers](https://flatbuffers.dev/schema/)), and Avro requires `?` fields to default to `null`. Prisma shows the ergonomic pattern most generators converge on: a field with a default is required on the model type but optional on the generated create input ([prisma #12703](https://github.com/prisma/prisma/discussions/12703)). Taken together, the cleanest reading for crucible is three distinct states. A plain member must be present. `name?: T` may be absent and has no default. `name: T = v` is non-null in both directions, may be omitted by a sender, and is optional in client builders. The compiler should reject `?` combined with `= v`, and policy should treat a changed default as breaking.

## Operations converge on one owned type per input, whoever writes the name

Every ecosystem surveyed arrived at the same observable outcome for operation inputs and outputs, even the ones that started elsewhere. Protobuf's "1-1-1" practice makes "the top-level request and response protos unique to each service+method" ([protobuf.dev](https://protobuf.dev/best-practices/1-1-1/)). Buf's lint docs call a unique request and response per RPC "one of the most important rules in modern Protobuf development" because "Sharing a Protobuf message between RPCs means every change to that message ripples across every RPC that references it" ([Buf lint rules](https://buf.build/docs/lint/rules/)). GraphQL natively supports inline arguments, yet the Apollo convention since 2017 is that mutations "should only ever have one input argument, named input, with a non-null unique input object type" ([Apollo blog](https://www.apollographql.com/blog/designing-graphql-mutations)). OpenAPI lets authors inline freely and is punished for it, with generators emitting "generic or similar class names like status1, status2, and inlineResponse200" ([APIMatic](https://www.apimatic.io/openapi/array-of-objects)). The real disagreement is who types the name. Protobuf makes the author write `GetBookRequest`, and practitioners grumble about the boilerplate of empty request and response messages ([HN 41515022](https://news.ycombinator.com/item?id=41515022)). Smithy 2.0's inline `input := { ... }` synthesises `<Op>Input`, with the suffix configurable through `$operationInputSuffix` ([Smithy IDL](https://smithy.io/2.0/spec/idl.html)). TypeSpec treats parameters as an anonymous model and leaves naming to emitters. That gap is why Azure ships a `no-unnamed-types` lint and the Java emitter an `empty-name` diagnostic ([TCGC](https://azure.github.io/typespec-azure/docs/libraries/typespec-client-generator-core/rules/no-unnamed-types/)), and why Fern's docs annotate an inline request with "this name is required for idiomatic SDKs" ([Fern endpoints](https://buildwithfern.com/learn/api-definitions/ferndef/endpoints)).

Crucible's decision 25 (anonymous bodies, never referenceable, named by a package-wide rule) takes the best of each. Its "never referenceable" clause has a documented justification: Smithy's `@input` trait exists so that "Required members of a structure marked with the @input trait are implicitly considered clientOptional", which is only safe because no other operation can share the shape ([Smithy type refinement traits](https://smithy.io/2.0/spec/type-refinement-traits.html)). The one counter-precedent is Google's AIP-131, where a Get returns the resource itself ("There is no `GetBookResponse`") ([AIP-131](https://google.aip.dev/131)). Crucible handles that case with `include` rather than a shared type, at the price of the generated-name change the decisions already flag.

Errors are where crucible departs from its siblings most visibly, and the departure is smaller than it looks. Among HTTP-oriented IDLs, Smithy uses `@error("client"|"server")` plus a separate `@httpError` ([Smithy HTTP bindings](https://smithy.io/2.0/spec/http-bindings.html)), TypeSpec uses an `@error` model and `@statusCode` in return unions ([TypeSpec HTTP](https://raw.githubusercontent.com/microsoft/typespec/main/website/src/content/docs/docs/libraries/http/operations.md)), and Fern declares errors in an `errors:` block with a `status-code` ([Fern errors](https://buildwithfern.com/learn/api-definitions/ferndef/errors)). The RPC IDLs already have keywords: Avro's `error Kaboom { ... }` "uses the same body syntax as `record`", and Thrift has `exception` ([Avro IDL](https://avro.apache.org/docs/1.12.0/idl-language/), [Thrift IDL](https://thrift.apache.org/docs/idl)). Crucible's `error NotFoundError { status 404 ... }` is close to Fern with Avro's keyword. Smithy splits fault from status for protocol neutrality. gRPC goes further and keeps errors out of the IDL entirely, using 16 canonical codes and typed details ([grpc.io](https://grpc.io/docs/guides/error/)). Crucible serves one protocol, so deriving fault from status costs nothing today. It becomes a mapping problem only if a non-HTTP protocol returns.

The harder issue is one Fern documents and the others leave to generators: how a client tells two errors with the same status apart. Fern's status-code discrimination requires each endpoint's errors to have distinct codes. Its name discrimination instead assumes "every error response has an extra property denoting the error name" ([Fern api.yml errors](https://buildwithfern.com/learn/api-definitions/ferndef/api-yml/errors)). On the envelope, the strongest practitioner guide is Zalando's. It mandates RFC 9457 Problem JSON on every endpoint, allows "custom problem types as extensions", and deliberately makes `type` URIs non-resolvable because "URLs are fragile and can drift out of sync over time" ([Zalando #176](https://opensource.zalando.com/restful-api-guidelines/#176), [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457)). Google's AIP-193 reaches the same "both" answer from the gRPC side: canonical code plus a machine-readable `(reason, domain)` pair ([AIP-193](https://google.aip.dev/193)).

Inferring path-label bindings from the URI template is safer in crucible's design than in TypeSpec's, because the failure modes come from fallback rules, not from inference itself. TypeSpec binds `{petId}` by name. Its trap is that "Path parameters are appended to the URL unless a substitution with that parameter name exists", and unannotated parameters fall into the body ([TypeSpec HTTP](https://typespec.io/docs/libraries/http/operations/)). A typo therefore yields a different valid API, which is why Azure added a `no-route-parameter-name-mismatch` lint. That lint itself admits "a relatively high false-positive rate" ([typespec-azure](https://azure.github.io/typespec-azure/docs/libraries/azure-core/rules/no-route-parameter-name-mismatch/)). Smithy's explicit `@httpLabel` adds less information than it seems. The spec already requires every labelled member to have "a corresponding URI label with the same name as the member", and every label to bind a required member ([Smithy HTTP bindings](https://smithy.io/2.0/spec/http-bindings.html)). Inference is safe if the compiler makes every unbound `{label}` an error, forbids `?` on a label-bound member, and never silently reroutes a member. FastAPI's route-order shadowing, where `/users/{user_id}` captures `/users/me` ([FastAPI](https://fastapi.tiangolo.com/tutorial/path-params/)), is a separate hazard for the route-uniqueness check in decision 48. Spring 6.1's removal of bytecode parameter-name recovery is a reminder to infer from the model, never from the environment ([Spring 6.1 notes](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-6.1-Release-Notes)).

## Syntax choices have the least evidence and the loudest opinions

Annotations versus keywords is the question practitioners argue about most and researchers have measured least. TypeSpec and Smithy both justify `@` syntax by extensibility. Decorators "form the core of TypeSpec's extensibility" ([TypeSpec decorators](https://typespec.io/docs/language-basics/decorators/)), and Smithy traits "extend a model and add capabilities that are not part of the core specification" ([smithy.io](https://smithy.io/2.0/)). Neither project documents a comparison with keyword alternatives. The objections are aesthetic: "The syntax leaves a bad first impression. I'm getting flashbacks to Java EE/JAX-RS days" ([HN 41601728](https://news.ycombinator.com/item?id=41601728)). The only empirical study found, a 2024 survey of 332 Java developers, saw preferences "scattered for all categories of annotation usage, revealing no consensus" ([arXiv 2404.17417](https://arxiv.org/abs/2404.17417)). TypeSpec's documented pain was not the `@` but its argument typing. Issue #2046 describes decorator arguments limited to string, number and boolean, with models "misused" to fill the gap ([typespec #2046](https://github.com/microsoft/typespec/issues/2046)). The defensible position is a hybrid with a stated boundary rule. Keywords should cover the closed set of semantics the compiler validates and the IR models (`readonly`, `idempotent`, `public`, `strict`, `internal`, `sensitive`), and `@` should cover open-ended metadata whose arguments the compiler type-checks. The rule matters more than either spelling. The draft weather model already writes `@token`, while decision 27 describes `token` as a marker without saying which form it takes.

Constraint syntax has no precedent at all for crucible's choice. Shipping schema languages use keyword or annotation forms (Smithy `@range(min:, max:)`, TypeSpec `@minValue`, Fern's `validation:` block) or boolean predicates (CUE `>=1 & <=100`, Pkl `Int(isBetween(0, 1023))`, protovalidate's CEL) ([CUE](https://cuelang.org/docs/tour/types/bounds/), [Pkl](https://pkl-lang.org/main/current/language-reference/index.html)). **No API IDL uses bare `1..100` range literals**, and no usability study compares the forms. Precedent elsewhere is mixed. Pascal-style subranges and Kotlin ranges are inclusive, but Rust's `a..b` is half-open. A Rust team writing `range 1..100` in a language implemented in Rust should expect some readers to assume 100 is excluded, so the spec should state that bounds are inclusive and consider spelling it `1..=100` or rejecting the ambiguity. The stronger lesson concerns vocabulary size, not spelling. Buf moved protovalidate to CEL because protoc-gen-validate's per-language templates had "fossilized" and caused "inconsistent rule support, even across official targets" ([Buf blog](https://buf.build/blog/protoc-gen-validate-v1-and-v2)). That failure belongs to systems that generate validators per language. Crucible validates once in the Rust server runtime, as Smithy and Fern do (Fern: constraints "are enforced by the server, but the generated client SDKs don't include validation logic"; [Fern types](https://buildwithfern.com/learn/api-definitions/ferndef/types)). A small closed vocabulary (`length`, `range`, `pattern`, `unique`) is therefore sustainable, and an expression language can wait for a real cross-field need.

Documentation and examples are the two areas where the evidence turns a convenience into a correctness argument. Smithy's `///` is CommonMark, TypeSpec's `/** */` is equivalent to `@doc`, and GraphQL's `"""` descriptions are reachable through introspection. None of their specs mentions link resolution ([Smithy IDL](https://smithy.io/2.0/spec/idl.html), [TypeSpec docs](https://typespec.io/docs/language-basics/documentation/), [graphql.org](https://graphql.org/learn/schema/)). The only precedent for compiler-checked `[Name]` links is rustdoc. RFC 1946 was motivated by link rot across rendering contexts ([RFC 1946](https://rust-lang.github.io/rfcs/1946-intra-rustdoc-links.html)). Today `broken_intra_doc_links` "warns by default", ignores links containing `/` or `[]`, and is silent across crates ([rustdoc lints](https://doc.rust-lang.org/rustdoc/lints.html)). Crucible's decision 41 to make dangling links an error goes further than rustdoc. That is reasonable for a single-namespace package, but the grammar needs rustdoc-style escape rules for literal brackets in prose. On examples, both modern IDLs type-check them. TypeSpec 0.58 requires example values that "MUST be assignable to the type" ([TypeSpec 0.58](https://typespec.io/release-notes/typespec-0-58/)), and Smithy ships an `ExamplesTraitValidator` ([Smithy javadoc](https://smithy.io/javadoc/1.52.0/software/amazon/smithy/model/validation/validators/package-summary.html)). Both are direct responses to OpenAPI, where examples are only "suggested" to match and third-party linters like 42Crunch and Spectral exist to catch drift ([42Crunch](https://docs.42crunch.com/latest/content/oasv3/oasconformance/bestpractices/v3-warning-example-schema-not-consistent.htm)). Smithy adds one detail worth copying, `allowConstraintErrors`. An error example sometimes needs an input that violates constraints, and a naive "examples must validate" rule forbids it ([Smithy documentation traits](https://smithy.io/2.0/spec/documentation-traits.html)).

## Copy-style reuse and positive resource binding remove the annotations users fight

Member reuse has a clear negative lesson, which is to never let tools infer inheritance from structure. Smithy's mixin design document rejects inheritance on wire-compatibility grounds: "specializing structures can break clients", and mixins "do not introduce any kind of runtime polymorphism" ([Smithy mixins design](https://github.com/smithy-lang/smithy/blob/main/designs/mixins.md)). The spec adds that removing a mixin is backward compatible when the members are restated, because copied members keep the target's shape ID ([Smithy mixins](https://smithy.io/2.0/spec/mixins.html)). TypeSpec's `...` spread "doesn't create any nominal relationship" ([TypeSpec models](https://typespec.io/docs/language-basics/models/)). OpenAPI's `allOf` is the cautionary case. Maintainers insist it "is simply model composition and does not imply a hierarchy", yet removing inheritance treatment for single-`$ref` `allOf` "broke things in the OpenAPI Generator" ([OAI #2500](https://github.com/OAI/OpenAPI-Specification/issues/2500)). Crucible's `include`, flattened before the IR, has the same semantics as a Smithy mixin or TypeSpec spread with simpler syntax. On the open question of whether `include` may target a structure that is also used as a type, TypeSpec's spread works on any model, and no friction from that freedom was found. Smithy's ban on members targeting mixins exists because mixins are not types, which `include` sidesteps.

Resources are where Smithy's design is both most valued and most fought. Smithy's resource shape is the most complete lifecycle model in a mainstream IDL. Mtdowling credits it with steering AWS teams toward good HTTP design and with deriving CloudFormation schemas automatically ([HN 27081084](https://news.ycombinator.com/item?id=27081084), [Smithy aws.cloudformation](https://smithy.io/2.0/aws/aws-cloudformation.html)). The friction is almost entirely in binding. Identifier and property binding is inferred by member name, every top-level member must bind or carry `@notProperty`, and `@nestedProperties` has no exclusion mechanism one level down ([Smithy service types](https://smithy.io/2.0/spec/service-types.html), [Smithy resource traits](https://smithy.io/2.0/spec/resource-traits.html)). In issue #2294, combining `@nestedProperties` with elision produced an error that maintainers called "a bit unclear", fixed only by an explicit `@resourceIdentifier` ([smithy #2294](https://github.com/smithy-lang/smithy/issues/2294)). In February 2026 a maintainer acknowledged that properties bound through a list output "seem to not consider... to be bound at all, for any purpose" ([smithy #2968](https://github.com/smithy-lang/smithy/issues/2968)). The alternatives show what a missing first-class construct costs. Google's api-linter carries **342 core rules**, of which roughly 80 check request/response shape and 63 HTTP binding, much of it verifying by convention what a `resource` block would guarantee by construction ([api-linter](https://linter.aip.dev/rules/core/)). TypeSpec's ARM library needs around ten lint rules (`list-response-envelope`, `beyond-nesting-levels` and others) to hold its template-based resources consistent ([typespec-azure ARM](https://github.com/Azure/typespec-azure/blob/main/packages/typespec-azure-resource-manager/README.md)).

Crucible's positive binding (decision 31) removes the 323 `@notProperty` uses outright, but decision 32 reintroduces inference by name and by type. The lesson from Smithy and from Speakeasy is to infer only what is unambiguous and to make every inference explainable. Speakeasy abandoned pure path-convention inference for Terraform and now requires `x-speakeasy-entity-operation` annotations for operation roles. It still infers Required, Optional and Computed attributes from request and response presence ([Speakeasy entity mapping](https://speakeasy.com/docs/terraform/entity-mapping)). For crucible's infrastructure generators, the target is the list CloudFormation's registry schema spells out: `primaryIdentifier`, `additionalIdentifiers`, `createOnlyProperties`, `readOnlyProperties`, `writeOnlyProperties`, and replacement when no update handler exists ([CloudFormation schema](https://docs.aws.amazon.com/cloudformation-cli/latest/userguide/resource-type-schema.html)). Smithy's CloudFormation generator derives mutability from which lifecycle operation carries each member and lets `@cfnMutability` override it, a pattern the IR should expose so every generator reads the result instead of recomputing it.

## Typed metadata and tiered policy are the converged extension model

On custom metadata, the field has converged on declared, typed, target-restricted annotations, with one lesson about where they must be visible. Smithy traits are shapes: `selector` constrains targets, `conflicts` forbids combinations, and `breakingChanges` "Defines the backward compatibility rules of the trait" ([Smithy model spec](https://smithy.io/2.0/spec/model.html)). Cap'n Proto declares `annotation foo(struct, enum) :Text;` with an explicit target list, almost exactly crucible's `metadata tier on operation: string` ([Cap'n Proto](https://capnproto.org/language.html)). Protobuf custom options are typed extensions with a retention flag. They "have runtime retention by default", while `RETENTION_SOURCE` keeps them visible only to the compiler and plugins ([protobuf.dev](https://protobuf.dev/programming-guides/proto3/)). TypeSpec added `auto dec`, which needs no JavaScript and lets "the compiler auto-generate the storage logic" ([TypeSpec decorators](https://typespec.io/docs/extending-typespec/create-decorators/)). That is effectively an admission that most custom decorators are pure data. The negative lessons come from GraphQL and OpenAPI. GraphQL directives are typed but invisible to introspection, a gap open since 2017 that forces tools to re-parse SDL ([graphql-spec #300](https://github.com/graphql/graphql-spec/issues/300)). OpenAPI's `x-` extensions are untyped and "may or may not be supported by the available tooling" ([OAS 3.1](https://spec.openapis.org/oas/v3.1.0.html)). Crucible's decision 43 (target kinds, typed values, `conflicts with`, no selectors, carried into the IR) matches the converged design. For a Rust compiler it is also the economical one: a JS or WASM plugin layer is costly, and Parcel measured WASM at 10 to 20 times slower than native ([leerob.com](https://leerob.com/n/rust)). Two refinements have precedent. A retention or audience flag, borrowed from protobuf, would let a runtime receive only the keys it consumes. A per-key compatibility rule, borrowed from Smithy's `breakingChanges`, would let `crucible-policy` know whether changing a key's value is breaking.

Lint and policy tools share a recognisable structure, and crucible's two-layer split fits it. Buf groups rules into opt-in strictness tiers (MINIMAL, BASIC, STANDARD, plus orthogonal COMMENTS and UNARY_RPC) "so you can opt in to a strictness level rather than enabling rules one at a time". It also defines four breaking-change levels keyed to what consumers depend on, from FILE (generated code) down to WIRE ([Buf lint](https://buf.build/docs/lint/rules/), [Buf breaking](https://buf.build/docs/breaking/rules/)). Smithy separates unsuppressible ERROR from DANGER, WARNING and NOTE, requires a reason on suppressions, and offers code-free `EmitEachSelector` rules ([Smithy model validation](https://smithy.io/2.0/spec/model-validation.html)). Spectral's 57-rule OpenAPI set leans on hygiene: unique operation IDs, description presence, unused components, examples that validate ([Spectral rules](https://github.com/stoplightio/spectral/blob/develop/docs/reference/openapi-rules.md)). GraphQL Inspector classifies diffs as breaking, dangerous or safe, and can soften "breaking" using usage data ([GraphQL Inspector](https://the-guild.dev/graphql/inspector/docs/essentials/diff)). Across all four, the dominant rule types are naming and suffix conventions, documentation presence, required-metadata presence and compatibility. One HN commenter shows that compatibility is relative to the consumer: moving a field into a `oneof` is wire-compatible but breaks generated Go ([HN 49322573](https://news.ycombinator.com/item?id=49322573)). Crucible's policy already distinguishes SDK-source breaks from wire breaks. The decisions should keep that consumer-class axis explicit, along with Buf's tiered packaging that makes adoption incremental.

## Toolchains, not grammars, decided Smithy's and TypeSpec's reach

Public sentiment on both incumbents outside their home companies is thin, and it is consistent about the toolchain. A December 2023 "Ask HN: Does anyone use AWS Smithy outside of AWS?" drew **exactly one reply**, which pointed to Disney Streaming's smithy4s ([HN 38546950](https://news.ycombinator.com/item?id=38546950)). Smithy's visible non-AWS ecosystem is essentially that Scala community. AWS's own list still marks the TypeScript, Rust, Go, Python, Ruby and Swift generators as under construction ([awesome-smithy](https://github.com/smithy-lang/awesome-smithy)). The most-cited reason to prefer TypeSpec is Smithy's runtime: TypeSpec's "lack of Kotlin and Gradle is a significant advantage over Smithy" ([HN 40206124](https://news.ycombinator.com/item?id=40206124)). AWS built a standalone CLI in 2023 because the Gradle workflow "is overly complex for developers who aren't already familiar with these tools" ([AWS blog](https://aws.amazon.com/blogs/developer/introducing-the-smithy-cli)). In 2025 it declined to publish that CLI to npm, explaining that "what we're distributing is a minimal JRE alongside a fat jar" ([smithy #2569](https://github.com/smithy-lang/smithy/issues/2569)). TypeSpec has more stars (5,880 against Smithy's 2,373 on 2026-10-08) and more enthusiasm, typified by "It's so much better than writing OpenAPI by hand, and I never ever will do that again" ([HN 39833321](https://news.ycombinator.com/item?id=39833321)). Its 1.0 announcement, however, could name only Pinterest as an outside collaborator, and versioning remained a preview library ([TypeSpec 1.0 GA](https://typespec.io/blog/typespec-1-0-GA-release/)). Its objections mirror Smithy's: "you still need node to run this thing" plus "yet another DSL" fatigue ([HN 41601728](https://news.ycombinator.com/item?id=41601728)). This evidence is thinner than it looks. Reddit was unreachable, and no company engineering blog explaining a choice of either language was found.

The table stakes are now explicit. Buf's v1 CLI aimed to be "a 'one-stop shop' for Protobuf development" with lint, breaking-change detection against git refs, and generation ([Buf CLI v1](https://buf.build/blog/buf-cli-v1)). In January 2026 Buf shipped a protobuf language server bundled into the same CLI binary, because "Protobuf lacked the same LSP support other major programming languages enjoy" ([Buf LSP](https://buf.build/blog/protobuf-lsp)). Smithy users asked for click-to-definition in both 2021 and 2024 ([HN 40206124](https://news.ycombinator.com/item?id=40206124)), and the official IntelliJ plugin has not been pushed since March 2022 ([awslabs/smithy-intellij](https://github.com/awslabs/smithy-intellij)). TypeSpec's VS Code extension and playground are part of its stable set and draw the praise. Rust tooling has a known adoption formula: order-of-magnitude speed, output compatibility, and prebuilt binaries shipped through existing package managers. Ruff ships "10-100x faster" with no runtime dependencies ([ruff](https://pypi.python.org/pypi/ruff)), and its acknowledged cost is a thinner plugin ecosystem ([leerob.com](https://leerob.com/n/rust)). A single native `crucible` binary that compiles, formats, lints, diffs and serves the LSP removes the objection both incumbents could not shake.

The build-your-own record points the same way. Palantir's Conjure kept its YAML IDL because "the constraints it imposes on API design... produce focus and clarity". It published a JSON IR plus a generator CLI contract (RFC002), never open-sourced its back-compat checker, and stayed a Palantir-only ecosystem at 492 stars despite a 2018 HN reception asking whether it was "a step backwards from... Thrift or Protobufs" ([Conjure concepts](https://github.com/palantir/conjure/blob/master/docs/concepts.md), [HN 18494628](https://news.ycombinator.com/item?id=18494628)). Stripe's internal Ruby DSL emits OpenAPI so that one person no longer has to keep seven client libraries current ([brandur.org](https://brandur.org/fragments/stripe-codegen)). Microsoft renamed Cadl to TypeSpec before 1.0 with deprecated aliases and a migration tool ([TypeSpec migration notes](https://typespec.io/docs/release-notes/cadl-typespec-migration)). Fern now tells new customers its own definition format "isn't recommended" and steers them to OpenAPI ([Fern errors](https://buildwithfern.com/learn/api-definition/fern/errors)). One cost is new: a bespoke language starts at a disadvantage because language models are trained on existing ones ([HN 40206124](https://news.ycombinator.com/item?id=40206124)). Crucible's position is unusually favourable on the external costs, since its only consumers are Leyline and Pigeon and it already emits OpenAPI. The costs that remain are internal: learning curve, model familiarity, and a toolchain that has to be as good as Buf's from the first release.

## Conclusion and recommendations

The research changes the framing of crucible's riskiest decision. Required-by-default is not a bet against protobuf's experience. It is the position protobuf's own team reached: explicit presence everywhere, with requiredness as a validation fact and not a parse fact. The real exposure is the input-loosening case, which Smithy has been unable to explain to its own users since 2.0. A second, less obvious finding is that crucible's single protocol and single server-side validator make several Smithy constructs unnecessary rather than merely awkward: the fault/status split, per-language constraint codegen, and the `@input`/`@clientOptional` matrix. Each existed to serve protocol neutrality or many independent runtimes. Crucible can drop them as long as it records that choice as a constraint on future protocols. Last, every documented failure of inference (TypeSpec's path fallback, Smithy's resource binding, OpenAPI's `allOf`) came from a silent fallback, never from the inference itself. "Infer, and make every miss a hard error" turns out to be the one rule that applies across questions 6, 9 and 10.

Evidence strength below means: **Strong**, multiple primary designer rationales plus documented outcomes; **Moderate**, one or two primary precedents or consistent attributed practitioner sentiment; **Weak**, analogy or thin anecdote; **None**, no precedent found either way.

| # | Open question | Recommendation | Evidence |
|---|---|---|---|
| 1 | Required-by-default, `?`, `= default` | Adopt required-by-default with `?`. Keep required a server-validation and type fact, never a client-parse rejection. Three states: plain (present), `?` (may be absent, no default), `= v` (non-null, sender may omit, optional in client builders). Reject `?` combined with `= v`. Policy flags tightened inputs, loosened outputs, changed defaults, and loosened inputs as an SDK-source break. | **Strong** on type ergonomics and evolution mechanics; **Moderate** on the exact default semantics |
| 2 | Anonymous I/O named by convention | Adopt: bodies never referenceable, names from one manifest rule. This keeps Smithy's `@input` uniqueness guarantee without the `FooRequest` boilerplate. | **Strong** (protobuf, Buf, GraphQL, Smithy converge) |
| 3 | `@annotation` vs keywords | Use a hybrid with a written rule: keywords for closed, compiler-validated semantics; `@` for open metadata and bindings with type-checked arguments. Resolve inconsistencies like `@token` vs `token`. | **Weak** (no comparative data; TypeSpec #2046 supports typed arguments) |
| 4 | `{ length 1..100 }` | Keep a small closed vocabulary validated once in the runtime. State that bounds are inclusive, and consider `..=` or a lint, because Rust readers parse `..` as half-open. Defer CEL-style expressions. | **None** for range literals; **Moderate** for the closed vocabulary (Buf/PGV, Fern, Smithy) |
| 5 | First-class `error` with status | Adopt. Guarantee a wire discriminator independent of status so two same-status errors stay distinguishable, and consider an RFC 9457-compatible envelope. Record that fault-from-status assumes HTTP. | **Moderate** (Fern, Avro, Zalando, AIP-193) |
| 6 | Path labels inferred from URI | Adopt inference with hard errors: every `{label}` binds a member of the same name, label members cannot be `?`, nothing falls back to path or body silently, and ambiguous routes are rejected. | **Moderate** (TypeSpec and FastAPI pitfalls are fallback-driven; Smithy names must already match) |
| 7 | `///` Markdown, checked `[Name]` links | Adopt as an error, with rustdoc-style escape rules for literal brackets and a defined resolution scope. | **Moderate** (one strong precedent, rustdoc; no IDL does it) |
| 8 | Inline `example` blocks | Adopt with type-checking, error examples bound to declared errors, and an `allowConstraintErrors`-style escape hatch. | **Strong** (Smithy, TypeSpec, OpenAPI drift evidence) |
| 9 | `include` vs mixins/spread/inheritance | Adopt copy-semantics `include`, flattened before the IR. No inheritance. Allowing `include` of a structure also used as a type is fine. | **Strong** against inheritance; **Moderate** for `include` targeting types |
| 10 | Positive resource binding | Adopt. Limit inference to unambiguous cases with diagnostics that name the rule. Treat list-output binding as first-class, and expose derived per-property mutability (create-only, read-only, write-only) in the IR. | **Strong** (Smithy issues, api-linter and ARM lint burden, CFN and Terraform needs) |
| 11 | Typed IDL-declared metadata | Adopt decision 43. Consider a retention or audience flag and a per-key compatibility rule. Keep metadata in the IR's reflection surface, not side files. | **Strong** (Smithy, Cap'n Proto, protobuf, TypeSpec `auto dec`; GraphQL #300 as the counterexample) |
| 12 | Linting and policy | Keep compiler validity separate from `crucible-policy` conventions. Add Buf-style strictness tiers, reasons on every exception, and compatibility levels keyed to consumer class (wire, JSON, generated source). | **Moderate** (four mature tools converge; no usage telemetry) |
| 13 | Tooling and distribution | Ship one native binary covering compile, format, lint, diff and LSP, distributed through cargo, brew and npm/pip wrappers. Keep the versioned JSON IR as the generator contract, open-source the diff, and fix the name before 1.0. | **Strong** on distribution (Smithy CLI, Buf, Ruff); **Moderate** on own-IDL lessons |
| 14 | Smithy/TypeSpec sentiment outside AWS/Microsoft | Treat both as niche outside their home companies, with toolchain runtime as the main complaint. This supports replacing Smithy but offers no external community to inherit. | **Moderate** (consistent but HN-heavy; Reddit unreachable) |
